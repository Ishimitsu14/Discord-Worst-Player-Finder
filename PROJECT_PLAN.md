# Discord Worst Player Finder — план проекта

Обновлено: 17 октября 2026. Этот файл содержит общий контекст для отдельных чатов по модулям. Подробные спеки создаются в OpenSpec; весь предыдущий диалог для работы не требуется.

## Согласованные решения

- Частный Discord-бот для компании друзей, один сервер и один канал публикации в первой версии.
- Только рейтинговые матчи Dota 2. Обычные игры, Turbo и нестандартные режимы в первую версию не входят.
- Настраивается простой список Steam32 account ID компании. Привязки к людям, владельцам аккаунтов или Discord-пользователям не нужны.
- Авторазбор — если минимум два аккаунта из списка играли на одной стороне. Также нужен ручной запуск по ID матча.
- Худшего выбираем среди всех пяти союзников, включая случайных игроков, после победы и поражения. Соперники дают контекст.
- Новый профиль Gemini выбирает ровно одного худшего; при близких кандидатах указывает низкую уверенность. Это шуточный бот: гиперболы, подколы и вольные игровые объяснения допустимы и не блокируют приёмку текста из-за недостаточной доказательности. Исходные числа, авторство цитат и техническая схема сохраняются; постоянные оговорки не нужны. Прежний формат MiMo сохраняется для старых пакетов.
- Целевой формат на русском: ник и герой, ироничная номинация, 3–4 игровых основания, собственная цитата при наличии и более едкий roast с допустимым матом, исход и ссылка на OpenDota. В самом конце — три игровых фактора поражения; после победы — три слабых места команды. Выбор и командные основания — по игре; чат используется для roast.
- Для обнаружения новых матчей согласован Steam Web API с опросом всей компании раз в минуту; закрытая история не удаляет аккаунт из списка, но ограничивает покрытие. Подробная статистика, подтверждение состава и реплеи остаются в OpenDota. Спека перехода готова, работающий runtime пока использует прежний поиск. Новый целевой профиль анализа — OpenRouter `google/gemini-3.8-flash` по присланному документу пользователя; компактные факты и новый аналитик реализованы и проверены локально, профиль остаётся experimental. Прежние MiMo-пакеты `xiaomi/mimo-v2.6-pro` и работающий runtime не переключены.
- Один сервис на VPS: TypeScript, Node.js, discord.js, SQLite. Разработка на Windows/PowerShell, запуск также на Linux. Модули — части одного приложения.
- Код подготавливает факты и считает показатели; модель интерпретирует их и выбирает худшего. Для нового профиля приняты правила из документа Gemini; качество, задержку и стоимость ещё предстоит проверить реальными экспериментами. Нашу сторону по-прежнему определяет pipeline по Steam32 ID, независимо от исхода матча.

## Важные границы между модулями

- Клиент OpenDota не выбирает рейтинговые игры, нашу сторону или худшего игрока. Его готовый проект контракта: [дизайн](openspec/changes/add-opendota-client/design.md), [требования](openspec/changes/add-opendota-client/specs/opendota-client/spec.md), [задачи](openspec/changes/add-opendota-client/tasks.md).
- OpenDota скачивает и разбирает реплей самостоятельно; бот отправляет ID матча и получает job ID. Готовность подтверждается свежими данными матча, а не исчезновением задания.
- Отсутствие расширенных данных, `null`, числовой ноль и пустой массив — разные состояния. Игрок внутри матча определяется по `player_slot`, даже без публичного account ID.
- Состояние `parsed` не гарантирует полноту всех логов. Пригодность данных для оценки проверяет подготовка фактов, ограничения передаются аналитику.
- Очередь и постоянная защита от повторной обработки принадлежат обработке матчей и хранилищу. Кеш клиента и объединение одновременных запросов действуют в пределах процесса.
- Discord оформляет результат, аналитик выбирает худшего по игре, а инструкция опирается на принятые правила и выводы лаборатории. Чат используется для roast. Плохой KDA сам по себе не доказывает плохую игру; «худший» и «причина поражения» требуют разных выводов.
- «Скилл» аналитика — загружаемая в запрос версионируемая инструкция с примерами и форматом ответа. Это отдельный артефакт продукта, не глобальный навык Codex и не обучение весов модели.

Ниже сохранён исходный порядок разработки проекта; текущее состояние реализации указано в таблице модулей.

1. Спека клиента OpenDota готова. Реализовать его можно по отдельному запросу, используя существующее изменение.
2. Следующая рекомендуемая спека — лаборатория оценки: начать с этих двух матчей, добавить третий для первых гипотез, собрать ручную обратную связь.
3. Проверить критерии на дополнительных играх, включая отдельные проверочные матчи, не использованные для примеров. Начальный ориентир — 10–15 матчей суммарно; сравнивать полный и сокращённый контекст модели.
4. По экспериментам уточнить спеки подготовки фактов и аналитика, первую инструкцию MiMo и формат результатов.
5. Подготовить спеки остальных модулей. Настройки компании и хранилище можно обсуждать независимо от калибровки модели; стыки сверять по документам.
6. Собирать приложение по этапам: ручной запрос → OpenDota → факты → MiMo → Discord; затем автоматический запуск, восстановление и VPS.

Для отдельной спеки не требуется сначала реализовать всех соседей. Изучай только их существующие контракты; не создавай реализации или полные спеки других модулей в том же чате без запроса.

## Как начать отдельный чат

Открой новый чат в этой же папке проекта и укажи ID модуля из таблицы. Например:

> Подготовь OpenSpec-спеку модуля evaluation-lab по PROJECT_PLAN.md. Прочитай AGENTS.md, общие решения и относящиеся к модулю документы. Работай только над этой спекой, без реализации кода.

Один модуль — одно изменение OpenSpec. Перед созданием проверь активные изменения и существующие спеки, чтобы продолжить подходящее изменение вместо дубликата. Готовые документы хранятся в `openspec/changes/<change>/`; в `openspec/specs/` переносятся по жизненному циклу OpenSpec, а не объявляются реализованными при написании.

На 17 октября 2026 установлен OpenSpec 1.14.2 с локальными навыками Codex. Проверка документации изменения: `openspec.cmd validate <change> --type change --strict --no-interactive` в PowerShell. В Linux используется команда `openspec`.

При завершении модуля обновляй его строку состояния и ссылку здесь. Детальные решения сохраняй в его OpenSpec-документах. При расхождении статуса с файлами сверяй `openspec list`, `status` и задачи: этот план — обзор, а не автоматический счётчик.
