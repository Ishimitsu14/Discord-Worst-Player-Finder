# Design

## Context

Мотивация и границы — в proposal.md. Исследован фактический код на 17 октября 2026:

| Стык | Наблюдаемое состояние |
|---|---|
| match-analysis | prepareGeminiAnalysis/analyzeGeminiMatch/validateGeminiAnalysis/presentGeminiAnalysis/checkGeminiRecovery уже существуют; Gemini v1/v2 и SSE проверены отдельно, автоматический management recovery — синтетически |
| match-facts | prepareCompactMatchFacts требует основной dictionary и heroMetricsDictionary; compact manifest использует sourceDataDigest вместо legacy dataDigest; публичной отдельной проверки этих словарей без snapshot пока нет |
| storage | схема 2; Job не хранит профиль; saveInputs/validateAttempt/receipt принимают только legacy, строгий список полей отклоняет SSE-поля Gemini; generic reserveAnalysis и resolveUncertain не ограничивают цепочку Gemini-повтора |
| pipeline | execute/analyze жёстко вызывают prepareMatchFacts/prepareAnalysis/analyzeMatch; sentFailure завершает обработку, budget блокирует любой unknown; один worker и отдельный discovery loop уже есть |
| Discord | renderAnalysis читает allies/selectedPlayers прежнего формата; cleanText/shorten/validateEmbed, nonce, отключённые mentions и постоянный журнал публикации пригодны для повторного использования |
| operations | loadService загружает analysis/prompts/v1 и основной dictionary; CLI не передаёт management key; health имеет закрытую схему прежних агрегатов |
| deploy | package.mjs включает analysis/prompts целиком, но из словарей только dotaconstants-v1.json: hero-metrics-v1.json сейчас отсутствует в runtime-артефакте |

Последний полный локальный набор до этой спеки: 426 тестов, 420 pass/6 Linux-only skip. Это исходная проверка уже сделанного Steam-изменения, не проверка планируемой интеграции. Новый Steam-клиент проверен двумя живыми GET; он не подтверждает Gemini runtime. Новые upstream возможности не предполагаются: интеграция использует уже реализованные клиенты, а перед каждой будущей генерацией остаётся свежий preflight endpoint/тарифов.

## Goals / Non-Goals

**Goals:** подключить существующий Gemini v2 к обычному ручному пути; сохранять оба семейства исходных форматов и их историю; перенести ограниченный recovery из лаборатории в постоянный журнал worker без скрытых повторов; включить комплектность материалов в offline-проверку артефакта.

**Non-Goals:** новая модель, промпт, эвристики выбора или транспорт; общий плагинный движок моделей; параллельные AI workers; новая очередь; миграция лабораторных файлов в рабочую БД; реальные сообщения/генерации, изменение установленного service.json, доставка/перенос ключей или калибровка. Синтетические проверки автоматического пути не означают включение automatic на VPS.

## Decisions

### 1. Профиль сохраняется в задаче, существующий default остаётся legacy

Добавить PipelineOptions.analysisProfile: `legacy | gemini`, default legacy. В Storage новые входы enqueueInitial/createRevision получают необязательный такой же выбор; Job возвращает закреплённый analysisProfile. В следующей миграции jobs получают NOT NULL колонку с default legacy и закрытым CHECK. Новые задачи получают выбранный профиль, старые — legacy даже до подготовки фактов. Первая задача пары matchId/side общая для профилей; смена модели не создаёт вторую первую задачу. Для Gemini после старого результата нужен явный admin reanalysis с новой ревизией.

Существующие revision_requests.digest не пересчитываются. Legacy-вход канонизируется в прежнюю форму без нового поля, в том числе при явно указанном legacy. Gemini входит в digest нового запроса. Повтор старого ключа с тем же старым входом остаётся идемпотентным; тот же ключ с другим профилем даёт конфликт. Проверить это отдельной старой фикстурой, а не только новой БД.

Альтернатива — определять профиль по текущему config или наличию prepared. Она меняет ещё не подготовленные старые задачи после рестарта, поэтому не подходит. Параметр обязателен лишь для осознанного выбора нового поведения, отдельные произвольные model/provider настройки не добавляются.

### 2. Исходные форматы и закрытая валидация

В публичных storage/pipeline контрактах добавить различимые варианты legacy/Gemini для bundle, prepared, started, final и PublicationContext/StoredResult. Разветвление выполняется по сохранённому профилю и проверяемым format, не по небезопасному приведению типов. Старые входы без выбора профиля остаются допустимыми; все вызывающие места и фикстуры обновляются при необходимости сузить union. Не копировать поля старого объекта в Gemini и не удалять новые поля Gemini при записи.

Для Gemini saveInputs связывает snapshot с manifest.sourceDataDigest, проверяет validateCompactBundle и точный результат prepareGeminiAnalysis с замороженным пакетом; исходный contextDigest и requestDigest проверяются независимо. Legacy сохраняет свои validateAnalysisBundle/prepareAnalysis и dataDigest. После появления prepared его body и пакет неизменяемы. Сохранённые Gemini v1 читаются, новые операции используют установленный gemini-v2. Никакой автоматической замены format ответа.

validateStarted/validateAttempt получают отдельные ветки Gemini с теми же правилами идентичности, допуска и стоимости. Ветка final сохраняет responseReceived, firstContentMs, streamBytes и проверяет их согласованность с requestSent/status; valid требует validateGeminiAnalysis, точного format подготовленного пакета и соответствия content/responseDigest. Собственная цитата и game-only evidence проверяются существующим валидатором. Ошибка SSE/схемы остаётся технической, не превращается в insufficient-evidence. Legacy selected/insufficient-evidence сохраняются.

Артефакты остаются в существующей immutable artifacts-таблице и тех же логических refs; новый профиль задаёт проверку содержимого. Введение второй системы хранения текстовых отчётов или преобразование Gemini в legacy потребовало бы дополнительных правил и потеряло исходный формат, поэтому не применяется.

### 3. Один pipeline с двумя явными ветками подготовки/анализа

Оставить requestMatch, discovery, parse, lease, checkpoint и publication как общие пути. execute выбирает подготовку по job.analysisProfile, а не config.analysisProfile. Для Gemini вызываются prepareCompactMatchFacts и prepareGeminiAnalysis; analyze вызывает analyzeGeminiMatch с существующим beforeSend, который заново проверяет бюджет/владение и сохраняет started до POST. При frozen prepared обновлённый текущий промпт не меняет тело. Старый анализ продолжается своим путём.

Необходимые новые зависимости pipeline: geminiPrompt, heroMetricsDictionary и отдельный managementKey, все необязательные для прежнего вызова. Переданный выбор новых Gemini-задач требует совместимых материалов ещё при создании. Если у прежнего caller в БД обнаружилась старая Gemini-задача без нужных зависимостей, worker откладывает её с analysis-profile-unavailable без OpenDota/модели вместо подмены профиля. Operations нового релиза передаёт оба семейства материалов, поэтому умеет обрабатывать смешанную очередь и после переключения новых задач обратно на legacy.

prepare-only сохраняет compact/prepared без inference/management/публикации. Basic по-прежнему ждёт разобранного реплея с прежним deadline; ограничитель OpenDota и переиспользование parse job не меняются. Supported match, manual min 1 без явной стороны, auto min 2, анонимные ID, две подходящие стороны и победа/поражение остаются ответственностью прежнего классификатора. Обычный requestMatch возвращает существующий результат или awaiting-data без новой генерации независимо от текущего профиля. Новая модель не означает новый ключ дедупликации.

### 4. Постоянная сверка и максимум один потомок

Использовать существующий checkGeminiRecovery, не переносить его сетевую логику в Storage и не вызывать лабораторный runner из сервиса. Условия уже реализованного клиента: requestSent=true, status transport-error/timed-out, responseReceived=false, generationId/content отсутствуют, streamBytes=0, все usage неизвестны, есть полный final и совпадающая identity. Восстановление по одному started не доказывает эти условия.

Добавить таблицу gemini_recoveries с parent_attempt_id как PRIMARY KEY/FK, recovery_ref на immutable artifact, retry_attempt_id как nullable UNIQUE/FK. В записи решения сохраняется исходный GeminiRecovery: attemptId, requestDigest, проверки, статус, подтверждённая стоимость либо резерв. Storage валидирует связь с исходным prepared/final, допустимые коды/ID, порядок/полноту проверок, конечные суммы и отсутствие права нового потомка у уже повторённой попытки. Для retry-allowed нужны ровно три полные пустые проверки с интервалами существующего клиента 10/30/60 секунд и reserveUsd=положительной консервативной оценке первой попытки. Произвольная строка reason или ручной вызов generic reserveAnalysis не заменяют решение.

Предлагаемые узкие операции Storage: read/saveGeminiRecovery и reserveGeminiRetry. Имена уточняются стилем реализации, поведение закреплено спеками. save фиксирует final-решение и резерв идемпотентно; изменение уже сохранённого решения отклоняется. При recorded с подтверждённой ценой save также закрывает unresolved исходной попытки, сохраняя её immutable final, чтобы задачу можно было завершить failed без повтора; recorded без цены остаётся unresolved. reserve retry в одной транзакции проверяет Claim, исходный профиль/final/решение и отсутствие потомка, снимает блокировку только этой исходной попытки, создаёт prepared receipt потомка и связывает его ID. Точный preparedRef тот же, ID другой. Ошибка любой записи оставляет прежнее состояние и ноль новых POST. Исходные started/final не переписываются; аудируемое снятие блокировки отражено ссылкой решения, не маскируется под пользовательское resolveUncertain.

Generic reserveAnalysis у Gemini не создаёт новый корень после начатой/отправленной попытки той же ревизии: её единственный допустимый потомок проходит reserveGeminiRetry. Ранее завершённый preflight без started/requestSent не является отправкой и сохраняет прежний безопасный путь подготовки. Ни release, ни generic resolveUncertain не обнуляют ограничение цепочки. Для нового полного анализа после исчерпания цепочки требуется явная новая ревизия с прежними правами. Если бюджет до допуска потомка недостаточен, сохранённый unresolved требует внимания; одно изменение лимита само не снимает эту блокировку, продолжение требует явного решения оператора.

Pipeline сначала сохраняет Gemini final. У непригодного non-valid отправленного исхода с неизвестной оплатой сохраняется unresolved до отдельного решения. Без key/eligible финала задача получает needs-attention; известный расход невалидного ответа даёт failed. Valid с неизвестной оплатой остаётся пригодным к публикации по прежним правилам, но блокирует будущие генерации без покрытия. Найденная management-генерация запрещает повтор: известная цена учитывается отдельно, отсутствие текста не исправляется догадкой. При найденном ID без цены неизвестность остаётся непокрытой и требует внимания. Unavailable/aborted/ошибочная/усечённая/устаревшая сверка не разрешает потомка.

Наличие потомка навсегда закрывает второе автоматическое разрешение для этой цепочки, в том числе после его preflight-отказа: новый ID для «ещё одной попытки» не создаётся. До каждой фактической отправки потомка выполняется обычный свежий preflight и beforeSend с бюджетом; метка x-session-id соответствует именно новому ID. Старый unknown и резерв не теряются.

### 5. Учёт резервов без ложного списания

Расширить BillingSummary двумя агрегатами: reservedCostUsd и uncoveredUnknownCount; прежние knownCostUsd, unknownCount и unfinishedEstimatedCostUsd сохраняются. Они вычисляются по исходным attempts и проверенным recovery-решениям, без дополнительных API при чтении.

Для каждой попытки effective actual cost берётся из исходного known либо подтверждённой отдельной management-стоимости, учитывается один раз. unknownCount показывает число ещё не подтверждённых фактических цен; исходный final при найденной цене не переписывается. Резерв допустимого retry-allowed покрывает соответствующий unknown для бюджетного допуска, оставаясь резервом, а не knownCost. Recorded без доступной цены, interrupted started, неизвестные legacy и исход потомка без цены остаются uncovered. Положительный резерв recorded без цены не даёт разрешения обойти непокрытую неизвестность.

Бюджет перед генерацией: uncoveredUnknownCount должен быть 0, доступный остаток = maxTotalCostUsd − knownCostUsd − reservedCostUsd. Свежая оценка должна помещаться и в остаток, и в maxEstimatedCostPerAttemptUsd. Если найденная цена заменяет резерв, он больше не суммируется с этой ценой. У дочерней отправки сохраняются собственные known/unknown/оценка. При valid второго ответа первая неизвестная цена всё ещё видна оператору, даже если бюджет допускает дальнейшие задачи за вычетом резерва.

Это расширяет прежнее безусловное правило блокировки unknown только по согласованной узкой политике трёх пустых проверок и резерва; MODIFIED requirements описывают исключение явно. Generic resolveUncertain не создаёт допустимое покрытие и не обнуляет расход.

### 6. Restart, отмена и владение

checkGeminiRecovery выполняется внутри прежнего единственного worker под продлеваемым Claim; discovery loop может продолжать сохранять ID. Для fake Clock адаптировать только передаваемый wait к существующим часам/Signal. Не добавлять новую постоянно работающую job или concurrent AI worker.

| Точка сбоя | Допустимое продолжение |
|---|---|
| Только started, final отсутствует | needs-attention; нельзя синтезировать responseReceived=false или повторять inference |
| Eligible final сохранён, решение не завершено | локальное восстановление может вернуть задачу только к management-проверке; повторить безопасные чтения допустимо, прямой POST запрещён |
| Решение/резерв сохранены, потомка ещё нет | использовать то же решение, проверить бюджет и создать не более одного потомка |
| Потомок reserved, started отсутствует | после interrupted recovery не создавать другого потомка; завершить как неподтверждённую до отправки попытку без автоматического POST |
| Потомок started без final | attention, третьей отправки нет |
| Valid сохранён до checkpoint | принять valid и продолжить публикацию без повторной модели/сверки |
| Publication ID или unknown уже в журнале | прежнее завершение по ID либо attention, без нового create-message |

Локальный recoverInterrupted не делает сеть; исключение для полного eligible final переводит лишь на продолжение проверки. Сеть остаётся в pipeline. Отмена/lease-lost останавливает новые management-проверки/допуски, достоверные исходы уже допущенных попыток сохраняются без устаревшего продвижения задачи. Незавершённая сверка не становится тремя пустыми проверками из-за рестарта.

### 7. Discord отображает сохранённый профиль

Добавить явную Gemini-ветку renderer через presentGeminiAnalysis/validateGeminiAnalysis, не пропускать raw Gemini Markdown через legacy validator и не ослаблять validateEmbed. Показ: ник/герой выбранного слота, номинация, отдельные 3–4 факта, цитата только по собственному quote ID с временем/маркером сокращения, verdict, исход/ссылка/экспериментальность. Три teamFacts v2 — последние три поля с заголовком поражения или слабых мест после победы; у v1 их нет и они не сочиняются.

Использовать прежние cleanText/shorten, пределы полей/суммы embed и отметку сокращения. Для трёх teamFacts предусмотреть три отдельных ограниченных поля: объединение всех максимальных строк в одно поле может превысить 1024 и потерять пункт. Размер проверяется после экранирования, включая кавычки/emoji/упоминания/ссылки. Все обязательные части остаются видимыми; при невозможном payload нет допуска публикации. allowed_mentions, nonce, enforce_nonce, target и сохранение точного JSON до send не меняются.

Обычный /worst и /worst-status выбирают renderer по сохранённому valid, в том числе если новая ревизия другого профиля неуспешна. В статус добавить безопасные причины сверки и разные формулировки known/reserved/unknown, не объявлять резерв оплатой или найденный generation ID готовым отчётом. Чтение не вызывает management, модель, поиск профиля либо публикацию. Права Administrator для reanalysis и scope guild/channel неизменны.

### 8. Сборка Operations и материалы артефакта

Config v1 принимает только известный analysisProfile; отсутствие — legacy. ServiceInput нового release содержит legacy prompt, gemini-v2 prompt, основной dictionary и hero-metrics-v1.json, чтобы обрабатывать смешанную очередь независимо от текущего выбора новых задач. Для исторических prepared v1 используется пакет внутри prepared. Не добавлять произвольные пути инструкций/моделей в service.json.

Добавить узкую публичную проверку двух словарей в match-facts с теми же pinned digest-проверками, что использует подготовка; Operations использует её в offline check без создания фиктивного матча. Это переиспользование существующего входного контракта, не смена словарей или правил расчёта. Валидация prompt/материалов/ключей выполняется до start/Gateway/активации, импорт остаётся инертным.

ServiceSecrets получает openRouterManagementKey; только CLI читает OPENROUTER_MANAGEMENT_KEY. Inference key остаётся OPENROUTER_API_KEY. Совпадающие непустые ключи отклоняются, management не подставляется вместо inference и не передаётся его транспорту. Без management обычный Gemini допустим, recovery выключен. Никаких переносов ключей между Windows/User env/VPS/GitHub этим изменением.

Health/ServiceStatus добавить reservedCostUsd/uncoveredUnknownCount как необязательные для чтения прежних v1-файлов, обязательные при записи нового runtime. Старые status без полей проходят прежнюю проверку; отсутствие поля не доказывает отсутствие скрытого резерва и не используется для допуска модели. Budget всегда читает SQLite, не health. JSONL выводит безопасные коды/ID и агрегаты, без prepared/content/response/raw exception.

В deploy/package.mjs явно добавить только evaluation/dictionaries/hero-metrics-v1.json к прежней allowlist. Prompt-каталог уже включается целиком; экспериментальные отчёты/локальные JSON/ключи туда не добавляются. Распакованный production install проходит offline check с новым примером без БД/сети. Пример: analysisProfile=gemini, automatic=false, mode=prepare-only, allowExperimental=false; выбранный ранее Steam сам не включается. Установленный config не переписывается.

## Risks / Trade-offs

- [Analytics запаздывает без подтверждённого максимума] → три пустые проверки не доказывают отсутствие списания; максимум один потомок, положительный резерв и явная неизвестность сохраняются. Это известная граница существующего recovery, не новая гарантия API.
- [Оценка не является пределом реального счёта] → до каждой отправки свежие тарифы и бюджет с резервом; сведения known/reserved/unknown раздельны.
- [Crash после допуска, но до фактической отправки] → сохраним attention вместо догадки об отсутствии эффекта; автоматическое завершение каждого такого случая не обещается.
- [Рост типов через четыре модуля] → явные различимые варианты и проверки публичных границ, общие шаги очереди/публикации не дублируются.
- [Старые queued-задачи сменят модель] → profile сохраняется до подготовки, migration default legacy и прежние revision digests неизменны.
- [Текст после экранирования не помещается] → отдельные bounded fields, validateEmbed после очистки и отметка сокращения; обязательные три пункта сохраняются.
- [Некомплектный release] → тест артефакта и offline-проверка обоих словарей до запуска.
- [Изменился формат БД] → следующая атомарная миграция, тесты схем 1/2/3 и cold backup старым релизом; откат кода не считается откатом данных.
- [Корректная схема не доказывает качество юмора] → существующие игровые требования/подача не меняются, калибровка и новые live-прогоны не объявляются выполненными.

## Migration Plan

1. Реализовать контракты/валидацию и одну следующую миграцию на актуальном базисе (сейчас 2→3); литералы схем 1/2 и их checksums не менять. Проверить fresh, upgrade 1→3 через прежнюю миграцию, 2→3, rollback DDL/commit, чужую/новую схему, старые результаты и discovery-кандидатов.
2. Проверить настоящую временную SQLite с поддельными OpenDota, Gemini SSE, management и Discord, в том числе смешанные ревизии, паузы, crash/reopen, reserve/child cap и известную/неизвестную публикацию. Сохранить прежние regression/golden-проверки legacy; реальные API-ключи не нужны.
3. Выполнить typecheck, полный набор и strict OpenSpec. Windows/Linux различать фактически; наличие service.yml не выдавать за успешный CI текущей ревизии. Проверить артефакт с production dependencies и без рабочих данных. Перед будущим archive отдельно синхронизировать baseline specs — main specs сейчас отсутствуют.
4. До будущей доставки остановить старый сервис, сделать существующим старым релизом cold backup БД и operations-state.json с прежним совместимым конфигом. До backup не открывать рабочую БД новым кодом, включая команду backup нового release. Offline check БД не открывает.
5. Первую настройку нового release оставить manual/prepare-only. Включение live, точный бюджет, перенос management key и реальный ручной smoke выполняются отдельно; после него отдельно решается автоматический Gemini. На production проверять доставку только status/revision/unit/checksums.
6. При несовместимом откате сохранить текущую БД отдельно и восстановить согласованную старую пару из backup, предварительно сверив последующие расходы/публикации. Автоматического удаления, downgrade или восстановления БД deploy-скриптом нет.

Эта спека не меняет код, схему, рабочие конфиги или секреты. Все описанные новые функции/статусы и проверки остаются задачами реализации.
