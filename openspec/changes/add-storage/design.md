# Design

## Context

Мотивация — [proposal.md](proposal.md), поведение — [spec.md](specs/storage/spec.md). Контракт реализован в `src/storage/`; фактические проверки и оставшиеся runtime-ограничения находятся в [VERIFICATION.md](../../../src/storage/VERIFICATION.md).

Проверено по исходникам на 17 октября 2026:

- Проект использует ESM, строгий TypeScript/NodeNext, Node.js >=22.14.0, Ajv и node:test. Хранилища, общего bootstrap, pipeline и Discord-модуля пока нет.
- `group-settings` возвращает неизменяемый `GroupSettings` из локального JSON. Публичного валидатора отдельного объекта нет; storage проверяет свой снимок на входе, не меняя API соседнего модуля.
- OpenDota возвращает `MatchSnapshot`, строковый job ID и безопасный `OpenDotaErrorSummary` с `requestMayHaveSucceeded`. Его кеш и объединение POST действуют только в памяти процесса.
- `match-analysis` экспортирует `validateAnalysisBundle`, `prepareAnalysis`, `validateMatchAnalysis`. `analyzeMatch` ожидает Promise от `beforeSend(StartedAttempt)` до единственного POST и возвращает `AnalysisAttempt`. Подготовленный объект содержит точное тело запроса, пакет инструкции и полную идентичность.
- У `AnalysisAttempt` нет статуса interrupted; при preflight-failed идентичность и attempt ID могут быть null. Состояния оплаты: not-sent, known, unknown. Эти типы storage не расширяет.
- Первичная проба в памяти подтвердила `DatabaseSync` на Node.js 22.14.0 и SQLite 3.47.2. При реализации проверены файловая БД, миграции и аварийное завершение на Windows; Linux пока не проверен.

Пилот [MiMo](../../../evaluation/PILOT_2026-10-17.md) закончился оплаченной попыткой без итогового ответа. Он подтверждает необходимость сохранять расходы ошибок отдельно от допустимых результатов. Перенос лабораторных файлов в новую БД и новые сетевые эксперименты в это изменение не входят.

## Goals / Non-Goals

**Goals:**

- Короткие атомарные операции над одним локальным файлом, без транзакций через сетевое ожидание.
- Разделить состояние задачи, неизменяемые артефакты и фактические исходы внешних попыток: потеря владения не должна терять поздний ответ.
- Дать будущему pipeline достаточный контракт для восстановления, не задавая его фильтры, бюджет и расписание.

**Non-Goals:**

- Общая библиотека очередей, ORM, распределённые обработчики, произвольные SQL-запросы из вызывающего кода.
- Гарантия ровно одного внешнего эффекта: локальная транзакция не может атомарно подтвердить удалённый POST.
- Редактирование текущих настроек, автоматическое удаление истории, сжатие, резервирование или сервис сверки расходов.

## Decisions

### 1. Встроенный SQLite и короткие синхронные операции

Использовать `node:sqlite` / `DatabaseSync`, одну точку экспорта `src/storage/index.ts`, типы и небольшие внутренние файлы по сложившемуся стилю. Публичные операции синхронные: `beforeSend: async started => storage.startAnalysis(claim, reservationId, started)` превращает подтверждённую локальную запись в ожидаемый аналитиком Promise. Сетевых вызовов и таймеров внутри storage нет. Транзакция никогда не переживает `await`.

В [документации Node.js 22.14](https://nodejs.org/download/release/v22.14.0/docs/api/sqlite.html) API помечен experimental. Предложение не требует установки нативного npm-пакета, но совместимость проверяется на минимальной версии проекта; обновление Node не считается автоматически проверенным. `better-sqlite3` добавил бы внешнюю нативную сборку, ORM — лишний слой; для одного сервиса они пока не нужны.

Выбрать `journal_mode=DELETE`, `synchronous=FULL`, `foreign_keys=ON`, `busy_timeout=1000` мс, проверять фактически применённые значения при открытии. WAL не нужен при небольшом числе коротких записей одного сервиса. Дополнительно [SQLite описывает WAL-reset bug](https://sqlite.org/wal.html), затрагивающий в том числе 3.47.2 при конкурирующих соединениях в WAL; выбранный rollback journal не использует этот режим. Возвращение к WAL потребует отдельной проверки версии SQLite и нагрузки.

Для изменений использовать параметризованные statements и `BEGIN IMMEDIATE`; откат обязателен при ошибке. SQLite допускает [одного одновременного писателя](https://sqlite.org/lang_transaction.html); busy после ограниченного ожидания возвращается вызывающему без внутреннего цикла повторов. Парсинг, хеширование и проверки артефактов делать до короткой транзакции, затем внутри перепроверять версию/владение и ссылки.

### 2. Открытие, формат файла и ошибки

`openStorage({ path, clock? })` принимает непустой файловый путь; относительный путь разрешается один раз. `:memory:`, URI и отсутствующий родительский каталог отклоняются. Путь передаёт bootstrap; рекомендуемое размещение `.local/app.sqlite`, без чтения env и создания каталогов при импорте. `clock.now()` возвращает безопасное неотрицательное Unix-время в миллисекундах; по умолчанию Date.now. Время новых записей создаёт storage, временные метки исходных DTO сохраняются без преобразования.

Новый пустой файл получает `application_id=0x44575046`, `user_version=1` и журнал миграций с номером и SHA-256 текста миграции. До настройки режима существующего файла проверить его принадлежность/версию; чужой непустой файл отклонить. Пустую принадлежащую проекту БД и будущие известные версии обновлять транзакционно; неизвестную более новую версию или несовпадение контрольной суммы отклонять. Для существующей своей БД проверять `quick_check` и внешние ключи. Автоматического пересоздания, удаления или понижения версии нет.

`StorageError` содержит `code`, `operation` и необязательные jobId/attemptId; сообщения стабильные. Коды: invalid-input, too-large, incompatible-schema, integrity-error, not-found, conflict, lease-lost, attempt-already-started, busy, io-error, closed. Не экспортировать исходную SQL-ошибку, SQL, параметры, абсолютный путь и payload в message/cause/toJSON. `close()` повторяем, операции после закрытия возвращают closed.

Если подтверждение COMMIT не получено, вызывающий не отправляет внешний запрос. После переоткрытия он читает журнал; повтор одноразового допуска никогда не используется для выяснения, был ли первый допуск успешным.

### 3. Минимальная модель данных

Все связанные сущности находятся в одной БД; JSON-sidecar-файлов нет. Идентификаторы задач/попыток — UUID, match ID — положительный safe integer, сторона — radiant/dire. Discord snowflakes остаются десятичными строками диапазона uint64; номера ревизий, версии и времена — безопасные целые.

| Сущность | Содержимое и ограничения |
|---|---|
| matches | match ID, firstSeenAt, lastSeenAt; повтор обновляет min/max времён |
| jobs | ID, match ID, side, revision, origin manual/automatic, снимок GroupSettings и его digest, state, step, version, nextRunAt, leaseToken/leaseUntil, ссылки на контрольную точку и результат |
| revision_requests | уникальный request ID, digest исходного запроса, созданный job ID; не удаляется после завершения задачи |
| artifacts | kind, digest, байты UTF-8 и версия конверта; уникальность kind+digest, проверка байтов при совпадении |
| Ссылки артефактов в jobs | snapshot_ref/bundle_ref/prepared_ref; отдельная таблица не требуется для трёх фиксированных видов; замена входа запрещена после подготовки анализа |
| external_attempts | ID, job ID, kind parse/analysis/publication, digest входа, локальное состояние prepared/started/finished/interrupted, исходные DTO и их digests, время; незавершённый started/interrupted блокирует новый допуск своего вида |
| resolutions | ID, attempt ID, время, ограниченная причина, решение allow-new-attempt либо accept-outcome, ссылки на подтверждение; исходная попытка не переписывается |

Поля контроля, уникальности и запросов хранить отдельными колонками; непрозрачные снимки — JSON/TEXT. Constraints и внешние ключи дублируют важные проверки кода. Уникальны `(matchId, side, revision)` и незавершённая задача для `(matchId, side)`; unfinished включает needs-attention. Частичные индексы и условные UPDATE защищают от двух соединений, а не только JS-проверки до записи.

Снимок настроек содержит только steamAccountIds/guildId/channelId. Проверки совпадают с текущим контрактом: непустой уникальный список Steam32 1..4294967294 и десятичные snowflakes без ведущих нулей 1..18446744073709551615. Снимок не перечитывается из файла при восстановлении. Отдельной таблицы редактируемых настроек нет.

Альтернатива «только готовый результат и статус done» не позволяет объяснить потерянную отправку; хранение произвольного объекта настроек могло бы сохранить секреты и разойтись с JSON-источником.

### 4. Постановка, ревизии и владение

`enqueueInitial` в одной транзакции создаёт запись матча при необходимости и ревизию 1 либо возвращает существующую ревизию 1. Новая задача получает queued, step=load-match, nextRunAt=createdAt=now, version=1. Проверенный новый ввод не заменяет её даже после завершения или создания более поздних ревизий. `getLatestJob` отдельно возвращает максимальную ревизию. Исходный origin — информация об инициаторе, не отдельный ключ дедупликации.

`createRevision` требует requestId и снимок настроек: сначала ищет ключ, сравнивает digest входа, затем проверяет наличие первой ревизии, отсутствие unfinished и назначает max(revision)+1. Без первой ревизии — not-found. Одинаковый ключ с тем же входом всегда возвращает тот же job, в том числе уже завершённый; с другим входом — conflict. Новый пакет фактов/инструкция после начала анализа требует новой ревизии. Повтор внешней попытки в той же ревизии использует уже закреплённый запрос.

Состояния и переходы:

| Из | В | Условие |
|---|---|---|
| queued / waiting | running | claimNext: nextRunAt <= now, выдача нового токена и leaseUntil=now+60000 |
| running | running | renewClaim или checkpoint с актуальным токеном, version и неистёкшим сроком |
| running | waiting | defer с nextRunAt, освобождение владения |
| running | needs-attention | неразрешённый исход внешнего действия |
| running | succeeded / failed | finish с проверенным результатом для succeeded либо безопасной причиной для failed; нет неразрешённого внешнего действия |
| needs-attention | waiting / failed | явное решение с аудитом; повтор не подразумевается самим переходом |

`step`: load-match, wait-parse, build-facts, analyze, publish. Это сохранённая точка продолжения для будущего pipeline; storage не исполняет её и не определяет, требуется ли разбор/публикация. Локальная контрольная точка хранит только ссылки и безопасную причину ожидания, без произвольного пользовательского payload.

При добровольных defer/finish не должно оставаться prepared-reservation активного вызова: сначала сохранить его исход. Операция с такой резервацией возвращает conflict, предотвращая потерю возможности завершить вызов после передачи владения. Аварийный prepared закрывается recoverInterrupted согласно разделу 7.

`claimNext` выбирает nextRunAt/createdAt/ID в стабильном порядке, выдаёт максимум одну задачу. `Claim` включает jobId, token и version; мутирующая операция возвращает обновлённую version. renew может продлить срок только до его истечения. Будущий обработчик должен обновлять владение во время долгого анализа; таймер не реализуется здесь. Не выдавать второй допуск внешнего действия при наличии unresolved-попытки даже после смены токена.

### 5. Артефакты и проверка существующих контрактов

У записи артефакта есть envelope version=1, kind и SHA-256 точных сохранённых байтов. Хеш конверта не подменяет digests соседних модулей. Для JSON допускаются только конечные числа, обычные объекты, массивы и JSON-значения, без циклов/undefined/functions. Сохранять DTO через JSON.stringify без сортировки ключей: после чтения FactsBundle должен давать ту же строку context внутри prepareAnalysis. Строковые файлы инструкции, content и `PreparedAnalysis.body` сохранять побайтно. Каноническую сериализацию использовать только для проверки digests соседних модулей и сравнения повторных команд/исходов; она не должна менять сохранённые артефакты.

Лимит одного артефакта — 32 MiB UTF-8; причины и диагностические ссылки — до 1000 символов. Существующие меньшие лимиты brief/request и ограничения output продолжают действовать. Размер проверяется до записи, ошибка не включает данные. Лимит — предложенный предел v1, а не измеренный максимум ответов OpenDota.

- Снимок: исходный `MatchSnapshot`; проверить структуру, data.match_id и parseState, сохранить retrievedAt. При связывании фактов сверить manifest.dataDigest с каноническим digest snapshot.data.
- FactsBundle: переиспользовать публичный `validateAnalysisBundle` для структуры, хешей и ссылок. Storage не пересчитывает показатели и не вызывает `verifyFactsBundle`, требующий исходные словари/опции подготовки.
- PreparedAnalysis: вызвать публичный `prepareAnalysis(bundle, prepared.prompt)` и сравнить все поля со входом, включая точное body. Это локальная проверка при записи, а не замена сохранённого запроса при чтении. Внутренние функции соседнего модуля не импортировать.
- Valid-результат: `validateMatchAnalysis(analysis, bundle)`, полное равенство AnalysisIdentity сохранённому запросу, digest content при наличии. Формат valid не означает подтверждённого пользователем качества; experimental/candidate и сведения калибровки сохраняются буквально.

При чтении проверять envelope digest и идентичности ссылок; возвращать сохранённые DTO, не готовить их заново текущей версией преобразования. Несовпадение — integrity-error. Поэтому обновление преобразователя не меняет старый результат незаметно.

### 6. Намерение, одноразовая отправка и исход

Одноразовый допуск отличается от повторяемого сохранения. Подготовка/reserve сама не разрешает сеть. Переход prepared → started коммитится с проверкой Claim; второй start по тому же ID возвращает attempt-already-started, даже если содержимое совпало. Новый ID не обходит unresolved-попытку того же вида. Только успешный первый возврат допускает один внешний вызов вызывающим кодом.

Запись исхода известной попытки допускает повтор с тем же каноническим DTO и digest, а противоречивый исход возвращает conflict. Для уже started-попытки её достоверный поздний исход сохраняется без действующего Claim: идентичность и связь с подготовленным входом всё равно проверяются. Это обновляет журнал, но не состояние/контрольную точку задачи. Новый владелец отдельно принимает исход в checkpoint. Старый процесс не может продвинуть задачу своим просроченным токеном.

| Вид | До отправки | Сохраняемый исход | Неопределённость |
|---|---|---|---|
| parse | match ID и digest намерения | job ID или OpenDotaErrorSummary | started без ответа либо requestMayHaveSucceeded=true без известного job ID |
| analysis | reservation с PreparedAnalysis; StartedAttempt в beforeSend | исходный AnalysisAttempt целиком | started без ответа; либо requestSent=true и billingState=unknown для стоимости |
| publication | допустимый результат, исходные guild/channel, точное подготовленное сообщение и digest | строковый message ID либо безопасный исход not-sent/unknown с кодом | started без ответа или unknown |

У parse отсутствие job на чтении не доказывает готовность; pipeline использует свежий MatchSnapshot согласно клиентскому контракту. Хранилище не делает такой вывод само.

Analysis reservation выдаёт локальный ID до одного вызова аналитика. Повторный вызов analyzeMatch требует новой reservation и нового attemptId. В `startAnalysis` проверяются все поля StartedAttempt, attemptId, цены и оценка. В `saveAnalysisOutcome` принимается final только с совпадающими identity/attemptId. Исключение — отказ до допуска: null-поля сохраняются как null, связь остаётся через reservation.

Если started уже сохранён, финальный requestSent=false не закрывает его автоматически: saveAnalysisOutcome возвращает conflict, оставляя допуск и неизвестность неизменными. Такой исход может возникнуть после отмены между callback и POST, но также после ошибочного повторного вызова аналитика, которому отказано в допуске. Принимать его как доказательство отсутствия первого POST нельзя. Явное accept-outcome принимает такой DTO отдельным параметром notSentOutcome с аудитом; до этого попытка требует внимания. Sent-исход и такое явное решение взаимно исключают друг друга; противоречащий поздний DTO возвращает conflict без перезаписи принятого исхода и без автоматического продвижения задачи.

Sent-исход без started отклоняется. Нельзя прикрепить чужой ответ, повысить calibration или сделать valid без analysis. Даже invalid-output/ошибка сохраняются вместе с usage. Известный parse job ID запрещает новый beginParse, а valid-анализ — новую reservation этой ревизии; новые версии входа требуют новой ревизии. Журнал готовой valid-попытки и указатель job.result различаются: `checkpoint` атомарно публикует ссылку на проверенную попытку только своей задачи с действующим Claim, finish проверяет её наличие. До этого она доступна как запись попытки, но не как принятый результат задачи.

Для publication хранится только строгий JSON-конверт версии 1 с guildId, channelId, analysisAttemptId и `message` как точная JSON-строка. Storage проверяет JSON-объект и размер, идентичность/цель/допустимый результат; структуру Discord payload и отключение mentions должен определить будущий Discord-модуль. Это не новая спека оформления embed. После известного message ID другая публикация этой ревизии запрещена. Изменение опубликованного сообщения и повторная публикация требуют отдельного будущего решения; v1 их не предполагает.

### 7. Восстановление и явные решения

`recoverInterrupted()` — явная локальная операция, не действие при импорте или каждом открытии. Она проверяет только running с leaseUntil <= now, снимает токен и повышает version:

- Нет неизвестного внешнего эффекта: waiting с прежним step и nextRunAt=now. Незавершённые prepared-reservation закрываются локальной отметкой отсутствия допуска без выдуманного AnalysisAttempt; новый вызов требует нового attemptId. Известный job ID, сохранённый исход анализа или message ID доступны для продолжения; ничего не переотправляется.
- Остался started без исхода: локальная receipt помечается interrupted, задача — needs-attention; исходные StartedAttempt/идентичность остаются неизменными. Такой анализ попадает в неизвестные расходы.
- Уже сохранён неизвестный исход parse/publication: needs-attention. Valid-анализ с неизвестной оплатой остаётся допустимым результатом; вопрос дальнейших расходов решает pipeline по сводке.
- Действующее владение не затрагивается. Одновременные восстановления используют условное обновление, без повторных событий.

`resolveUncertain` принимает attempt ID, reason, evidenceRef, решение и целевое состояние waiting/failed. accept-outcome ссылается на отдельно сохранённый подтверждённый исход либо принимает notSentOutcome для описанного исключения; allow-new-attempt разрешает новый ID, сохраняя риск повторного эффекта и неизвестный расход старого. Решение не генерирует сеть и само по себе не закрывает стоимость нулём. Повтор resolution ID с теми же данными идемпотентен, с другими — conflict. Смена needs-attention → waiting/failed выполняется вместе с решением и проверкой ожидаемой version, без обхода другого неразрешённого действия.

Поздний ответ после разрешения новой попытки дописывается в старую историю; автоматически назначать его текущим результатом, менять принятое решение или уже сохранённый message ID нельзя. Если выявились два внешних эффекта, вызывающий получает обе записи для явного разбора.

### 8. Стоимость и чтение результатов

Хранить исходные usage/rates/estimatedCostUsd/billingState из DTO. Проверять конечность, неотрицательность и согласованность not-sent/requestSent; не округлять стоимость при записи. known допускает costUsd=0, unknown требует costUsd=null, not-sent не создаёт фактический расход. Сохранённые started/interrupted без финала дают неизвестную стоимость; prepared без started денег не резервирует.

`getBillingSummary` по всем попыткам либо заданной задаче возвращает `knownCostUsd`, `unknownCount`, `unfinishedEstimatedCostUsd` отдельно. Законченную invalid-output с известной ценой считать так же, как valid. Не складывать оценку с известной ценой как «фактические расходы», не выдавать эту сводку за гарантию соблюдения бюджета. Пересчёт исторической оплаты по новым тарифам и автоматический GET generation metadata не входят в v1; неизвестность может сохраняться до отдельной функции сверки.

`getLatestResult(matchId, side)` выбирает принятую valid-попытку максимальной ревизии, возвращая job/revision, исходные AnalysisIdentity/AnalysisAttempt, настройки и известные ссылки публикации. insufficient-evidence возвращается буквально. Если результата нет — null. `getLatestJob` и `getJob` показывают в том числе ошибочную новую ревизию; `listAttempts(jobId)` возвращает историю с локальными receipt/resolution, не смешивая их с DTO аналитика. Эти запросы не изменяют состояние.

### 9. Публичные операции и стыки

Ниже целевой минимальный API; подробные TypeScript-типы создаются при реализации на основе этой модели. Все операции синхронные, без raw SQL или произвольного callback внутри транзакции.

| Группа | Операции и возвращаемые данные |
|---|---|
| Файл | openStorage({path, clock?}) → Storage; close() → void |
| Обнаружение | recordMatch({matchId, observedAt}) → MatchRecord |
| Постановка | enqueueInitial({matchId, side, origin, settings}) → Job; createRevision({requestId, matchId, side, settings}) → Job |
| Выполнение | claimNext() → {job, claim} или null; renewClaim(claim) → Claim; checkpoint(claim, {step, artifactRefs?, resultAttemptId?}) → {job, claim}; defer(claim, {nextRunAt, reason}) → Job; finish(claim, {state: succeeded/failed/needs-attention, reason?}) → Job |
| Входы | saveInputs(claim, {snapshot?, bundle?, prepared?}) → {refs, claim}; снимки по ссылкам доступны через getJobArtifacts(jobId) |
| Анализ | reserveAnalysis(claim, {attemptId, preparedRef}) → reservation; startAnalysis(claim, reservationId, StartedAttempt) → void; saveAnalysisOutcome(reservationId, AnalysisAttempt) → Receipt |
| Разбор | beginParse(claim, {attemptId}) → Receipt; saveParseOutcome(attemptId, {jobId} либо {error}) → Receipt |
| Discord | beginPublication(claim, {attemptId, analysisAttemptId, message}) → Receipt; savePublicationOutcome(attemptId, {messageId} либо {state, code}) → Receipt |
| Восстановление | recoverInterrupted() → количества resumed/attention; resolveUncertain({resolutionId, jobId, expectedVersion, attemptId, decision, state, reason, evidenceRef, notSentOutcome?}) → Job |
| Чтение | getJob(id), getLatestJob(matchId, side), getLatestResult(matchId, side), listAttempts(jobId), getBillingSummary({jobId?}) |

saveInputs атомарно сохраняет переданные артефакты и checkpoint refs, возвращает обновлённый Claim; подготовка допускает ссылки на ранее сохранённый snapshot/bundle. reserve/start и запись исходов меняют журнал, но не version задачи; действительность Claim проверяется внутри начала/резервирования. checkpoint, saveInputs, renew и переход состояния меняют version. beginParse/beginPublication сразу атомарно создают started и выдают единственный допуск; отдельной резервации им не требуется.

Изменение выполняет только storage и его тесты/инструкцию. Интеграцию callback аналитика показать локальным примером с поддельным транспортом; `analyzeMatch`, клиент OpenDota и JSON-loader менять не нужно. Структура будущих команд и правила автоматического возобновления будут уточняться в своих изменениях на базе этих минимальных стыков.

### 10. Конфиденциальность и локальные данные

Публичный API принимает перечисленные DTO, а не `AnalyzeDependencies`, HTTP request/response или произвольный объект конфигурации. Авторизация, env, сырые provider metadata и отдельный reasoning не сохраняются. Текстовое content, снимки и точные запросы остаются локальными приватными данными; storage не может обнаружить любой секрет, вручную помещённый в произвольную строку. Вызывающий обязан не передавать такие строки.

Существующее `.local/` в `.gitignore` покрывает БД и её rollback-журнал при рекомендованном размещении. Пользовательский путь вне `.local/` должен находиться вне репозитория. Никаких реальных снимков/ключей в фикстурах; тесты используют синтетические данные и временные каталоги. Удаления и retention API в v1 нет.

## Risks / Trade-offs

- [Экспериментальный node:sqlite] → Проверить минимальный Node 22.14 и текущую среду, зафиксировать версии в VERIFICATION; другой драйвер согласовать отдельно при реальной несовместимости.
- [Синхронные операции блокируют event loop] → Ограничить размер, проверять вне транзакции, не держать транзакцию во время сети; для одного небольшого сервиса не вводить worker заранее.
- [Локальная БД не знает исход удалённой отправки] → Started до сети, неизвестный исход и явное решение; не обещать exactly-once для OpenDota/OpenRouter/Discord.
- [Lease истекает, пока старый процесс ещё ждёт HTTP] → Долговечная попытка блокирует новый допуск, токен защищает состояние; поздний ответ можно сохранить. Решение allow-new-attempt осознанно сохраняет риск дубля.
- [Часы ОС изменились] → Один источник времени на сервис; отклонять некорректные значения, не восстанавливать действующее владение. Резкий скачок может задержать или ускорить lease, но не обходит журнал допусков.
- [Диск/файловая система не обеспечивают обещанную durability] → FULL, локальный диск, реальные fault/reopen тесты; не использовать сетевой общий файл. Автоматическое резервирование остаётся operations.
- [Хранение полных артефактов увеличивает БД] → Предел на артефакт, дедупликация и приватное локальное размещение; измерения размера и retention можно добавить после появления реальной нагрузки.
- [Pipeline и Discord ещё не спроектированы] → API обозначен предложением; при существенном изменении стыков обновить документы до интеграции, не расширять их реализацию здесь.

## Migration Plan

1. Реализовать модуль отдельно от bootstrap: первая запись схемы v1 только при явном openStorage в созданном вызывающим каталоге.
2. Проверить на временных файловых БД создание, повторное открытие, изменение версии, отказ миграции и отсутствие очистки при ошибках. Лабораторные `.local/`-артефакты не импортировать.
3. Проверить параллельные соединения и завершение дочернего процесса вокруг фиксации допуска/исхода, с поддельными внешними действиями. Не выполнять оплаченные или Discord-запросы.
4. Выполнить typecheck/test, строгую проверку OpenSpec; записать фактические Windows/Node/SQLite результаты и отдельно Linux, если среда доступна. Готовность документов не означает выполнение этих проверок.
5. Подключать модуль отдельным изменением pipeline. Для будущего обновления схемы остановить приложение и сохранить согласованную копию БД; автоматический бэкап здесь не создаётся. Откат — совместимый код либо восстановленная копия при остановленном сервисе, без downgrade SQL и удаления нового файла.
