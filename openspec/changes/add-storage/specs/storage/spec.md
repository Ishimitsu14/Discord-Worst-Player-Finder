# Spec Delta

## Purpose

Хранилище сохраняет задачи обработки матчей, исходные артефакты, результаты и историю внешних действий между запусками приложения. Оно предоставляет постоянную дедупликацию и сведения для продолжения работы без автоматического повторения действий с неизвестным исходом.

## ADDED Requirements

### Requirement: Явное открытие постоянного хранилища

Хранилище SHALL открываться по явно переданному локальному пути, сохранять подтверждённые изменения между открытиями и закрываться явно. Импорт модуля MUST NOT открывать файлы, читать окружение или запускать сеть и фоновые обработчики.

#### Scenario: Повторное открытие
- **WHEN** приложение сохраняет задачу, получает подтверждение, закрывает и снова открывает тот же файл
- **THEN** доступны та же задача, её состояние и связанные записи

#### Scenario: Непригодный путь
- **WHEN** передан пустой путь, временное хранилище в памяти или отсутствующий родительский каталог
- **THEN** открытие завершается типизированной ошибкой без создания другого хранилища

### Requirement: Совместимость и атомарное обновление формата

Хранилище MUST проверять принадлежность и версию существующих данных, применять поддерживаемые обновления атомарно и отклонять чужой, повреждённый или более новый формат. Ошибка открытия MUST NOT приводить к удалению, очистке или подмене файла новой пустой базой.

#### Scenario: Неподдерживаемая версия
- **WHEN** файл использует версию формата новее поддерживаемой
- **THEN** приложение получает ошибку несовместимости, а данные не изменяются

#### Scenario: Ошибка обновления
- **WHEN** один из шагов обновления формата завершается ошибкой
- **THEN** частичные изменения этого обновления не становятся подтверждённым состоянием

### Requirement: Сохранение обнаруженных матчей

Хранилище SHALL принимать проверенный положительный безопасный целочисленный match ID, сохранять время первого и последнего обнаружения и повторно использовать запись того же матча. Оно MUST NOT самостоятельно определять режим, сторону компании или пригодность матча для анализа.

#### Scenario: Повторное обнаружение
- **WHEN** один матч обнаружен несколько раз, в том числе через разные аккаунты
- **THEN** остаётся одна запись матча, первое обнаружение сохраняется, последнее не уменьшается

### Requirement: Дедупликация первого запуска

Первый ручной и автоматический запуск SHALL иметь общую идентичность по match ID и стороне. Повторная постановка MUST возвращать существующую первую ревизию без замены её контекста, цели публикации, состояния или результата, включая завершённые задачи.

#### Scenario: Ручной запуск после автоматического
- **WHEN** для уже поставленной пары match ID и стороны поступает ручной запрос с другими текущими настройками
- **THEN** возвращается первоначальная задача и её сохранённый контекст

#### Scenario: Другая сторона
- **WHEN** запрошен тот же матч для противоположной стороны
- **THEN** эта пара имеет отдельную первую ревизию

### Requirement: Явные ревизии повторного анализа

Новая ревизия SHALL создаваться только по явному запросу с ключом идемпотентности и при отсутствии незавершённой ревизии этой пары. Повтор того же ключа и входа MUST возвращать прежнюю ревизию; другой вход с тем же ключом MUST отклоняться. История прежних ревизий сохраняется.

#### Scenario: Повтор команды создания ревизии
- **WHEN** подтверждение создания потеряно и вызывающий повторяет тот же запрос
- **THEN** возвращается уже созданная ревизия без увеличения её номера

#### Scenario: Конкурирующий повторный анализ
- **WHEN** две разные команды пытаются создать следующую ревизию, пока одна из них уже незавершена
- **THEN** создаётся только одна ревизия, вторая команда получает конфликт

### Requirement: Неизменяемый контекст задачи

Задача SHALL сохранять снимок проверенных настроек компании, сторону и цель публикации. Последующее изменение JSON-настроек MUST NOT менять этот снимок. Снимок задачи MUST NOT становиться вторым редактируемым источником рабочих настроек.

#### Scenario: Смена канала в настройках
- **WHEN** настройки изменены после постановки задачи
- **THEN** сохранённая задача сохраняет исходный канал; новый контекст применяется только к новой задаче или ревизии

### Requirement: Воспроизводимые артефакты

Хранилище SHALL сохранять неизменяемые снимки матча, пакет фактов и подготовленный запрос с инструкцией, версиями и digests. Привязка артефакта MUST проверять match ID, сторону и целостность. Разные байты под одной идентичностью MUST отклоняться; исходные данные MUST NOT пересчитываться при чтении.

#### Scenario: Повторное чтение запроса
- **WHEN** после перезапуска запрошен сохранённый подготовленный анализ
- **THEN** возвращаются исходное тело запроса, пакет инструкции и их идентичности

#### Scenario: Несовместимый пакет фактов
- **WHEN** к задаче привязывают пакет другой стороны или с неверным digest
- **THEN** запись отклоняется целиком, прежние артефакты остаются доступны

### Requirement: Атомарные контрольные точки

Изменение состояния задачи, привязки артефактов и указателя на результат SHALL подтверждаться атомарно относительно соответствующей контрольной точки. Изменение MUST проверять ожидаемую версию задачи; конфликт MUST NOT затирать более новое состояние.

#### Scenario: Сбой сохранения результата
- **WHEN** сохранение результата и его привязки прерывается до подтверждения
- **THEN** читатель видит либо прежнюю контрольную точку, либо целиком новую, без частичной привязки

### Requirement: Ограниченное владение задачей

Получение готовой задачи SHALL быть атомарным и выдавать ограниченное по времени владение с уникальным токеном. Продление, переход состояния и допуск внешнего действия MUST отклоняться для истёкшего или заменённого токена. Время следующего запуска SHALL учитываться при выборе задачи.

#### Scenario: Одновременное получение
- **WHEN** два обработчика одновременно запрашивают одну готовую задачу
- **THEN** только один получает действующее владение

#### Scenario: Устаревший обработчик
- **WHEN** прежний обработчик пытается изменить задачу после выдачи нового владения
- **THEN** изменение отклоняется без перезаписи состояния нового обработчика

### Requirement: Одноразовый допуск внешнего действия

Перед запросом разбора, платным анализом или публикацией SHALL подтверждаться уникальная запись намерения, связанная с задачей и входом. Повторный допуск той же попытки MUST отклоняться, даже при одинаковых данных. До подтверждения записи вызывающий MUST NOT отправлять внешнее действие.

#### Scenario: Повтор вызова перед отправкой
- **WHEN** одна и та же попытка уже получила подтверждённый допуск и снова запрашивает его
- **THEN** второй допуск не выдаётся, новая внешняя отправка не разрешается

#### Scenario: Неудачная фиксация
- **WHEN** запись намерения не подтверждена из-за ошибки хранения
- **THEN** вызывающий получает ошибку и не отправляет запрос

#### Scenario: Отказ повторному вызову не отменяет первый допуск
- **WHEN** после сохранённого начала повторный вызов получил отказ в допуске и вернул отсутствие отправки
- **THEN** такой исход не закрывает первую попытку автоматически и не разрешает новую отправку

### Requirement: Журнал разбора OpenDota

Хранилище SHALL сохранять известный job ID разбора либо безопасную сводку ошибки, включая признак возможной успешной отправки. Неизвестный исход MUST блокировать автоматический повтор POST; известный job ID SHALL быть доступен для продолжения проверки готовности.

#### Scenario: Ответ с job ID сохранён
- **WHEN** приложение возобновляет задачу с известным job ID
- **THEN** получает этот ID для проверки готовности без создания нового задания разбора

#### Scenario: Ответ потерян
- **WHEN** отправка могла создать задание, но job ID не получен или не сохранён
- **THEN** попытка остаётся с неизвестным исходом и не становится разрешением повторить POST

### Requirement: Совместимость с попытками аналитика

Хранилище SHALL принимать существующие StartedAttempt и AnalysisAttempt без изменения их формата, сопоставляя их с заранее сохранённым подготовленным запросом. Ошибка до отправки с отсутствующей идентичностью SHALL сохраняться в контексте задачи без выдуманной идентичности и списания.

#### Scenario: Сохранение перед платным запросом
- **WHEN** аналитик передаёт StartedAttempt перед отправкой
- **THEN** допуск проверяет полную идентичность запроса и подтверждается до возврата управления аналитику

#### Scenario: Отказ до отправки
- **WHEN** аналитик возвращает preflight-failed с requestSent=false и пустой идентичностью
- **THEN** сохраняются исходная ошибка и отсутствие отправки без фиктивного успешного анализа

### Requirement: Идемпотентное завершение попытки

Сохранение полученного исхода SHALL допускать точный повтор того же содержимого без второго результата. Противоречивое завершение того же attempt ID MUST отклоняться. Просроченное владение MUST NOT мешать сохранению достоверного ответа уже допущенной попытки, но MUST NOT разрешать смену состояния задачи устаревшим обработчиком.

#### Scenario: Потеря подтверждения сохранения
- **WHEN** обработчик повторно сохраняет тот же исход после потери подтверждения
- **THEN** получает ранее сохранённую запись без дубликата

#### Scenario: Поздний ответ
- **WHEN** ответ допущенного анализа пришёл после истечения владения
- **THEN** он сохраняется в журнале; обновление задачи требует нового действующего владения

### Requirement: Проверенные результаты и история

Результатом анализа SHALL становиться только valid-попытка с проверенными форматом, ссылками на факты и идентичностью. selected и insufficient-evidence SHALL сохраняться как разные допустимые исходы. Чтение последней задачи и последнего допустимого результата MUST различаться; неудачная новая ревизия MUST NOT удалять прежний результат или повышать статус калибровки.

#### Scenario: Новая ревизия не дала ответа
- **WHEN** после сохранённого допустимого результата новая ревизия завершилась invalid-output
- **THEN** последняя задача отражает ошибку, а запрос последнего допустимого результата возвращает прежний анализ и его ревизию

### Requirement: Восстановление с учётом неизвестного исхода

Восстановление SHALL затрагивать только просроченное владение. Задача без незавершённого внешнего действия SHALL продолжаться с сохранённой контрольной точки; неподтверждённое завершение отправки SHALL переводить её в состояние внимания. Восстановление MUST NOT выполнять сеть или автоматически повторять такие действия.

#### Scenario: Сбой между допуском и сохранением ответа
- **WHEN** процесс завершился и осталась только запись начала анализа или публикации
- **THEN** восстановление сохраняет неизвестность и блокирует автоматическую повторную отправку

#### Scenario: Сбой на локальной подготовке
- **WHEN** владение истекло до допуска внешнего действия
- **THEN** задача становится доступна для продолжения с последней подтверждённой точки

### Requirement: Явное разрешение неопределённости

Хранилище SHALL сохранять решение о неизвестном исходе с причиной, временем и ссылкой на исходную попытку, не стирая её. Разрешение новой попытки MUST быть отдельным явным решением вызывающего; оно MUST NOT означать, что прежний запрос не выполнялся или был бесплатным.

#### Scenario: Решение повторить после проверки
- **WHEN** вызывающий явно разрешает новую попытку после неопределённого исхода
- **THEN** решение доступно для аудита, новая попытка имеет другой ID, а прежняя неизвестная стоимость сохраняется

### Requirement: Учёт стоимости без подмены неизвестности

Хранилище SHALL сохранять usage, известную фактическую стоимость, оценку и состояние оплаты отдельно. Неизвестная стоимость MUST NOT превращаться в ноль или оценочную стоимость. Сводка SHALL отдельно возвращать известные расходы, число неизвестных попыток и оценки незавершённых отправок, без принятия решений о бюджете.

#### Scenario: Оплаченный некорректный ответ
- **WHEN** анализ завершился invalid-output с известной стоимостью
- **THEN** расход учитывается независимо от отсутствия пригодного результата

#### Scenario: Потеря ответа после начала
- **WHEN** у допущенной попытки нет подтверждённого завершения
- **THEN** сводка показывает неизвестную стоимость и отдельную оценку, а не нулевой расход

### Requirement: Постоянная запись публикации

Публикация SHALL связывать ревизию, допустимый результат, сохранённую цель и digest подготовленного сообщения. Известный message ID SHALL сохраняться без потери точности. Неизвестный исход MUST блокировать автоматическую повторную публикацию; повторное сохранение того же message ID SHALL быть идемпотентным.

#### Scenario: Сбой после отправки сообщения
- **WHEN** Discord мог принять сообщение, но подтверждение не сохранено
- **THEN** задача требует разрешения неопределённости вместо автоматической повторной публикации

#### Scenario: Известное опубликованное сообщение
- **WHEN** задача прочитана после перезапуска с сохранённым message ID
- **THEN** возвращаются тот же ID, исходная цель и использованная ревизия анализа

### Requirement: Безопасные ошибки и границы хранения

Ошибки SHALL содержать стабильный код и безопасную идентичность операции без SQL, содержимого артефактов или секретов. Хранилище MUST NOT принимать объекты сетевых зависимостей, API-ключи и заголовки авторизации как часть контракта. Недопустимые входы и превышение ограничений SHALL отклоняться до изменения данных.

#### Scenario: Ошибка ввода с приватными данными
- **WHEN** запись артефакта отклонена по структуре, размеру или целостности
- **THEN** ошибка не содержит тело запроса или содержимое снимка

#### Scenario: Конфликт или занятая база
- **WHEN** запись не может быть выполнена из-за конкуренции или ошибки диска
- **THEN** операция не сообщает об успешном допуске внешнего действия и не запускает его самостоятельно
