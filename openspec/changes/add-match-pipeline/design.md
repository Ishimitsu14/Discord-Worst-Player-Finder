# Design

## Context

Мотивация — [proposal.md](proposal.md), наблюдаемое поведение — [spec.md](specs/match-pipeline/spec.md). Ниже проект нового модуля; его код пока отсутствует.

Проверено по исходникам 17 октября 2026:

- GroupSettings содержит только steamAccountIds/guildId/channelId и загружается отдельно. Настройки конвейера и секреты нельзя добавлять в этот JSON.
- OpenDotaClient принимает limit 1..100/offset, возвращает исходные режимы и кеширует историю 30 секунд. getMatch поддерживает fresh; один requestParse не повторяет POST. waitForParsedMatch подтверждает готовность свежим parseState, не исчезновением job.
- Storage уже сохраняет задачи, входы и внешние попытки. Claim действует 60 секунд; renewClaim, checkpoint и saveInputs меняют version. Reserve/start и сохранение исхода version задачи не меняют. SQL-транзакции короткие и синхронные.
- У storage нет курсора обнаружения, произвольных метаданных задачи, дневного бюджета или операции перезапуска failed-задачи. При наличии prepared запрещена замена входа; checkpoint может принять существующий valid-исход своей ревизии, если попытка не released.
- prepareMatchFacts требует положительную длительность, boolean radiant_win, канонические уникальные слоты и всю пятёрку выбранной стороны. Parsed не доказывает наличия всех журналов. Словарь и профиль фиксируются существующим модулем.
- analyzeMatch делает preflight, вызывает асинхронный beforeSend, отправляет один POST и возвращает AnalysisAttempt. До callback могут быть null identity/attemptId. Реальный пилот пакета 8192/upstream-default вернул length без результата; пакет остаётся experimental.
- Discord-интерфейс и operations отсутствуют. Их реализация, миграции storage и новые реальные API-прогоны не входят в это изменение.

Справочники OpenDota подтверждают значения [lobby_type](https://raw.githubusercontent.com/odota/dotaconstants/master/build/lobby_type.json) 5/6/7 как рейтинговые и [game_mode](https://raw.githubusercontent.com/odota/dotaconstants/master/build/game_mode.json) 23 как Turbo, 15 как custom, 22 как all_draft. Список поддерживаемых обычных режимов ниже — правило конвейера v1; balanced сам по себе не доказывает рейтинговость.

## Goals / Non-Goals

**Goals:**

- Переиспользовать публичные API готовых модулей; не вводить параллельное хранилище, HTTP-транспорт или новую схему данных.
- Один последовательный worker на БД, воспроизводимые входы и явные причины остановки/ожидания.
- Проверять полный процесс с настоящей временной SQLite и поддельными внешними API, сохраняя различие между тестом протокола и качеством MiMo.

**Non-Goals:**

- Гарантия обнаружить всю историю при ограниченной пагинации, распределённые workers и общий бюджет нескольких процессов.
- Автоматическое разрешение неизвестных исходов, финансовая сверка OpenRouter, сброс расходов и скрытые повторы платного запроса.
- Выбор худшего в коде, изменение инструкции/ролей, привязки аккаунтов к людям, Discord SDK и настройка VPS.

## Decisions

### 1. Публичный модуль и конфигурация

`src/match-pipeline/index.ts` экспортирует типы, безопасные ошибки и `createMatchPipeline(options, dependencies)`. Небольшие внутренние файлы отделяют классификацию/обнаружение от исполнения шагов. Файлы, env, БД и зависимости открывает caller; новых npm-пакетов нет.

Предлагаемые параметры v1:

| Параметр | Значение и проверка |
|---|---|
| mode | prepare-only по умолчанию, либо явно live |
| automaticSince | постоянный Unix timestamp в миллисекундах, обязателен для обнаружения; неотрицательный safe integer, не позже текущего времени |
| pollIntervalMs | 900000 по умолчанию; положительное safe integer не меньше 60000 |
| pageSize / maxPagesPerAccount | 20 / 1 по умолчанию; размер 1..100, число страниц 1..10 |
| maxCandidatesPerScan | 100 по умолчанию, 1..1000 уникальных match ID |
| workerIdleMs | 1000 по умолчанию, не меньше 1000 |
| pauseMs | 300000 по умолчанию, не меньше 60000; ожидание включения live, бюджета или адаптера |
| parseTimeoutMs / parsePollMs | 900000 / 15000 по умолчанию; положительные, poll не меньше 15000 и не больше timeout |
| analysisTimeoutMs | 180000 по умолчанию, в пределах существующего API аналитика; тело запроса и max_tokens не меняются |
| publicationTimeoutMs | 30000 по умолчанию, положительное safe integer в диапазоне таймера Node |
| maxTotalCostUsd / maxEstimatedCostPerAttemptUsd | обязательные конечные положительные числа для live, без подразумеваемого $0.25 |
| allowExperimental | false по умолчанию; явное разрешение анализа сохранённым experimental-пакетом |

Все неизвестные поля отклоняются. Параметры и GroupSettings копируются и закрепляются на срок жизни экземпляра. Изменение режима/лимитов или активация другого конфигурационного снимка требует остановки и создания нового экземпляра; существующие задачи сохраняют собственные настройки. Общую загрузку конфигурации здесь не реализуем.

`automaticSince` — часть постоянной локальной конфигурации будущего bootstrap. При первом включении caller фиксирует момент включения и затем передаёт тот же timestamp; автоматического `Date.now()` вместо отсутствующего значения нет. Так не требуется новый state/cursor в SQLite. API позволяет ручную обработку без включённого обнаружения. Новый экземпляр с намеренно другой границей — явное изменение конфигурации, а не эффект перезапуска.

### 2. Классификация и сторона

Один локальный классификатор применяется перед постановкой и исполнением. Поддерживаются lobby_type 5/6/7 совместно с game_mode 1/2/3/4/5/12/16/17/22. Остальные значения возвращают unsupported-match. Исход должен быть boolean, duration > 0. Все присутствующие слоты должны быть каноническими и уникальными; для анализа требуется полная выбранная пятёрка. Матч может иметь неполный состав соперников согласно match-facts.

Рейтинговость не выводится из победы, MMR, названия героя или одного balanced-флага. Справочник режимов фиксируется локальными константами v1 с указанными источниками; загрузки из сети во время классификации нет. Это не изменение закреплённого словаря фактов.

Сторона определяется по слотам 0..4 / 128..132. Счётчик компании — множество разных числовых Steam32 из GroupSettings и snapshot.data.players[].account_id. 0, 4294967295, null, отсутствие и строки не считаются подтверждением. Повтор одного account ID в разных слотах не даёт два голоса; противоречивый повтор на разных сторонах возвращает ambiguous-side.

- Ручной запрос с side использует её без условия двух друзей. Без side допускается ровно одна сторона, на которой опознаны друзья; при наличии друзей на обеих сторонах или ни на одной возвращается requires-side.
- Автоматический запрос требует ровно одну сторону со счётчиком >=2. Ноль подходящих сторон — not-group-match; две — requires-side. Вторая задача автоматически не создаётся.
- История аккаунта даёт кандидата, но не заменяет отсутствующие ID в полном матче. Даже если одна история недоступна, матч из другой может подтвердить компанию полным составом.

Отказ классификатора не создаёт фиктивного результата insufficient-evidence. Этот статус может вернуть только аналитик после подготовки пригодных фактов.

### 3. Постановка и обнаружение

`requestMatch({matchId, side?})` проверяет типы до сети. Для явной стороны сначала можно вернуть существующую первую задачу: getLatestJob находит пару, затем enqueueInitial возвращает её revision=1 без изменения настроек. Новая постановка или определение стороны требует свежего getMatch и классификации. Получение статуса уже известной задачи выполняется отдельным чтением без сети.

`requestReanalysis({requestId, matchId, side})` всегда требует явную сторону для постоянства ключа команды. После проверки матча вызывает createRevision с текущим снимком GroupSettings; отсутствие первой задачи или unfinished отражаются как conflict/not-found. Первый запрос не превращается в повторный анализ автоматически.

`discoverOnce()` проходит настроенные аккаунты последовательно через существующий OpenDotaClient. Страницы запрашиваются с заданными pageSize/offset, до короткой/пустой страницы или лимита. Список candidate ID объединяется по всему циклу; обрабатывается не более maxCandidatesPerScan. Противоречивые/повторные строки не увеличивают счётчики. Порядок времён между страницами не считается доказанным, поэтому раннего завершения только по «старой» строке нет.

Для каждого кандидата рассчитывается `(start_time + duration) * 1000`, с проверкой целых, переполнения и отсутствия будущего времени. Автоматически рассматриваются только endAt > automaticSince. Старт игры до границы допустим, завершение до неё — нет. История предварительно отсекает явно старые/неподдерживаемые строки, но окончательная классификация и сторона подтверждаются свежим полным матчем. В storage передаётся enqueueInitial с origin=automatic.

Уже существующая automatic-задача с теми же настройками на подтверждённой стороне переиспользуется. Для уменьшения повторных подробных GET допускается пропуск кандидата, когда getLatestJob показывает такую задачу; ручная задача на другой стороне не считается доказательством автоматической стороны. Неподходящие матчи не получают постоянную фиктивную задачу. recordMatch фиксирует обнаруженные ID, но не используется как курсор или отрицательный кеш пригодности.

DiscoveryReport содержит scanAt, cutoff, просмотренные страницы/кандидаты, поставленные/существующие job ID, причины отклонений, requires-side, ограниченные безопасные ошибки по аккаунтам и partial. При полной странице на пределе, ограничении кандидатов, ошибке аккаунта/страницы/подробного GET выставляется partial. Следующий цикл начинает ограниченный просмотр заново с той же границей; он не обещает наверстать всё после долгого простоя. Дополнительные страницы включаются явной конфигурацией, пропущенный матч можно поставить вручную.

Альтернатива с долговечным курсором потребовала бы отдельного изменения storage. Для небольшого частного сервиса сначала используем ограниченный повторный просмотр и существующую дедупликацию. Таймер следующего опроса отсчитывается от завершения цикла; переполнение интервала не создаёт параллельный цикл.

### 4. Обработка сохранённых задач

`processNext()` берёт максимум одну задачу через claimNext; пересекающийся вызов возвращает busy, а не второе владение. Один объект конвейера и один последовательный worker на БД — условие эксплуатации v1. Запуск нескольких процессов на ту же БД не является поддерживаемым способом масштабирования бюджета.

Сначала читаются job, getJobArtifacts и listAttempts. Журнал важнее устаревшего имени step: известный message ID позволяет завершить задачу; подходящий unreleased valid-исход принимается checkpoint без повторного MiMo; prepared используется буквально. Released-попытка остаётся историей и автоматически текущим результатом не становится.

| Шаг | Действие и подтверждённая точка |
|---|---|
| load-match | getMatch fresh, проверка режима/стороны по снимку настроек задачи, saveInputs(snapshot). Parsed → build-facts; basic → wait-parse |
| wait-parse | свежий GET; parsed сохраняется и продолжает build-facts. Для basic известный job ID используется повторно; без допуска разбора задача ожидает. В live перед первым requestParse выполняется beginParse, затем сразу saveParseOutcome |
| build-facts | prepareMatchFacts с закреплённым словарём и side задачи, без ручных roleOverrides в v1; prepareAnalysis с переданным пакетом. saveInputs(bundle, prepared) атомарно закрепляет входы, checkpoint → analyze |
| analyze | режим/калибровка/бюджет, одна reservation и один вызов analyzeMatch; сохранить final. Valid → принять checkpoint и publish; иной отправленный результат → failed, без исправляющего запроса |
| publish | известный message ID → succeeded; нет адаптера/live → waiting. Иначе локальная подготовка, beginPublication, один send, сохранение исхода и succeeded либо остановка по правилу исхода |

Во время исполнения используется settings задачи. Последующие настройки процесса не меняют сторону, канал или список компании старой задачи. Для automatic заново подтверждаются минимум два ID на её стороне; если свежие данные противоречат подтверждённой стороне, задача завершается eligibility-changed без отправки.

Перед первым POST по восстановленной задаче выполняется свежая проверка пригодности. Она не заменяет закреплённые факты: если изменились режим, исход, длительность или состав героев/слотов относительно сохранённого подготовленного входа, возвращается input-changed с необходимостью новой ревизии. Позднее обогащение необязательных данных не пересобирает прежний запрос. После принятого анализа публикация использует этот результат без нового получения статистики.

`wait-parse` использует короткую проверку getMatch(fresh) и при необходимости getParseJob. Исчезновение job — не успех. Срок ожидания вычисляется от createdAt сохранённой допущенной parse-попытки, а не от нового запуска процесса. До срока — defer с nextRunAt=max(now+parsePollMs, retryAt). После срока и последнего свежего basic — failed с parse-timeout. Повторять POST по таймауту, анализировать basic как скрытый fallback или удалять прежний снимок нельзя.

Перед первым beginParse проверить также getLatestJob противоположной стороны того же матча и её listAttempts. Известный job ID переиспользуется с исходным сроком, не создавая фиктивную свою отправку. При unresolved-разборе другой стороны допускается только fresh GET и ожидание с причиной shared-parse-unknown, без нового POST; после появления parsed можно продолжить без повторного разбора. Если job ID неизвестен, срок такого ожидания также берётся из сохранённой чужой попытки. Истёкшее ожидание завершается failed, чужая попытка и её неизвестность не изменяются. Это закрывает случай двух явных ручных сторон в одном сервисе без нового контракта storage.

В prepare-only basic сохраняется и ждёт parse-disabled без намерения отправки; parsed проходит до сохранённого prepared и ждёт live-disabled. Такой запуск не создаёт поддельных valid-ответов и не вызывает beforeSend. Смена режима позволяет продолжить те же пригодные входы. Отсутствие publisher оставляет принятую задачу waiting/publish с publisher-unavailable; это не ошибка анализа.

### 5. Режимы, стоимость и один вызов аналитика

Live требует ключ, maxTotalCostUsd и maxEstimatedCostPerAttemptUsd. Проверка относится к одному worker и всем попыткам в переданной БД за всё время, а не к дню, пользователю или только успешным результатам. Пилотные файлы лаборатории не входят в эту БД и не импортируются; прежний лимит $0.25 не является конфигурацией нового сервиса. Разделение по дням потребовало бы нового контракта хранения и пока не нужно.

Порядок analyze:

1. Прочитать сохранённый prepared. Проверить live и его calibration; experimental допускается только при allowExperimental. Не изменять calibration и не повышать max_tokens автоматически после length.
2. Прочитать getBillingSummary. При unknownCount > 0 не вызывать analyzeMatch вообще. При исчерпанном остатке — waiting с budget-exhausted. Ожидающие неопределённые стоимости не подменяются estimatedCostUsd.
3. Создать новый UUID и reserveAnalysis только непосредственно перед одним вызовом analyzeMatch. Передать maxEstimatedCostUsd=min(лимит попытки, общий лимит минус knownCostUsd), явный timeout и signal.
4. В beforeSend ещё раз проверить актуальное владение, остановку и сводку расходов после сетевого preflight. В одном синхронном участке без await между проверкой и записью сравнить StartedAttempt.estimatedCostUsd с обоими лимитами и вызвать startAnalysis с текущим Claim. Возврат разрешает один POST.
5. Сохранить возвращённый AnalysisAttempt прежде любого checkpoint, освобождения задачи или следующего вызова. Valid принимается как результат; selected/insufficient-evidence сохраняются буквально. Все отправленные невалидные/ошибочные исходы завершают задачу failed без retry POST. Известная цена учитывается независимо от status.

Новая попытка не создаётся из-за invalid-output, length, 429 после POST, timed-out, transport-error или model-mismatch. Пользовательское повторение — requestReanalysis либо отдельное явное аудируемое решение по неизвестному действию. Ошибка до отправки позволяет локальное ожидание: metadata-unavailable/cooldown учитывают retryAt, unknown-price/unsupported-endpoint и превышение оценки показывают причину ожидания конфигурации. При новом безопасном preflight используется новый reservation ID, старый исход сохраняется.

Если callback отказал по бюджету до записи started, аналитик вернёт not-sent/preflight-failed; этот исход закрывает prepared-reservation, затем задача переводится в waiting. Конкретная причина отказа callback хранится в локальном контексте вызова как безопасный код, не выводится из строки исходного исключения.

Для started с последующим requestSent=false storage намеренно вернёт conflict: это не повод отменять первый допуск. Задача переводится в needs-attention при сохранившемся владении либо остаётся для recoverInterrupted. Только внешний оператор может принять проверенный notSentOutcome через существующий resolveUncertain. Сам pipeline этого не делает.

Unknown-стоимость финального sent-исхода отличается от незавершённого внешнего действия. Анализ valid с неизвестной ценой можно сохранить и опубликовать, но новые генерации блокируются. Ошибочный финал с неизвестной ценой даёт failed и явное предупреждение о расходе; storage не допускает needs-attention без unresolved-действия, поэтому внимание в статусе вычисляется также по billingState. Разрешение повторить действие в storage не устраняет неизвестность оплаты и не обходит бюджетную проверку. Автоматическая финансовая сверка остаётся вне v1.

Ограничение — проверка оценки, а не жёсткая гарантия фактического счёта: тарифы и эвристика могут отличаться от результата. При фактическом превышении сохранённый расход не обрезается, следующие генерации блокируются. Несколько процессов могли бы одновременно пройти чтение общей сводки; v1 требует единственного экземпляра сервиса на БД, а не обещает распределённую резервацию бюджета.

### 6. Lease, ошибки и восстановление

На время processNext хранится один изменяемый execution context с текущим Claim и AbortController. Heartbeat раз в 20000 мс вызывает renewClaim и заменяет Claim. Каждая синхронная checkpoint/saveInputs-операция также немедленно обновляет контекст. Замыкания beforeSend и завершения не сохраняют старую копию version; сетевое ожидание не держит SQL-транзакцию.

При lease-lost прекращаются новые действия и отменяется ожидание. Поздний достоверный исход parse/analysis/publication всё равно передаётся в соответствующий saveOutcome, но checkpoint/finish старым токеном не вызывается. Ошибка записи/COMMIT считается фатальной для текущего запуска: цикл прекращается, новые задачи и отправки не начинаются, caller получает storage-failure. БД не закрывается и не пересоздаётся автоматически.

Состояния восстановления:

| Сохранённое состояние | Продолжение |
|---|---|
| queued / waiting с наступившим nextRunAt | claimNext, чтение контрольной точки и журнала |
| просроченный running без отправки | явный recoverInterrupted, затем продолжение с нового токена |
| known parse job ID | свежая проверка данных / ожидание того же задания |
| prepared без started, закрытый при аварии | новый reservation ID при следующем разрешённом анализе, тело запроса прежнее |
| started/interrupted без final либо unknown parse/publication | needs-attention, без автоматического нового POST |
| unreleased valid без job.resultAttemptId | принять existing attempt через checkpoint и продолжить publish |
| job.resultAttemptId без адаптера | ждать адаптер, результат уже доступен |
| известный message ID без terminal job state | finish succeeded с новым действующим владением, без send |
| failed / succeeded | не перезапускать; ручный первый запрос показывает сохранённое состояние |

До первого цикла исполнения вызывается recoverInterrupted, затем периодически перед claimNext, чтобы можно было подобрать недавно истёкшее владение прошлого процесса. Оно не трогает действующие lease. Сам pipeline не вызывает resolveUncertain с allow-new-attempt. Если оператор отдельно дал такое решение, новый ID допустим по журналу; для анализа дополнительно остаётся проверка неизвестной оплаты, для разбора сначала снова проверяется fresh parsed. Это явное разрешение оператора, а не автоматический retry.

GET-ошибки network_error/timeout/upstream_error/rate_limited откладывают задачу до max(retryAt, now+60000), не создавая намерение POST. Встроенные ограниченные GET-retry клиента сохраняются; второго быстрого retry-цикла вокруг них нет. Срок parseTimeout продолжает идти между перезапусками. Permanent not_found/unauthorized/forbidden/invalid_response и ошибки фактов/размера завершают задачу с безопасным кодом. Доменная проверка словаря и пакета выполняется публичными функциями при подготовке до MiMo; содержимое ошибок не включается в диагностику.

При отмене до started сохранить not-sent и вернуть задачу в waiting с прежним шагом. После started следовать полученному фактическому исходу; отмена не доказывает отсутствие удалённой отправки. Если результат доступен, сначала сохраняется он; если остаётся неразрешённое действие — needs-attention либо восстановление после истечения владения.

### 7. Стык публикации

Передаваемый необязательный адаптер:

```ts
interface Publisher {
  prepare(input: PublicationContext): string;
  send(input: PublicationInput, options: { signal: AbortSignal }): Promise<{ messageId: string }>;
}
```

PublicationContext содержит Job, принятый AnalysisAttempt, его FactsBundle и исходный MatchSnapshot. Prepare — локальное построение точной JSON-строки без сети; формат embeds, mentions, доступность guild/channel и права отвечает будущий Discord-модуль. PublicationInput — уже существующий тип storage с version, guildId, channelId, analysisAttemptId и message. Цель берётся из settings задачи, а не текущих настроек процесса.

Pipeline проверяет JSON-объект и предел до beginPublication, затем передаёт в send сохранённый receipt.input. Успех требует строкового uint64 message ID и savePublicationOutcome до finish succeeded. Повторный чтение известного ID не вызывает prepare/send. Подготовка без адаптера или с локально некорректным payload даёт waiting с publisher-unavailable/publication-invalid, не создавая намерение отправки.

Адаптер может вернуть безопасную типизированную ошибку с code и подтверждённым исходом not-sent/unknown. Любая неизвестная ошибка после вызова send и неверный успешный message ID считаются unknown; сырое исключение не хранится. Not-sent завершает задачу failed, сохраняя анализ; автоматического повтора публикации нет. Исправление/редактирование уже отправленного сообщения и повтор известного отказа публикации отдельной командой не входят в v1. Сохранённый анализ остаётся доступным для показа Discord-интерфейсом.

Таймаут ожидания send не доказывает отмену его физической отправки. Если underlying Promise ещё выполняется, оставить started без выдуманного final, перевести задачу в needs-attention и подписаться на поздний исход без смены job state. Это позволяет сохранить поздний message ID через существующий storage API. Если адаптер уже завершил Promise с неизвестным исходом, сохранить терминальный unknown. Повторная противоречивая запись не затирает принятый исход. Остановка не обещает остановить удалённый эффект; неизменяемый журнал остаётся основанием для следующего решения.

### 8. API, цикл и диагностика

| API | Контракт |
|---|---|
| createMatchPipeline(options, dependencies) | проверить параметры/GroupSettings/форму зависимостей, скопировать конфигурацию; без опроса и POST |
| requestMatch({matchId, side?}, {signal?}) | queued/existing с job и result либо requires-side/rejected с безопасным кодом; явный положительный number |
| requestReanalysis({requestId, matchId, side}, {signal?}) | новая revision либо идемпотентный прежний job; без скрытого повтора генерации |
| discoverOnce({signal?}) | DiscoveryReport; параллельный опрос этого экземпляра сообщает busy |
| processNext({signal?}) | idle/busy либо job ID с достигнутым сохранённым состоянием; не более одной задачи |
| getStatus({jobId}) | текущий Job, безопасная причина, attention и последний принятый результат пары отдельно от последней ревизии; без сети |
| run({automatic = true, signal?}) | явный длительный цикл опроса и одного worker, без перекрытий своего вида; automatic=false допускает ручную очередь без automaticSince |
| stop() | прекратить новые действия, отменить ожидание и дождаться доступных сохранений/выхода циклов; БД и клиенты не закрывать |

Dependencies: готовые GroupSettings/OpenDotaClient/Storage, FactsOptions со словарём, PromptPackage, apiKey/fetcher аналитика при live, необязательный Publisher и onEvent, clock с now/setTimeout/clearTimeout. На соседние внутренние файлы не опираться. Собственный fetch конвейер не создаёт. FactsOptions в v1 принимает только dictionary; override ролей и изменение инструкции через ручную команду не добавляются.

Run объединяет опрос и обработчик; discovery и worker могут ждать сеть одновременно, но внутри каждого вида перекрытия нет. Они используют один OpenDotaClient с его ограничениями частоты. Новый run во время работы возвращает already-running. Stop идемпотентен; остановленный экземпляр не принимает новых исполняющих действий, для следующего запуска создаётся новый объект. GetStatus после stop доступен, пока caller не закрыл Storage. Отсутствие готовой задачи даёт задержку workerIdleMs, ожидание следующего запуска задачи не держит владение.

onEvent получает только jobId/matchId/side/revision/state/step/code и агрегаты DiscoveryReport. Сырые запросы, content, ключи, HTTP headers, оригинальные Error.message/cause и полные списки аккаунтов туда не передаются. Исключение или отклонённый Promise onEvent поглощается и не становится исходом запроса. Ошибки самого pipeline содержат стабильный код и безопасные ID; данные не выводятся в консоль автоматически.

### 9. Проверка до интеграции с Discord

Тесты используют существующие синтетические fixtures, настоящие временные SQLite-файлы и реальные публичные функции OpenDota/фактов/аналитика с поддельным fetch. Не создавать фиктивный production-анализатор, выдающий худшего для режима подготовки.

Покрыть ручные/авто стороны, ранжирование режимов, активацию/перезапуск и граничные времена; повторные страницы, ошибки одного аккаунта, лимиты и partial; общую дедупликацию и идемпотентные ревизии. Интеграция проходит basic → known parse job → fresh parsed → факты/prepared → started → valid → сохранённое сообщение/ID. Проверяются также already-parsed и insufficient-evidence.

Управляемые часы проверяют heartbeat/version при длинном запросе, потерю владения, cooldown, parse deadline и stop без настоящих задержек. Fault-тесты/дочерний процесс прерывают работу между фиксацией результата и checkpoint, перед/после publication admission и отправки. После переоткрытия не должно быть второго платного POST или сообщения. Отдельно проверить сохранение позднего исхода, callback not-sent после started, ошибку диска и завершение цикла при ней.

Бюджет проверять на известных расходах, invalid-output, unknown, изменении оценки между проверками и фактическом превышении; prepare-only/нет experimental-допуска/нет publisher дают ноль соответствующих POST. Полный набор проекта выполнить после focused-проверок; известный Windows sandbox EPERM на fs.link существующей лаборатории перепроверять с необходимыми разрешениями, не меняя её код. Linux отметить отдельно по фактическому запуску, без объявления его проверенным по TypeScript.

## Risks / Trade-offs

- [Ограниченная история и поздняя индексация OpenDota] → Повторный просмотр, постоянная дедупликация, partial и ручной ID. После долгого простоя возможны пропуски вне глубины; полного исторического catch-up v1 не обещает.
- [Потеря automaticSince в конфигурации bootstrap] → Обнаружение требует явное постоянное значение; не подставлять новый timestamp. Сохранность файла конфигурации обеспечивает operations.
- [Несколько процессов обходят последовательную проверку бюджета] → Один экземпляр сервиса на БД — условие v1. Распределённые резервации потребовали бы отдельного storage-изменения.
- [Эвристика цены и неизвестная оплата] → Нет гарантии жёсткого счёта; все исходы сохраняются, при unknown новые генерации блокируются до отдельного разбора.
- [Профиль MiMo ещё не дал пригодного реального ответа] → prepare-only по умолчанию, явный experimental-допуск, без автоматического увеличения лимита/повторов и без заявления о калибровке.
- [Истечение lease, отмена либо поздняя отправка SDK] → Актуальный Claim в execution context, heartbeat и durable started; поздний исход сохраняется отдельно, а удалённый exactly-once не обещается.
- [Изменение данных между подготовкой и исполнением] → Сохранённый вход неизменяем; существенное противоречие требует новой ревизии, обогащения не меняют запрос скрыто.
- [Публикация ещё не реализована] → Минимальный порт с тестовым адаптером, допустимый анализ хранится независимо. Реальные permissions/mentions/Discord SDK проверяются модулем 6.

## Migration Plan

1. Реализовать новый модуль и его инструкцию отдельно, не меняя форматы/миграции storage и не подключая автоматический запуск из существующего CLI лаборатории.
2. Выполнить локальные интеграционные и crash-тесты на временных БД без ключей и реальных внешних отправок. Зафиксировать результаты typecheck/test/OpenSpec и платформенные пробелы в `src/match-pipeline/VERIFICATION.md`.
3. Подключать bootstrap и Discord отдельными изменениями. Первое включение автоматического режима требует сохранённого automaticSince; live включается отдельной конфигурацией с бюджетом и осознанным допуском experimental.
4. Откат — остановить конвейер, сохранить БД и вернуть прежний bootstrap. Задачи и журнал не удаляются; схемы БД не меняются. Повторное подключение использует ту же границу активации и существующие контрольные точки.
