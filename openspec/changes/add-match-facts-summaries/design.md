# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md). Наблюдаемое состояние кода перед изменением:

- `normalize.ts` связывает десять участников карточки с каноническими слотами, хранит их смерти, отдельный header и `inconsistent-death-counts`. Короткий отчёт пока не разделяет сумму по сторонам.
- `brief.ts` уже группирует метрики и сохраняет производные в `facts.derived`. В объектах передаются type/key/time и подтверждённый actor; счётчика именно строений нет.
- `Registry` создаёт последовательные eN, зависимости и формулы. Проверка воспроизводит весь пакет, coverage сопоставляет значения с исходником, ссылки принимаются только на переданные значения.
- `prepareMatchFacts` имеет единственный профиль. `match-analysis/input.ts` проверяет закрытые свойства v1 и точные версии manifest. Простое добавление свойств сломает этот контракт.
- `src/evaluation-lab/facts.ts` сохраняет шесть артефактов, manifest последним; отдельный диагностический повтор использует внутренние normalize/buildBrief.

Реальный сохранённый снимок 9048979975 и [отчёт эксперимента](../../../analysis/EXPERIMENT_2026-10-17.md) подтверждают конкретные ошибки. Это не гарантия поведения всех ответов OpenDota и не сравнение качества моделей. V2 ещё не реализован, его размеры, время и переносимость на Linux не измерены.

## Goals / Non-Goals

**Goals:** вычислять три объявленных семейства сводок из нормализованных наблюдений, обеспечить независимую проверку значений и покрытия, сохранить воспроизведение v1 и явный выбор v2.

**Non-Goals:** новый общий движок формул, API произвольных выборок драк, автоматическая проверка русского текста, универсальный рейтинг или нормативы ролей. Сокращение выхода MiMo и подключение нового входа — отдельный этап модуля 5. Эта работа не обещает уменьшения входа или ускорения генерации.

## Decisions

### 1. Отдельный формат и сохранение старого пути

Добавить явный `briefFormat` в параметры публичной подготовки/проверки: отсутствие или `match-brief-v1` выбирает старый путь, `match-brief-v2` — новый, прочие значения дают `invalid-input`. Для проверки несовместимость пакета/выбранного профиля даёт `integrity-error`; проверка не определяет новый формат молча по данным.

Сохранить имена и смысл существующих `Brief`, `FactsBundle`, `Manifest`, `FactsOptions` для v1; добавить типы V2 и перегрузки. Старый вызов статически возвращает прежний тип; новый формат возвращает V2. Общие проверки размера, ссылок и Markdown принимают оба формата, не расширяя автоматически тип входа текущего аналитика. Внутренние общие части переиспользуются без дублирования нормализации.

| Поле | V1 | V2 |
|---|---|---|
| context.version / format | 1 / match-brief-v1 | 2 / match-brief-v2 |
| facts.version / format | 1 / facts-v1 | 1 / facts-v1 |
| manifest.version | 1 | 1 |
| factsProfile / briefProfile | facts-profile-1 / brief-profile-1 | facts-profile-2 / brief-profile-2 |
| factsTransform / briefTransform | normalize-1 / summarize-1 | normalize-1 / summarize-2 |

Формат полных наблюдений и нормализация не меняются; профиль полных фактов меняется из-за новых `derived` и каталога. V2 строится из прежней основы с добавленным `summaries`; старые значения и ID образуют неизменённый префикс реестра. Новые evidence создаются после полного построения основы в фиксированном порядке. V1 не получает новых полей, каталога или limitations. У V2 новые digests/bundleId, а не переписанная идентичность старого результата.

Альтернатива — дописать поля в v1 либо сразу переключить потребителей — отвергнута из-за строгой схемы и сохранённых prepared/body. Отдельный сервис или новая БД не нужны.

### 2. Компактный контейнер сводок

`context.summaries` содержит `fightDeaths`, `buildingKillEvents`, `allyMetricOrder`. Те же наблюдения с ID помещаются в `facts.derived.summaries`. Каталог и ограничения V2 объясняют единицы, выборку, смысл нуля и неполноты. Никаких account ID, ников, произвольных raw-строк или ручной оценки в новых полях.

Сохраняются все данные v1: пять союзников и доступные соперники, ресурсы/поддержка, роли, фазы, предметы, все карточки, объекты и coverage. Размер ограничивается объявленным профилем и явной ошибкой, а не адаптивным удалением данных. V2 — расширение наблюдаемого контекста; экономию токенов не заявляем.

### 3. Смерти: сторона, выборка и полнота

`fightDeaths.byFight` следует порядку карточек и содержит `index`, `totals` с полями `radiant`, `dire`, `allies`, `opponents`, список `unavailableSlots` и `headerStatus: match|mismatch|unknown`. `totals` — одна именованная группа с ID. Значения внутри — число либо обычное unavailable-наблюдение.

Для стороны S вычисляется сумма `deaths` пяти её канонических участников только при известных числах у всех пяти. Смерти — неотрицательные safe integer; итог также проверяется на safe integer. Неполные значения не суммируются в якобы точный итог. Если хотя бы один слот недоступен, соответствующее поле получает unavailable с причиной `incomplete-side`; независимая сторона остаётся доступной. При неизвестном mapping обе стороны недоступны. `allies/opponents` — отображение Radiant/Dire через выбранную сторону, без повторной иной формулы.

`headerStatus` сравнивает header с суммой обеих сторон, только когда все величины доступны. Mismatch не исправляет данные: это суммы наблюдений участников, а не удостоверенный общий размен. Пропуски не требуют подавлять все остальные метрики карточки.

`fightDeaths.allCards` хранит состояние источника, число карточек и аналогичную группу итогов. Для стороны итог доступен, только если её сумма доступна в каждой карточке и итог — safe integer. Пустой present-список даёт ноль с основанием count=0; missing/null/invalid сохраняют unavailable соответствующего состояния. Любое расхождение header остаётся видимым и на уровне совокупной сводки списком индексов конфликтных карточек.

Итоги относятся только к предоставленным карточкам, которые могут перекрываться и не исчерпывают игру. Их нельзя называть уникальными смертями матча. Произвольные подгруппы не агрегируются: например, готовая сумма всех карточек не доказывает сумму карточек 0/1/5. Ограничение дальнейших формулировок аналитика — задача следующей инструкции.

Альтернатива — использовать общий header для нашей стороны — уже дала ошибку. Частичная сумма с подписями lower bound здесь не нужна: недоступный точный итог и видимые исходные значения проще для потребителя.

### 4. Строения: считать записи нужной категории

`buildingKillEvents` хранит `sourceState` и наблюдение `counts` с ID. При present-журнале его значение содержит `byPlayerSlot` для десяти канонических слотов, `unassigned`, `knownBuildingEvents`, `otherEvents`, `unclassifiedEvents`, `excludedByTime`. При missing/null/invalid весь counts недоступен с соответствующим состоянием. Нули означают только число подтверждённых записей в предоставленном журнале.

Предлагаемая закреплённая классификация V2:

| Тип события | Допустимый key | Категория |
|---|---|---|
| building_kill | распознанные tower, melee/range rax, fort из существующего allowlist | строение |
| CHAT_MESSAGE_TOWER_KILL | распознанный tower | строение |
| CHAT_MESSAGE_BARRACKS_KILL | распознанный melee/range rax | строение |
| First Blood, Roshan, Aegis и варианты, courier из существующего allowlist | не используется для признания строением | другие события |
| неизвестный/отсутствующий type, неподдержанный либо противоречащий типу key | — | неклассифицированные |

Это правила нашего преобразования, а не утверждение о полноте upstream-форматов. До классификации событие с недоступным временем или time вне `[0,duration]` относится к `excludedByTime`. Каждая исходная запись попадает ровно в одну категорию. Нераспознанные токены остаются безопасными unknown/unavailable, произвольные строки не возвращаются в контекст.

Строение прибавляется исполнителю только через существующий подтверждённый actor; крип/конфликт/неизвестный actor прибавляет `unassigned`. Инвариант: `knownBuildingEvents = sum(byPlayerSlot) + unassigned`; число всех исходных записей равно сумме четырёх категорий. В counts включены обе стороны; союзники определяются по слоту. Tower damage, last hit, Aegis и общий вклад не подменяют друг друга.

Единица — **событие журнала уничтожения строения**, не гарантированно уникальное здание. Каждая запись учитывается по исходному индексу; повторяющиеся записи не дедуплицируются эвристически по key или времени: одинаковый tower4 key может относиться к разным башням. Limitations явно запрещают вывод о гарантированной уникальности и полном числе действий за матч. Неполнота атрибуции/классификации показывается счётчиками, даже если parseState=parsed.

Альтернатива — подсчитать все события с actor — смешала бы First Blood со строениями. Новая эвристика определения исполнителя не вводится.

### 5. Порядок метрик: равенства и неизвестные

Фиксированный порядок восьми ключей: `hero_damage`, `tower_damage`, `hero_healing`, `stuns`, `gold_per_min`, `xp_per_min`, `net_worth`, `participation`. Все уже представлены у союзников; новая оценка роли или вычисление эффективности не требуется.

Для каждого ключа `allyMetricOrder[metric]` — отдельный факт с ID и значением `{groups:[{value,slots}], unavailableSlots, complete}`. Известные исходные числа сортируются по возрастанию; строго равные значения объединяются, слоты внутри группы идут канонически. `complete` истинно только при пяти известных значениях. Для каждого союзника существует ровно одно место: в одной группе либо unavailableSlots. Если известных нет, groups пуст, complete=false, минимум и максимум не выдумываются.

Первая/последняя группа — минимум/максимум **среди известных значений**; глобальность сравнения подтверждает только complete. Фильтрации «герои с контролем» нет: stuns сравниваются для всей пятёрки. Округление применяется только к Markdown, не к равенствам/порядку/ID. Числовой порядок не получает меток good/bad, штрафов, весов или списка кандидатов в худшие.

Альтернатива — общий рейтинг либо минимальный показатель, округлённый до сортировки — меняет смысл данных и выходит за границу подготовки фактов.

### 6. Происхождение и проверка

Новые записи Registry используют отдельные версионированные transform для сумм по сторонам/карточкам, классификации строений и порядка метрик. Поля metric/unit и каталог задают смысл групп; вложенная структура значения допустима через существующий generic Fact и Registry.add, без расширения старого Group произвольными кортежами.

Основания охватывают все входы, определяющие результат, включая отсутствие совпадений:

- смерти: группа смертей участников, mapping и нужные source paths, header для статуса, count/состав карточек для allCards;
- строения: count/путь всего журнала, type/key/time, actor и состояние всех записей, а не только подходящих герою;
- порядок: группы метрик всех пяти союзников с их слотами, включая unavailable, а не только отсортированные известные числа.

Значение каждой новой ссылки находится в context и facts.derived; source paths и зависимости остаются локально. Старые ID не перенумеровываются. `verifyFactsBundle` с явным V2-профилем проверяет версии/digests/реестр, независимое покрытие и воспроизведение по снимку. `checkCoverage` дополнительно подтверждает точное число карточек, партицию событий, представленность пяти слотов в каждом порядке и совпадение переданных сводок с локальными. Неизвестный transform/profile и согласованная подмена отвергаются.

В unit tests ожидаемые суммы/группы задаются вручную. Они не вычисляются тем же helper, который проверяют. Проверка валидности ссылки подтверждает переданное значение, но не истинность произвольного предложения модели.

### 7. Офлайн-вход, размеры и проверка реализации

Добавить `--brief-format match-brief-v1|match-brief-v2` только для `lab facts`, по умолчанию v1. Флаг у другой операции либо неизвестное значение дают локальную ошибку. Тонкий адаптер принимает тот же выбор; диагностический повтор normalize/buildBrief использует выбранный путь, а не измеряет v1 под подписью v2.

Будущий пример после реализации:

```powershell
npm.cmd run build
npm.cmd run lab -- facts --match-id 9048979975 --side dire --brief-format match-brief-v2
```

Команда требует снимок в выбранном локальном corpus. Его наличие в live-session само по себе не означает присутствия в corpus; для проверки используется существующий офлайн-import `collect --from-file` в отдельный development-корпус, с checksum/происхождением, без изменения прежних экспериментов. Нет автоматического поиска снимка по чужим каталогам.

Формат и версии видны в manifest/summary/diagnostics. Шесть артефактов, новый каталог на вызов, minified context, manifest последним и запрет перезаписи сохраняются. Markdown показывает новые значения с ID и неполнотой, без добавления локально скрытых подробностей. При overflow нет готового пакета; ошибка содержит bytes/limit, выбранный формат известен из параметров вызова.

Проверки реализации:

- Синтетические тесты для обеих сторон, отсутствия мутаций, повторов, неизвестных данных, нуля, связей и повреждений; golden v1 закрепляется до изменения генератора.
- Регрессии: Dire-смерти по карточкам `[2,2,0,1,2,1]`, Radiant `[1,1,3,3,5,2]`; итоги 8/15 относятся к карточкам, а не всему матчу. Отдельная проверка карточек 0/1/5 предотвращает подмену общих 9 смертей союзными значениями 2/2/1.
- Четыре строения и First Blood дают четыре события строений Wraith King; Aegis не прибавляет строение Rubick. Sven с 11.133545 stuns располагается перед Wraith King с 24.23296; равенства, неполнота и округление проверяются отдельно.
- Offline CLI с запрещённым fetch и пустыми ключами, ошибка формата, checksum, overflow и прерванная запись; проверка сохранения текущего requestDigest v1 и прохождения существующего потребителя без изменения `match-analysis`.
- На четырёх прежних development-снимках и сохранённом 9048979975 сравнить v1/v2: размеры facts/context/evidence, точность контрольных сводок, coverage, prepare/verify timings. Старые файлы не менять; локальные снимки не добавлять в Git. Если файл недоступен, зафиксировать конкретный пробел проверки.

Цель 32768 и предел 65536 UTF-8 bytes остаются разными показателями. Прибавление сводок может привести к overflow на большом снимке: это фиксируется как неуспешная подготовка для него, а не как достигнутая совместимость или повод вырезать данные. Перед будущим подключением потребителя необходим успешный v2 для выбранного эксперимента; проблема размера решается отдельным явным пересмотром профиля. Число байтов и локальные timings не являются замерами токенов, скорости или качества MiMo.

## Risks / Trade-offs

- [Модель продолжает ошибаться вопреки сводкам] → отдельные ссылки и ограничения, затем изменение инструкции и содержательное ревью; эта работа не объявляется калибровкой.
- [Новые сводки выходят за 64 KiB] → явный отказ, измерения на сохранённых данных, отсутствие автоматического fallback и честный список неподготовленных снимков.
- [Логи неполны, дублируются или противоречат друг другу] → счётчики известных записей и ограниченная выборка; missing не ноль, parsed не доказательство полноты.
- [Два формата расходятся при поддержке] → одна нормализация, неизменённый путь v1, отдельные golden и проверка префикса реестра; нет массового рефакторинга соседей.
- [Поле v2 ошибочно передано строгому потребителю v1] → отдельный discriminator и тип, явный выбор; текущие потребители остаются на v1 до отдельной интеграции.

## Migration Plan

1. По отдельному запросу реализовать V2 и офлайн-подготовку, не меняя режимов production и сохранённых пакетов.
2. Выполнить синтетические, совместимые и локальные проверки снимков; документировать размеры/покрытие и реальные ограничения. Доставка на VPS не входит в этот этап.
3. Передать модулю 5 точную схему V2 и результаты. Затем отдельно подготовить его поддержку и сокращённый ответ; перед платным экспериментом сверить неизвестный расход прежнего контроля.
4. Откат использования V2 — убрать явный выбор и продолжить V1. Новые локальные артефакты сохраняются отдельно; миграция SQLite и переписывание prepared/body не требуются.
