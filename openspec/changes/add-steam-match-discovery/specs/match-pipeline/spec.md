# Spec Delta

## MODIFIED Requirements

### Requirement: Ограниченное обнаружение с отчётом о полноте

Опрос SHALL просматривать историю каждого настроенного аккаунта в пределах явных лимитов выбранного источника, объединять match ID и изолировать ошибку одного аккаунта. Достижение лимита, ошибка страницы или невозможность подтвердить кандидата SHALL отражаться в отчёте. Частичный просмотр MUST NOT выдаваться за полное покрытие истории. Закрытые аккаунты SHALL оставаться в списке следующих опросов.

#### Scenario: Частный или недоступный аккаунт
- **WHEN** история одного аккаунта недоступна, а другого содержит подходящий матч с подтверждённой компанией
- **THEN** доступный кандидат обрабатывается, отчёт сохраняет ошибку первого аккаунта

#### Scenario: Глубины просмотра не хватило
- **WHEN** достигнут предел страниц или кандидатов
- **THEN** цикл заканчивается с признаком ограничения; граница активации не сдвигается и фоновая неограниченная загрузка не начинается

#### Scenario: История снова стала доступна
- **WHEN** аккаунт ранее возвращал закрытую историю, а в следующем цикле разрешил её чтение
- **THEN** его история снова проверяется без изменения списка компании и ручного сброса постоянной блокировки

#### Scenario: Все истории закрыты
- **WHEN** выбранный источник не предоставляет историю ни одного настроенного аккаунта
- **THEN** отчёт показывает частичное покрытие и причины, а не успешное отсутствие новых матчей; ручной запуск остаётся доступным

## ADDED Requirements

### Requirement: Явный источник истории и совместимый интервал

Конвейер SHALL явно поддерживать историю Steam и прежнюю историю OpenDota. Без выбора нового источника SHALL сохраняться прежнее поведение. Для выбранного Steam интервал по умолчанию SHALL быть 60 секунд между завершением опроса и следующим циклом. Циклы MUST NOT перекрываться, а выбор источника MUST NOT включать автоматический или платный режим.

#### Scenario: Старая конфигурация
- **WHEN** источник истории не указан
- **THEN** используются OpenDota и прежний интервал по умолчанию без требования Steam-ключа

#### Scenario: Минутный опрос Steam
- **WHEN** автоматическое обнаружение явно запущено с источником Steam без собственного интервала
- **THEN** следующий цикл начинается после завершения предыдущего и паузы 60 секунд; точное время появления матча не обещается

#### Scenario: Ручная работа без Steam
- **WHEN** выполняется только ручной запрос по ID, а зависимость Steam не передана
- **THEN** он использует существующий путь OpenDota без требования истории Steam

### Requirement: История Steam предоставляет только кандидата

Матч из Steam SHALL сохраняться как кандидат до подтверждения свежими данными OpenDota. Отсутствие в истории длительности, исхода или режима MUST NOT отклонять кандидата и MUST NOT заменяться фиктивными значениями. Временную границу SHALL определять фактическое завершение из OpenDota, а не время начала или первого обнаружения.

#### Scenario: Игра началась до включения
- **WHEN** время начала кандидата раньше постоянной границы, а подтверждённое завершение позже неё
- **THEN** кандидат не исключается только по времени начала и допускается при выполнении остальных условий

#### Scenario: Старый матч в новой истории
- **WHEN** Steam впервые вернул ID после включения, но OpenDota подтвердил завершение до или ровно в момент границы
- **THEN** кандидат помечается пропущенным без разбора реплея, анализа или публикации

### Requirement: Сторона подтверждается независимо от доступности истории

Кандидат SHALL допускаться автоматически только по прежним правилам завершённого рейтингового матча и минимум двух разных ID компании на одной стороне свежего OpenDota. Закрытая история одного участника MUST NOT исключать его узнаваемый ID из проверки состава. История одного друга MUST NOT подменять отсутствующий ID второго.

#### Scenario: Одна доступная история на пару
- **WHEN** Steam вернул матч через одного друга, а OpenDota подтверждает его и второго друга с закрытой историей на одной стороне
- **THEN** создаётся одна общая задача для всех пяти союзников

#### Scenario: Второй друг анонимен
- **WHEN** в свежем составе узнаваем только один ID компании
- **THEN** автоматический анализ не запускается, кандидат получает причину неподтверждённого состава; ручной путь с прежними правилами остаётся доступен

#### Scenario: Компания на обеих сторонах
- **WHEN** минимум два ID компании подтверждены на каждой стороне
- **THEN** кандидат требует выбора стороны и не создаёт два автоматических анализа

### Requirement: Постоянное ожидание запаздывающих данных

Отсутствие матча в OpenDota, временная ошибка или ещё неизвестное завершение SHALL оставлять кандидата ожидающим с сохранённым сроком следующей проверки. Ожидание SHALL иметь конечный срок от первого обнаружения и переживать перезапуск без продления. До подтверждения MUST NOT выполняться POST разбора, платный анализ или публикация.

#### Scenario: Steam опередил OpenDota
- **WHEN** история уже содержит ID, а OpenDota ещё возвращает отсутствие матча
- **THEN** кандидат сохраняется для следующей проверки, а не теряется и не становится неудачным платным анализом

#### Scenario: Кандидат исчез из последних страниц
- **WHEN** ещё ожидающий кандидат больше не попадает в ограниченный просмотр Steam
- **THEN** его сохранённая проверка OpenDota продолжается в пределах первоначального срока

#### Scenario: Ожидание истекло
- **WHEN** данные не подтвердились до установленного срока
- **THEN** кандидат получает статус необходимости проверки с причиной истечения срока; автоматические GET по нему прекращаются

### Requirement: Ограничение нагрузки подтверждения

Повторный опрос истории MUST NOT заново запускать подтверждение окончательно обработанных кандидатов того же контекста. Проверки ожидающих кандидатов SHALL учитывать срок запуска, общий лимит OpenDota и конечный предел проверок за цикл. Новые ID MUST NOT постоянно вытеснять ранее ожидающие; исчерпание лимита SHALL отражаться в отчёте.

#### Scenario: Один ID от нескольких аккаунтов
- **WHEN** несколько историй и страниц содержат один match ID
- **THEN** он имеет одну запись кандидата в текущем контексте и не вызывает отдельный GET подробностей для каждого аккаунта

#### Scenario: Минутный повтор истории
- **WHEN** завершённое решение по кандидату уже сохранено
- **THEN** очередное появление того же ID не вызывает новый GET OpenDota или новую задачу

#### Scenario: Лимит подтверждения исчерпан
- **WHEN** в цикле больше ожидающих кандидатов, чем разрешено проверить
- **THEN** остальные сохраняются для следующих циклов, а отчёт явно показывает отложенные проверки

#### Scenario: История первых аккаунтов занимает предел
- **WHEN** первые аккаунты снова возвращают уже известные ID, а у следующих аккаунтов есть новые матчи
- **THEN** известные ID не расходуют предел новых кандидатов и не мешают принять отложенные новые ID в следующих циклах

### Requirement: Обычный запрос по ID не дублирует обнаружение

Обычный запрос SHALL прежде всего переиспользовать доступные задачу и результат по матчу и стороне. Если соответствующей задачи и результата нет, но кандидат текущих настроек ожидает данные, SHALL возвращаться состояние ожидания с ID матча и безопасной причиной. Такое чтение MUST NOT запускать второй поиск истории или платный анализ.

#### Scenario: Запрос во время ожидания данных
- **WHEN** пользователь запрашивает ID ожидающего кандидата без готовой задачи
- **THEN** получает состояние ожидания данных OpenDota без выдуманного job ID или отчёта

#### Scenario: Ручная задача уже создана
- **WHEN** до подтверждения автоматического кандидата тот же матч и сторона уже поставлены вручную
- **THEN** после подтверждения используется прежняя задача; сохраняется доступный результат и новая платная попытка не создаётся
