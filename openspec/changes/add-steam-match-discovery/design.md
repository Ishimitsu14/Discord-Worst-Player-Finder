# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md). Ниже отделены существующий код, проверенный протокол и предлагаемые изменения.

### Текущий проект

- `src/match-pipeline/pipeline.ts` получает историю через `deps.opendota.getPlayerMatches`. Перед GET подробностей применяются `supported(row)` и `endAt(row)`: существующий `PlayerMatch` включает длительность, исход, режим и слот.
- Steam не возвращает этот DTO. Подставлять нулевую длительность или фиктивную победу нельзя: это изменит допуск и временную границу.
- `discoverOnce` уже изолирует ошибки аккаунтов, объединяет ID и имеет один цикл обнаружения независимо от единственного обработчика задач. `classify` подтверждает два разных ID по свежему составу OpenDota. Эти правила сохраняются.
- `storage.recordMatch` хранит только первое/последнее наблюдение. Таблица `jobs` требует сторону, а `enqueueInitial` постоянно устраняет повторы по матчу и стороне. Для неизвестного состава пока нет постоянного ожидания до постановки задачи.
- `src/storage/database.ts` принимает схему 1 и проверяет точный checksum. Новая таблица требует отдельной миграции, а не изменения исходной строки schema задним числом.
- Operations читает секреты из окружения в CLI и передаёт их библиотекам. По умолчанию `automatic=false`, `mode=prepare-only`. `automaticSince` находится в `operations-state.json` и сохраняется при смене источника.
- Discord уже выдаёт задачу, последний принятый результат и ссылку на сообщение. Пока у результата постановки нет отдельного варианта ожидания данных без job ID.

### Проверенные внешние сведения

В этой сессии 17 октября 2026 выполнены GET к `https://api.steampowered.com/IDOTA2Match_570/GetMatchHistory/v1/` с `account_id` и `matches_requested=5`. Ключ, URL с ключом и сырые ошибки не сохранялись в проекте.

| Аккаунт | Наблюдение |
|---|---|
| `98341323` | HTTP 200, API status=1, пять записей, total_results=500, results_remaining=495; первые ID `9048979975`, `9048915444` |
| `122376567` | HTTP 200, API status=15; отдельная повторная GET-проверка подтвердила отказ в доступе к истории |

Это проверка одного доступного и одного недоступного аккаунта. Она не доказывает задержку индексации, полноту всех матчей, пагинацию, работу с VPS или обход приватности.

[Условия Steam Web API](https://steamcommunity.com/dev/apiterms) устанавливают общий суточный предел 100 000 вызовов. [Обзор Valve](https://partner.steamgames.com/doc/webapi_overview) описывает публичный API-хост и параметры запросов. Это не гарантия конкретного минутного лимита или отсутствия кеширования. Предлагаемые ниже ограничения клиента — наши, а не новые утверждения о квотах Valve.

## Goals / Non-Goals

**Goals:**

- Переиспользовать очередь, классификатор и путь ручного анализа, отделив историю от подробностей матча.
- Сохранить минутный опрос всего списка и ограничить дополнительную нагрузку подтверждения на OpenDota.
- Переживать появление матча в Steam раньше OpenDota, перезапуск и повторные наблюдения.
- Дать проверяемые границы совместимости и миграции до реализации.

**Non-Goals:**

- Универсальный реестр провайдеров, распределённые workers и новый сервис.
- Изменение аналитика, существующих запросов к модели, формата отчёта и прав команд.
- Гарантия обнаружения игры, если все её участники скрывают историю, или полного catch-up после произвольного простоя.
- Автоматическое включение Steam на VPS, смена постоянной границы или новая платная генерация.

## Decisions

### 1. Небольшой отдельный клиент истории

Новый модуль `src/steam/` следует устройству `src/opendota/`: публичный index, типы, валидация, клиент и внутренний HTTP. Имена внутренних файлов определяются при реализации по минимальному необходимому объёму, без новой транспортной библиотеки.

Предлагаемый публичный контракт:

- `SteamHistoryClient({ apiKey }, { fetcher?, clock?, random? })`;
- `getMatchHistory(accountId, { limit=20, startAtMatchId?, signal? })`;
- страница `{ matches: [{ matchId, startTime }], nextStartAtMatchId: number | null }`;
- `SteamHistoryError` с безопасными `code`, `operation`, опциональными `httpStatus`, `apiStatus`, `retryAt`.

ID аккаунта проверяется как Steam32 1..4294967294, размер страницы 1..100, match ID как положительный safe integer, startTime как неотрицательный safe integer в секундах. Большой uint64 отклоняется, а не округляется. Ответ не преобразуется в существующий OpenDota `PlayerMatch`.

Запрос идёт только на фиксированный публичный HTTPS-хост по указанному пути. `apiKey` попадает в параметр `key` внутри транспорта, а не в возвращаемые DTO; redirects запрещены. `result.status=15` даёт `history-private`; иные неуспешные API-статусы — `api-error`. HTTP-ошибки различаются отдельно. Сырые сообщения Steam и сетевые исключения не становятся публичным cause.

Для успешной страницы проверяются массив, ID/время и согласованность num_results/total_results/results_remaining. При наличии продолжения следующий startAtMatchId равен минимальному ID страницы минус один. Пустая страница с объявленным продолжением и непродвижение отклоняются. Порядок и дополнительные поля не заменяют проверки; чужие поля не включаются в компактный DTO.

Предлагаемые пределы: 10 секунд на HTTP-попытку с чтением тела, не более двух повторов GET после временных сбоев с задержками 1 и 2 секунды плюс существующий стиль jitter 0..250 мс; до 60 отправок в скользящую минуту на один клиент, включая повторы. HTTP 429 даёт общий cooldown по Retry-After, fallback 60 секунд. HTTP 401/403, status=15 и некорректная страница внутри операции не повторяются. Отмена очищает ожидания. Ключ хранится в закрытом поле и проверяется на отражение в ответе.

Альтернатива — расширить OpenDotaClient вызовами другого хоста. Она смешивает учёт двух квот и обработку разных протоколов; отдельный маленький клиент сохраняет границы проекта.

### 2. Явный выбор без скрытого fallback

В `PipelineOptions` добавляется `historySource?: 'opendota' | 'steam'`, в зависимости — необязательный порт чтения Steam. Без выбора действует прежний OpenDota; переданный ключ не выбирает источник автоматически. Для Steam pollIntervalMs по умолчанию 60000, для прежнего пути остаётся 900000. Явно заданный интервал имеет приоритет, минимум остаётся 60000.

Создание конвейера остаётся инертным. Перед запуском обнаружения Steam проверяется наличие нужной зависимости; обычный ручной запрос не требует её. Одновременно работают прежние один discovery loop и один worker. После окончания цикла применяется пауза: это не обещание обнаружения строго через 60 секунд после окончания игры.

Все ID из GroupSettings опрашиваются в исходном порядке и остаются в следующих циклах, включая закрытые. Частный отказ останавливает только страницы этого аккаунта. При глобальной ошибке авторизации либо общем cooldown последующие сетевые отправки прекращаются; отчёт отмечает непроверенные аккаунты, а не объявляет их приватными. Автоматического fallback на OpenDota-историю или STRATZ нет.

Пагинация Steam использует startAtMatchId, прежний путь сохраняет offset. `pageSize=20`, `maxPagesPerAccount=1` и `maxCandidatesPerScan=100` переиспользуются. В Steam-пути последний предел относится к новым уникальным записям кандидатов за цикл: уже известные журналу ID его не расходуют. Поэтому первые аккаунты со старой историей не занимают весь предел навсегда; в следующем цикле можно принять отложенные ID следующих аккаунтов. Истории остальных аккаунтов продолжают проверяться в пределах общего лимита Steam, даже когда новые ID откладываются. При достижении предела возвращается partial; отсутствие кандидата за пределом просмотренных страниц не считается доказанным отсутствием матча.

### 3. Постоянный журнал до определения стороны

Добавляется одна таблица `discovery_candidates` в ту же SQLite. Это не вторая очередь анализа. Контекст — digest канонических GroupSettings и automaticSince; секреты в digest и таблицу не входят. Ключ записи — `(context_key, match_id)`.

Минимальные поля: contextKey, matchId, firstSeenAt, lastSeenAt, expiresAt, state, nextCheckAt и reason. Состояния: `pending`, `admitted`, `ignored`, `needs-attention`. Метки времени локального журнала — Unix ms. expiresAt сохраняется один раз как firstSeenAt + discoveryTimeoutMs с проверкой безопасного целого. Повтор истории, смена значения по умолчанию и перезапуск не продлевают этот срок; изменённый параметр применяется к новым кандидатам.

Storage предоставляет операции наблюдения/чтения, выборки due-кандидатов и сохранения решения. Наблюдение не меняет state, reason или nextCheckAt уже существующей записи. Подтверждённые изменения транзакционны; попытки модели, результаты и артефакты прежних задач не затрагиваются.

После допуска сначала выполняется прежний `enqueueInitial`, затем пометка `admitted`. Если процесс упал между шагами, повторная проверка находит существующую задачу; постоянная дедупликация делает повтор безопасным без новой общей транзакции между модулями. Ручная задача той же стороны тоже переиспользуется.

Альтернатива — память процесса или повторный полный GET подробностей каждой записи истории. Первая теряет ожидание при рестарте, вторая возвращает нагрузку на OpenDota и расходует квоту на старые матчи. Журнал хранит только состояние обнаружения; полные данные сохраняются существующей задачей после допуска.

### 4. Ограниченное подтверждение OpenDota

Каждый цикл сначала записывает обнаруженные ID, затем проверяет due-кандидатов текущего контекста. В Steam-пути нельзя применять supported/endAt к краткой записи истории. Начало до automaticSince не является отрицательным решением: игра могла завершиться после включения.

Предлагаемые дополнительные параметры конвейера:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| discoveryRetryMs | 60000 | Пауза между проверками ещё не готовых данных, safe integer >=60000 |
| discoveryTimeoutMs | 1800000 | Предельное ожидание от первого обнаружения, safe integer >=discoveryRetryMs |
| maxDiscoveryChecksPerScan | 10 | Конечный предел кандидатов, проверяемых за один цикл, целое 1..1000; независим от предела новых наблюдений |

Due-кандидаты выбираются по nextCheckAt, firstSeenAt и matchId; новые наблюдения не продвигают их вперёд. За цикл — до maxDiscoveryChecksPerScan вызовов подтверждения; внутренние повторы GET дополнительно учитывает прежний ограничитель OpenDota. POST разбора продолжает расходовать прежний взвешенный бюджет. При cooldown сохраняется nextCheckAt не раньше retryAt; фиксированное число проверок не отменяет лимиты клиента.

Решение после свежего getMatch:

| Наблюдение | Решение |
|---|---|
| 404, временный сбой, нулевая длительность/неизвестный исход либо пока неполная пятёрка | pending до следующей проверки, без внешних POST |
| Истёк срок ожидания | needs-attention / discovery-timeout; дальнейшие автоматические GET прекращаются |
| Некорректный ответ или постоянная ошибка источника | needs-attention с безопасной причиной |
| Завершение <=automaticSince или неподдерживаемый режим | ignored; не проверять заново в этом контексте |
| Меньше двух узнаваемых друзей, конфликт ID или две подходящие стороны | needs-attention, без догадок о приватных игроках |
| Подходящий матч и единственная сторона с двумя разными ID | enqueueInitial либо прежняя задача, затем admitted |

Для incomplete-allies исключение относится к пока неполному составу; дубликаты или некорректные слоты не исправляются предположением. firstSeenAt не выдаётся за время завершения. После постановки worker снова применяет прежние проверки пригодности перед внешними действиями.

Обработанные кандидаты не получают новый getMatch при каждом опросе Steam. Ожидающие переживают выпадение из последних страниц. Изменение списка друзей создаёт иной контекст и позволяет новую проверку; существующие jobs остаются общими по match ID и стороне. Отдельный вечный cursor/high-watermark не нужен: поздно появившийся ID в пределах страниц не теряется из-за меньшего числового ID.

### 5. Наблюдаемые ответы и диагностика

DiscoveryReport сохраняет прежние поля и дополняется безопасными счётчиками ожидающих/отложенных кандидатов. `partial=true` сопровождает ошибки аккаунтов, пределы страниц/кандидатов/проверок и непроверенное подтверждение. Коды различают `steam-history-private`, авторизацию, rate limit и ожидание OpenDota. Operations передаёт только настроенный accountId, код источника и агрегаты, без raw URL, тел и ключей. Схема heartbeat не обязана меняться; ready не означает полное покрытие.

Для `requestMatch` добавляется вариант результата `awaiting-data` с matchId, безопасной причиной и nextCheckAt либо null. Сначала учитываются существующие задачи/последний valid-результат; когда сторона не задана и существуют обе стороны, сохраняется прежняя необходимость её выбора. Только при отсутствии задачи/результата читается кандидат текущего контекста.

Для pending с неистёкшим deadline ответ читается из журнала без нового поиска истории и без платного запроса. После needs-attention обычный ручной запрос вправе один раз пройти прежнюю свежую проверку OpenDota; если данные всё ещё недоступны, ответ отражает прекращённое автоматическое ожидание. Ручной путь не снимает budget/experimental-проверки и не становится скрытой командой повторного анализа.

В `src/discord-interface/interface.ts` новый вариант обрабатывается до существующей ветки без job. Достаточно приватного текста: «Матч найден. Ожидаем данные OpenDota». nextCheckAt — время попытки, а не ETA готовности. `/worst-status` по job ID, renderer готового отчёта и права `/worst-reanalyze` сохраняются.

### 6. Передача конфигурации

`pipeline.historySource` и три параметра подтверждения проходят ту же закрытую валидацию конфигурации, что и остальные PipelineOptions. `ServiceSecrets` получает `steamKey`; только CLI читает `STEAM_API_KEY`. Библиотеки не читают env. В автоматическом Steam-режиме ключ проверяется до активации automaticSince и Gateway; в ручном режиме его отсутствие не мешает работе.

Runtime создаёт SteamHistoryClient при необходимости и передаёт общий fetcher/clock для тестов, отдельный ограничитель Steam и существующий OpenDotaClient. `.env.example` получает пустое имя переменной. Пример сервиса указывает historySource=steam и pollIntervalMs=60000, сохраняя automatic=false/prepare-only. Само изменение примера не меняет установленный конфиг VPS.

Документация отдельно показывает безопасное сохранение ключа на Windows и явную передачу в окружение нового процесса; пользовательская переменная Windows, добавленная после запуска терминала, не гарантирует обновления process.env. Для Linux используется существующий приватный service.env, без копирования ключа из Windows этим изменением.

## Risks / Trade-offs

- [Закрыты все истории участников матча] → Нет обещания автообнаружения; ручной ID остаётся доступен. Узнаваемые ID закрытых аккаунтов не исключаются из состава.
- [Steam видит ID раньше статистического сервиса] → Постоянный pending с ограниченным сроком; до подтверждения нет разбора или анализа.
- [OpenDota скрывает ID второго друга] → Сохранить причину неподтверждённой компании; не считать анонимного игрока другом по косвенным данным.
- [Много старых ID при первом включении] → Проверить их ограниченными порциями и сохранить окончательные решения; не фильтровать по времени начала вместо завершения.
- [Новая схема SQLite] → Миграция с неизменным checksum версии 1, тесты старых задач и cold backup до первого открытия новым кодом. Старый релиз после этого не обещает открыть БД.
- [Ограниченные страницы и простой] → partial и документированный предел catch-up. Ручной ID дополняет обнаружение, но полное покрытие не обещается.
- [Квоты разделяются с другими приложениями] → Наш limiter не является глобальным счётчиком ключа; соблюдать 429 и не объявлять 100 000 гарантированным доступным остатком.
- [Небольшой предел подтверждений] → Возможна дополнительная очередь перед OpenDota; due-порядок предотвращает постоянное вытеснение старых кандидатов новыми.

## Migration Plan

1. Реализовать и проверить модуль с подменёнными HTTP/часами, включая текущие успешный и закрытый ответы как синтетические фикстуры без ключа. На Windows/Linux проверить источник и миграцию без реальных API.
2. Добавить следующую миграцию SQLite (на текущем базисе 1→2): сохранить прежний schema checksum, существующие таблицы/данные и добавить discovery_candidates в одной транзакции с новой записью migrations. Ошибка оставляет прежнюю схему; более новый формат по-прежнему отклоняется.
3. До будущей доставки остановить старый сервис и сделать существующим старым релизом cold backup app.sqlite вместе с operations-state.json. Не открывать БД новым бинарным кодом до этого backup: его открытие может выполнить миграцию. Прежний конфиг на этом шаге ещё не содержит неизвестных старому релизу полей.
4. Проверить новый релиз с явно подготовленной конфигурацией без включения automatic/live. Смена источника не меняет сохранённый automaticSince. Перенос ключа и включение автоматического режима выполняются отдельным операционным действием.
5. Для будущего smoke достаточно одного ограниченного чтения Steam и проверки диагностики/prepare-only на тестовой установке. Не использовать production для создания тестовых задач, сообщений или платных генераций.
6. При откате остановить процесс и сохранить текущее состояние отдельно. Старый релиз запускать с совместимыми конфигом и БД из backup, не удаляя новую БД. Откат рабочей БД может убрать события после backup и потому не является автоматическим исправлением.

Этот запрос создаёт только planning-артефакты. Миграция, runtime, smoke и доставка ещё не выполнялись. Непроверенные эксплуатационные свойства перечислены выше; блокирующих продуктовых решений для начала реализации не осталось.
