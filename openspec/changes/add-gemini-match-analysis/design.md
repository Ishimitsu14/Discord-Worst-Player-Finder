# Design

## Context

См. [proposal.md](proposal.md), [требования](specs/gemini-match-analysis/spec.md) и [входной профиль](../add-gemini-compact-facts/design.md). Текущий аналитик, storage и Discord работают с `match-analysis-v1`: обязательны оценки пятерых, comparison, один/два выбранных и ближайшая альтернатива. Новый короткий ответ не соответствует этому контракту. `operations/config.ts` выбирает прежний пакет; одного добавления файлов промпта для переключения недостаточно.

В лаборатории уже есть потоковые эксперименты и обработка ошибок OpenRouter. Их можно использовать как проверенный образец транспорта, но production-модуль не должен импортировать локальные экспериментальные файлы. Новая реализация остаётся внутри `src/match-analysis/` с явным публичным входом.

## Goals / Non-Goals

**Goals:** один проверяемый короткий ответ выбранного Gemini-профиля, ссылки на игровые факты, воспроизводимый запрос и точная атрибуция цитаты.

**Non-Goals:** менять классификацию матчей, автоматически подключать новый формат к SQLite/Discord/VPS, объявлять калибровку завершённой либо доказывать причинность по структурно корректному ответу.

## Decisions

### 1. Отдельный пакет и API

Добавить `analysis/prompts/gemini-v1/` и отдельные публичные операции `createGeminiPromptPackage`, `prepareGeminiAnalysis`, `analyzeGeminiMatch`, `validateGeminiAnalysis`. Общие безопасные средства HTTP, digest и учёта попыток можно переиспользовать внутри модуля. Старые входы и идентичности запросов не меняются.

Пакет имеет id `gemini-match-v1`, вход `gemini-compact-v1`, ответ `gemini-match-analysis-v1`, calibration `experimental`. Manifest пакета фиксирует профиль, инструкцию и схему. Подготовка проверяет compact bundle, matchId/side, пять уникальных кандидатов, dictionary/context/package digest; request digest относится к точному передаваемому телу. Steam32 ID для выбора стороны не передаются модели.

Альтернатива — дополнить старый результат выдуманными assessment/comparison — отклонена: потребители получили бы фиктивные сведения ради совместимости схемы.

### 2. Короткий контракт ответа

Новый объект содержит только следующие поля:

| Поле | Ограничения |
|---|---|
| version / format | `1` / `gemini-match-analysis-v1` |
| selectedPlayerSlot | ровно один слот из пяти кандидатов |
| nomination | русское ироничное звание, 1–100 символов |
| facts | 3–4 объекта `{claim,evidenceIds}`; claim 1–240 символов, 1–6 уникальных игровых ID |
| quoteId | ID переданной реплики выбранного игрока либо null |
| verdict | один русский панчлайн, 1–400 символов |
| confidence | low / medium / high |
| limitations | до двух непустых строк по 160 символов |

Дополнительные поля запрещены. Идентификация идёт по слоту; ник, герой, текст и время цитаты берутся из проверенного контекста. Модель не возвращает переписанную «дословную» цитату. При `truncated=true` интерфейс обязан показать сокращение. Текст verdict обыгрывает цитату, но не заменяет её исходный текст.

Локальная схема проверяет все ограничения независимо от возможностей endpoint. В upstream response_format передаётся поддерживаемая структурированная схема без превращения неподдерживаемого ограничения в обещание API. Строковые лимиты считаются единым способом в package/validator; JSON Schema использует стандартный подсчёт Unicode code points. Запреты на игровые выдумки и качество шутки дополнительно оцениваются человеком.

### 3. Инструкция из документа пользователя

Основа — присланные правила Gemini; «проигравшая команда» заменяется на переданную нашу сторону. В prompt закрепляются один худший, номинация, 3–4 факта, финальный панчлайн, temperature 0.65 и русский сарказм с допустимым матом. Это продуктовая эвристика, а не установленные нормативы Dota.

Правило саппортов переносится буквально по смыслу: плохой KDA сам по себе недостаточен; выбор Pos 4/5 требует одновременно нулевого вижен-вклада, нулевого урона, подтверждённого AFK-леса и KP<25%. В текущем компактном входе AFK-лес не измеряется. Следовательно, это условие остаётся unknown, а не выполняется по GPM, покупкам или чату. Ограничение осознанно сужает выбор саппортов; снять его можно отдельным согласованным изменением.

Для коров перечисляются сравнение net worth с противником и его саппортами, нулевой tower_damage и покупки Blink/BKB после 20 минут. Для героев — LC: меньше 150 Duel Damage после 30 минут, отсутствие подтверждённой защиты керри против контроля и слабые denies мидера. Число дуэлей не восстанавливается из бонусного урона. Пример 100 урона к 40-й минуте и 10 denies — ориентиры из документа, не самостоятельное доказательство руина. Unknown роли, предмета или контроли не заменяется выдуманным фактом.

Состав противника доступен как контекст. Если наличие BKB не доказано или неизвестно применение предмета, модель не утверждает «не купил»/«не нажал». Низкий benchmark не превращается в доказательство AFK. При неоднозначности выбирается один кандидат с низкой уверенностью и оговорками.

### 4. Чат и проверка ссылок

Системная инструкция и данные передаются раздельно. JSON содержит отдельные игровые и chat-группы. Ники, сообщения и их ссылки объявляются недоверенными данными; встроенные просьбы сменить кандидата или проигнорировать правила не исполняются. Инструментов у запроса нет.

`facts[].evidenceIds` допускает только переданные игровые группы match/player/items/benchmarks/special/opponent с доступными показателями. Недостаточно сослаться только на ник или unavailable. Ссылка может подтверждать сведения о сопернике, необходимые для сравнения. Chat-ID запрещён в игровых основаниях.

`quoteId` проверяется отдельно: существует в текущем отправленном контексте, имеет тип chat, автор равен selectedPlayerSlot. При подходящем собственном флейме инструкция требует обыграть реплику; иначе quoteId=null и roast опирается на игру. Чужие обвинения не считаются игровыми доказательствами. Ни семантическое отсутствие флейма, ни причинность машинным валидатором не доказываются.

Выбран один вызов с обеими секциями, как в предложении пользователя. Два последовательных LLM-вызова могли бы отделить выбор от текста, но увеличили бы стоимость и задержку и не соответствуют выбранной схеме. Ограничение ссылок проверяет основания, но не гарантирует независимость скрытого выбора модели от чата.

### 5. Параметры и жизненный цикл попытки

Предлагаемые настройки профиля: `google/gemini-3.8-flash`, standard `google-ai-studio`, без fallback, temperature 0.65, reasoning `{effort:"low",exclude:true}`, `stream:true`, `stream_options.include_usage:true`, max_tokens 2048, timeout 180000 ms, maxRequestBytes 32768. Это начальные параметры эксперимента, не результат калибровки. Полный запрос дополнительно ограничен по размеру; переполнение не исправляется удалением кандидатов или скрытой обрезкой.

При подготовке проверяются актуальные metadata выбранного endpoint: модель, параметры, structured output, лимиты и тарифы. Предложенные параметры сверены с [каталогом OpenRouter](https://openrouter.ai/api/v1/models/google/gemini-3.8-flash/endpoints) 17 октября 2026; preflight обязан повторить проверку, поскольку каталог меняется. Нет endpoint/тарифа/поддержки — нет POST. Ключ передаётся вызывающим кодом, не хранится в пакете.

Существующий предохранитель beforeSend должен записать started и проверить заданный вызывающим кодом предел оценочной стоимости до отправки. Ровно один POST, без SDK retry, fallback, исправляющего запроса и отдельного roast. Полученный content разбирается только после подтверждённого окончания SSE; таймаут, незавершённый поток или invalid JSON не дают пригодного результата.

Сохраняются безопасные HTTP-код/класс ошибки, доступные generation ID, finish reason, usage и cost, включая отклонённый ответ. Идентификатор из заголовка/ошибки не теряется из-за раннего HTTP return. При отсутствии подтверждённого расхода — unknown, не 0. Частичный текст помечается как непригодный. Токен, сырые заголовки и reasoning не публикуются. Измеряются время первого фрагмента и полное время; 1.5–2 секунды из исходного документа — неподтверждённая цель.

[OpenRouter Streaming](https://openrouter.ai/docs/api_reference/streaming) описывает финальный usage-кадр Chat Completions с пустым delta и повторным finish_reason. Парсер допускает такой повтор только при наличии usage и неизменном finish. Новый текст, конфликт finish и отсутствие DONE по-прежнему отклоняются. Исходные попытки не переписываются после исправления; локальный replay явно отделяется от реального потока.

### 6. Границы подключения

| Потребитель | Контракт следующего подключения |
|---|---|
| match-facts, модуль 4 | зависимый `prepareCompactMatchFacts`, отдельный manifest и проверка ссылок |
| evaluation-lab, модуль 8 | явный выбор нового пакета/входа и сохранение короткого результата через существующий журнал; тест транспорта без платных запросов |
| match-pipeline, модуль 3 | сохранить auto min 2 Steam32 на одной стороне и manual min 1 на одной стороне; прежняя явная сторона и обработка неоднозначности сохраняются; новый facts/analysis выбирается явно |
| storage, модуль 7 | добавить поддержку нового формата/его валидатора и неизменяемой идентичности; не подделывать старый объект |
| Discord, модуль 6 | отобразить ник/героя, номинацию, 3–4 основания, собственную цитату с временем, панчлайн, исход и ссылку; сохранить экранирование и отключённые mentions |
| operations, модуль 9 | явно выбрать совместимый пакет и материалы в конфигурации вместо жёсткого старого v1 |

В этом изменении реализуются аналитик и минимальный явный лабораторный адаптер; поддержка остальных потребителей — отдельный этап. Закрытие задач этого изменения не означает готовый бот с новым форматом.

### Уточнение подачи после первого прогона

`analysis/prompts/gemini-v2/` сохраняет вход и параметры v1, но задаёт ответ `version: 2`, `format: gemini-match-analysis-v2`, более едкий roast (2–3 связанных предложения, до 700 символов) и обязательный `teamFacts`: ровно три различных `{claim,evidenceIds}` с прежними пределами claim/ссылок. Это шуточные командные объяснения поражения, а после победы — слабые места. Они рассматривают всю пятёрку, не повторяют трижды приговор выбранному игроку и не используют чат как доказательство. Числа остаются исходными; категоричные игровые интерпретации допустимы без постоянных оговорок.

Панчлайн строится на предметных метафорах и собственной реплике; мат допустим, но не заменяет шутку. После реального v2 пользователь одобрил гиперболы и вольные игровые объяснения: отсутствие логов не запрещает шутку «не коснулся вышек» по нулевому урону. Постоянные оговорки не нужны, limitations может быть пустым. Числовая основа, авторство цитат, правила выбора и защиты саппортов сохраняются. Семантические замечания ревью больше не являются блокером только из-за недостаточной доказательности шутки.

В текущей инструкции явно записать выходные литералы `version=2`, `format=gemini-match-analysis-v2` и отличие от входного `gemini-compact-v1`. Схема/валидатор остаются строгими: неверный format не исправляется автоматически. Изменение инструкции даёт новый package/request digest без смены контракта; замороженные пакеты, реальные попытки и прежнее ревью не переписываются. Новый отзыв пользователя хранится отдельно от первоначального ревью.

Локальный валидатор поддерживает обе закрытые схемы; транспорт дополнительно связывает версию ответа с подготовленным пакетом. Загрузчик принимает только два известных точных профиля/схемы. Старый пакет и точные тела запросов v1 не меняются. Лабораторная подготовка по умолчанию выбирает v2, а исторические планы используют свои замороженные пакеты. Для результата v2 лаборатория сохраняет также Markdown-превью: номинация, игровые основания, собственная цитата, roast, оговорки/ссылка и в самом конце три пункта с заголовком «Почему проебали» или «Где накосячили, несмотря на победу». Отдельного LLM-запроса нет; Discord/runtime этим уточнением не подключаются.

## Risks / Trade-offs

### Сверка management API перед ограниченным повтором

Каждый новый Gemini POST получает заголовок `x-session-id=attemptId`, уже уникальный в журнале лаборатории. Точное тело и digest прежних запросов не меняются. Это метка корреляции, не ключ идемпотентности. `GeminiAttempt` фиксирует получение HTTP-ответа отдельно от первого content.

Отдельный `checkGeminiRecovery` принимает только сетевой сбой/таймаут без HTTP-ответа, content/ID/usage. Проверки Analytics выполняются через 10/30/60 секунд от завершения попытки, по точной session_id, с меняющимся концом UTC-окна. Ошибки, чужая session, старый cachedAt, усечение и некорректная структура запрещают повтор. Найденный ID останавливает проверки; GET generation уточняет стоимость, но его ошибка не разрешает генерацию.

При трёх пустых проверках лаборатория под существующим active.lock сохраняет решение и положительный резерв в размере консервативной оценки первой попытки, затем создаёт одну новую попытку с новым ID. Перед новым POST выполняются штатные свежий preflight, бюджет и started. После сбоя второй попытки дальнейших повторов нет. Исходные файлы не переписываются; подтверждённая management-стоимость или резерв учитываются будущими запусками по связанной sidecar-записи. Отмена и авария сохраняют существующее fail-closed поведение журнала/lock.

CLI передаёт отдельный `OPENROUTER_MANAGEMENT_KEY` только клиенту сверки; inference endpoint получает только обычный API key. Без management key сохраняется один POST. Старые сохранённые попытки без нового признака получения ответа не повторяются автоматически. Подключение к production runtime остаётся отдельным этапом.

Analytics может запаздывать без документированного предела: три пустые проверки уменьшают риск, но не гарантируют отсутствие дубликата. Поэтому сохраняются максимум один повтор и резерв на обе потенциально оплаченные попытки. В этой задаче достаточно синтетических транспортных тестов; платные API-вызовы не нужны.

- [Ошибка выбора при корректных ссылках] → ручная оценка на реальных матчах, отдельные выводы о валидности и содержательном качестве.
- [Недоступность роли/AFK/механики] → unknown, запрет подмены отсутствия нулём; ограничение правила саппортов явно принято.
- [Влияние чата на скрытый выбор] → разделение секций, проверка типов ссылок и эксперимент с изменённым чатом; полная независимость не обещается.
- [Слабый roast или шаблонность] → ревью текста и сохранённые реальные ответы; схема сама по себе не подтверждает юмор.
- [Смена API или неизвестный расход] → свежий preflight, журнал, один POST, отсутствие автоповторов.

## Migration Plan

Сначала завершить отдельное изменение compact facts. Затем добавить пакет/валидатор и транспорт с офлайн-проверками; старые golden-запросы и результаты остаются прежними. Подготовить явный лабораторный запуск с новым форматом и проверить реальные ответы отдельным согласованным экспериментом. Перед runtime провести отдельное подключение storage/pipeline/Discord/operations. Откат — выбор прежнего пакета; исторические артефакты не переписываются.

Для контрольных данных использовать сохранённый снимок 9048915444 либо явно синтетический fixture; иллюстративный JSON из присланного документа не считать точной статистикой этого матча. Проверки включают победу нашей стороны, неизвестные поля и роли, собственный/чужой/поддельный quote ID, 3 и 4 основания, prompt injection, HTTP 400, SSE-обрыв и известный/неизвестный расход. Платные прогоны и смена VPS не входят в подготовку этой спеки.
