# Design

## Context

В проекте есть только план, OpenSpec-документы и локальные настройки инструментов. `src/`, `package.json`, общая сборка и реализованные модули отсутствуют. Мотивация и границы находятся в [proposal.md](proposal.md), наблюдаемое поведение — в [spec.md](specs/group-settings/spec.md).

Проверено 17 октября 2026:

- В [проекте контракта OpenDota](../add-opendota-client/design.md) `accountId` — число от 1 до 4294967294; 0 и 4294967295 исключены. Этот диапазон переиспользуется для совместимости, а не объявляется проверкой существования Steam-аккаунта.
- [Официальная документация Discord](https://docs.discord.com/developers/reference#snowflakes) описывает ID как snowflake размером до 64 бит и строковую передачу в HTTP API для сохранения точности.
- В текущем `.gitignore` уже исключены локальные настройки Codex и файлы окружения, но каталога `.local/` ещё нет в исключениях.

JSON-формат, строгая проверка, имя каталога и загрузка при запуске ниже — предлагаемые решения проекта. Реального файла компании, Discord ID, проверки доступа к серверу/каналу и runtime-проверок загрузчика сейчас нет. Начальные Steam32 ID известны из PROJECT_PLAN.md, но не являются готовой конфигурацией и не попадают в публикуемый пример.

## Goals / Non-Goals

**Goals:** один небольшой модуль без runtime-зависимостей, ясный контракт для будущих потребителей и одинаковое чтение файла на Windows/Linux. Публичные значения готовы к передаче клиенту OpenDota и Discord без конвертации.

**Non-Goals:** модуль не создаёт клиентов SDK и не управляет жизненным циклом приложения. Минимальные стыки с будущими модулями описаны ниже; их реализации и полные спецификации в изменение не входят.

## Decisions

### 1. Обычный локальный JSON

Планируемый каталог — `src/group-settings/` с одной публичной точкой экспорта. Разделять функции по файлам только при необходимости. Использовать встроенные файловые операции Node.js и `JSON.parse`; отдельный SDK, YAML/JSON5 парсер, библиотека конфигурации и дополнительные repository/service слои не нужны для трёх полей.

Общую TypeScript сборку переиспользовать, если она появится до реализации. Иначе добавить минимальную основу Node.js 22.14+ с компиляцией TypeScript, `build`, `typecheck` и `node:test`, как предложено в соседних изменениях. При реализации сначала перечитать общие файлы и не заменять появившиеся решения других модулей.

Планируемый шаблон `config/group-settings.example.json`:

```json
{
  "steamAccountIds": [100000001, 100000002],
  "guildId": "100000000000000001",
  "channelId": "100000000000000002"
}
```

Это вымышленные тестовые значения без проверки существования. README явно требует заменить все ID своими. Настоящий локальный файл рекомендуется хранить в `.local/group-settings.json`; при реализации добавить `.local/` в `.gitignore`, сохранив существующие исключения. Этот путь — соглашение инструкции, не встроенный fallback загрузчика. Пример и локальный файл создаются только на этапе реализации/настройки.

JSON выбран для одного редактируемого файла без дополнительного формата и зависимости. Набор отдельных переменных окружения потребовал бы правил разбора списка и смешивания источников; SQLite добавила бы миграции и конкуренцию источников при отсутствии редактирования в приложении. Ни то ни другое для этой версии не требуется. Секреты остаются в окружении и относятся к `operations`.

### 2. Минимальный публичный контракт

```ts
export interface GroupSettings {
  readonly steamAccountIds: readonly number[];
  readonly guildId: string;
  readonly channelId: string;
}

export function loadGroupSettings(path: string): Promise<GroupSettings>;
```

Функция проверяет непустой строковый путь, читает указанный файл один раз и либо возвращает полный снимок, либо отклоняет Promise с `GroupSettingsError`. Относительный путь разрешается относительно рабочего каталога процесса стандартными средствами Node.js; абсолютный путь поддерживается. Проверка `trim()` применяется только для обнаружения пустого аргумента: пробелы в настоящем имени файла не удаляются. URL и поиск файла по дереву каталогов не вводятся.

Выбор пути из CLI/окружения и вызов функции принадлежат точке сборки приложения в `operations`; в этом модуле нет собственного чтения `process.env`, CLI, singleton или реестра настроек. Приложение загружает настройки до запуска потребителей. Ошибка блокирует старт обработки матчей и публикации; конкретный bootstrap будет реализован в своём изменении.

Результат — новый объект и новый массив только проверенных значений. Заморозить и объект, и массив во время выполнения: одного TypeScript `readonly` недостаточно для общего снимка. Глобальный кеш не нужен. Внутренняя функция проверки входа может быть выделена для тестов, но не требует отдельного публичного API.

### 3. Проверка содержимого без автоматического исправления

| Поле | Проверка | Результат |
|---|---|---|
| Корень | Не `null`, не массив, объект ровно с тремя разрешёнными полями | Любое лишнее или отсутствующее поле — ошибка |
| `steamAccountIds` | Непустой массив; каждый элемент — `number`, `Number.isSafeInteger`, диапазон 1–4294967294; повторения запрещены | Новый массив в исходном порядке |
| `guildId`, `channelId` | Строка по шаблону `^[1-9][0-9]{0,19}$`; значение не больше `18446744073709551615` при точном сравнении | Исходная строка |

Для Discord после проверки длины/формата допустимо локальное сравнение через `BigInt`; в возвращаемом объекте и JSON остаётся строка. Не переводить ID через `Number` и не проверять фиксированную длину 18/19 цифр, дату snowflake или реальность объекта. Верхняя граница — ограничение представления uint64, а не разрешение Discord публиковать по любому такому ID.

Один аккаунт допустим: модуль не регулирует готовность автоматического отбора. Порог минимум двух аккаунтов на одной стороне задан общим планом и применяется в `match-pipeline`. Пустой список считается ошибкой настройки компании. Дубликаты отклоняются с позицией повторения, чтобы не скрывать ошибку и не создавать видимость двух участников. Не сортировать и не объединять аккаунты по владельцу; несколько аккаунтов одного человека остаются разными ID.

Не принимать строковые Steam32, Steam64, ссылки, Steam2/Steam3, Discord-упоминания, пробелы вокруг ID или дополнительные поля. Автоматическая конвертация и удаление дубликатов сделали бы ошибочный ввод незаметным. Наличие данных истории, закрытый профиль, рейтинг и участие в матче не влияют на локальную проверку.

### 4. Чтение и безопасные ошибки

Читать UTF-8; удалить один начальный символ BOM перед разбором. JSON с CRLF и LF обрабатывается одинаково. Комментарии и хвостовые запятые не поддерживаются. Применять обычную семантику `JSON.parse` без своего парсера и дополнительных форматов.

Публичная ошибка `GroupSettingsError` содержит безопасное русское `message`, `code` и для ошибок проверки массив `issues` с `path` и безопасным описанием:

| `code` | Причина | Диагностика |
|---|---|---|
| `read-error` | Файл отсутствует, недоступен или путь указывает на каталог | Контролируемое сообщение о чтении; системное исключение не выдаётся наружу |
| `invalid-json` | Синтаксис JSON неверен | Контролируемое сообщение о формате без фрагмента входного текста |
| `invalid-settings` | Пустой аргумент пути, неверный корень, поле, диапазон или дубликат | Путь и ожидаемое условие без фактического значения |

Пути диагностик ограничены `$path` для аргумента загрузчика, `$` для корня/неизвестного поля, именами трёх известных полей и индексами `steamAccountIds[n]`. Имя неизвестного ключа также не выводить: в нём случайно может оказаться чувствительный текст. Для нескольких ошибок допустим список в детерминированном порядке; полный сбор всех возможных ошибок не является обязательным контрактом.

Не включать исходный объект, значения, текст файла, необработанные сообщения `JSON.parse`, stack/cause исходного исключения в публичную ошибку. Не писать собственных логов с содержимым настроек. Вызывающий код может безопасно показать категорию и `issues`; глобальная система логирования остаётся в `operations`. Скрытые повторы чтения, исправление файла, fallback и частичный результат не нужны: пользователь исправляет источник и перезапускает приложение.

### 5. Один снимок на запуск и стыки модулей

Загрузчик сам не подписывается на файл. После его редактирования/удаления ранее выданный объект сохраняется, новый явный вызов читает текущее содержимое. В штатном приложении настройки загружаются один раз на запуск; горячее переключение на новую компанию или канал не проектируется.

| Потребитель | Предлагаемый минимальный контракт | Что остаётся у потребителя |
|---|---|---|
| `match-pipeline` | Получает `settings.steamAccountIds` через аргумент инициализации | Опрос, рейтинговый режим, сторона, минимум два разных ID, ручной запуск и влияние изменившегося списка на восстановление |
| `discord-interface` | Получает `settings.guildId` и `settings.channelId` | Существование/принадлежность/тип канала, доступ бота, права отправки и embeds, обработка сетевых ошибок |
| `operations` | Получает путь из своей конфигурации и вызывает `loadGroupSettings` перед потребителями | Секреты, проверка внешних зависимостей, завершение старта при ошибке, запуск/перезапуск и диагностика |
| `storage` | Не хранит редактируемую копию этих трёх полей | Данные задач/результатов и необходимые снимки контекста обработки по собственному контракту |

Соседние модули пока не реализованы и их полные спеки отсутствуют. Таблица задаёт только нужный стык, не утверждает готовность интеграции. `opendota-client` принимает каждый ID как аргумент своего публичного API и не читает настройки напрямую. Лаборатория оценки продолжает работать независимо от настроек компании и наличия Discord ID.

### 6. Проверка модуля

Изолированные проверки — `node:test` с временными файлами и вымышленными ID, без ключей, сети и базы. Сценарии контракта проверяют типы/границы/дубликаты, точность строковых Discord ID, UTF-8 BOM, ошибки чтения/JSON, безопасные сообщения и неизменяемость снимка. Нативный отказ в доступе при необходимости воспроизводится подменой файлового чтения; успешная проверка отсутствующего файла не считается проверкой прав ОС.

Проверить отсутствие неявного reread: загрузить файл, изменить/удалить его, убедиться, что снимок прежний, затем явно загрузить повторно и получить новое содержимое/ошибку. Модуль не импортирует Discord/OpenDota/SQLite и не обращается к ним при импорте или загрузке. Совместимость путей проверяется без ручной сборки разделителей; Windows проверяется фактически, выполнение на Linux фиксируется отдельно при отсутствии доступного Linux-окружения.

Пока подготовлены только документы. Ни чтение реального файла, ни старт сервиса, ни права Discord не проверены. Валидация OpenSpec подтверждает структуру документов, а не работоспособность загрузчика.

## Risks / Trade-offs

- [Опечатка блокирует запуск] → понятная ошибка известного поля, небольшой рабочий пример и отказ от скрытого fallback.
- [Корректный ID указывает на неподходящий канал или недоступный аккаунт] → не обещать сетевую пригодность после локальной проверки; внешние проверки принадлежат потребителям.
- [Файл отредактирован во время работы] → единый неизменяемый снимок и явное требование перезапуска; влияние на незавершённые задачи описывает `match-pipeline`.
- [Локальный файл случайно попадёт в Git] → `.local/` в исключениях, вымышленный пример и проверка правил исключений при реализации.
- [Другая реализация уже добавила сборку] → перед общими правками перечитать файлы и переиспользовать существующую основу.

## Migration Plan

Существующей конфигурации и пользователей приложения нет; миграции данных и SQLite не требуются. При реализации добавить модуль, пример и инструкцию. Настройка окружения создаёт локальную копию примера с реальными ID, а будущий bootstrap передаёт её путь и блокирует запуск потребителей при ошибке.

Для возврата к прежним настройкам восстановить локальный файл и перезапустить приложение. Загрузчик не меняет файлы, задачи и результаты; правила продолжения незавершённой обработки после изменения списка/канала остаются частью будущего `match-pipeline`.
