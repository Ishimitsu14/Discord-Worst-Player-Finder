# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md), поведение — в [spec.md](specs/match-facts/spec.md). В проекте уже есть TypeScript/ESM, Node.js 22.14+, Ajv, `node:test`, CLI и 71 тест лаборатории. Производственные `src/opendota/` и `src/match-facts/` отсутствуют. Клиент OpenDota описан, но не реализован; его предполагаемый `MatchSnapshot` содержит `data`, `parseState`, `retrievedAt`. Старые утверждения об отсутствии кода в документах соседнего изменения относятся к моменту их подготовки.

Изучены `src/evaluation-lab/{context,context-v2,corpus,prepare,files,cli,types}.ts`, тесты v2 и документация лаборатории. Сейчас каждый evidence повторяет ID, значение, слот, единицу, JSON pointers и transform, а карточки драк дополнительно ссылаются на этот список. `compact-v2` сохраняет карточки, но большую часть логов обзора/подключений представляет счётчиками. По согласованному уточнению алгоритм должен заранее собрать короткий отчёт для ИИ; полный объявленный набор фактов и подробная хронология сохраняются локально. Для подготовки обоих представлений ИИ не используется.

Проба была выполнена только в памяти: evidence разложены по вложенным именованным полям, исходные пути/единицы/transform убраны из модельной части. Это оценка перепаковки полного набора, не готовый короткий отчёт и не проверка смысловой эквивалентности или качества. Вариант с кортежами ещё меньше, но именованные ячейки выбраны ради читаемости и проверки. Эти измерения не подтверждают достижимость новых 32/64 KiB: короткий отчёт дополнительно использует объявленные агрегаты и фиксированную проекцию фактов.

В последнем снимке действительно есть противоречие: `teamfights[0].deaths = 4`, сумма `players[].deaths = 5`. Его нельзя исправлять выбором удобного счётчика. Подготовка/проверка/сериализация текущего v2 на этом снимке заняла около 16 мс по медиане пяти запусков; основная задержка прежнего ответа была в ручной работе. Ускорение новой аналитики MiMo не измерено: платных прогонов не было.

Первичные источники проверены по закреплённым ревизиям:

- [compute.ts, core e30f5ac](https://github.com/odota/core/blob/e30f5ac973dfece86d096ee0a27f08c0248948e3/svc/util/compute.ts): `position_est` оценивается по раннему фарму/покупкам обзора и линиям при наличии данных всей команды; это предположение. `life_state_dead` складывает состояния 1/2, а `total_gold` вычисляется через GPM и длительность, поэтому это разные показатели с разным происхождением.
- [Parse.java, parser ac6e79c](https://github.com/odota/parser/blob/ac6e79c6d7d227f0ee68a98164d2cb4f6a47c45d/src/main/java/opendota/Parse.java) и [processExpand.mjs](https://github.com/odota/parser/blob/ac6e79c6d7d227f0ee68a98164d2cb4f6a47c45d/processors/processExpand.mjs): минутный `gold_t` берётся из total earned gold, networth — отдельное поле; временные точки опираются на interval. Новое представление не называет `gold_t` net worth.
- [processTeamfights.mjs](https://github.com/odota/parser/blob/ac6e79c6d7d227f0ee68a98164d2cb4f6a47c45d/processors/processTeamfights.mjs): канонические десять участников, отрезки с минимум тремя смертями, незакрытый последний бой может отсутствовать. Эта логика не гарантирует согласованность всех полей production ответа.

Снимки, локальные оценки и результаты не публикуются. Нет независимых эталонов качества новой сводки; все четыре матча уже обсуждались с пользователем и не подходят для независимого holdout этого подхода.

## Goals / Non-Goals

**Goals:** одно детерминированное преобразование без ИИ, полный локальный набор, короткий заранее рассчитанный отчёт для интерпретации моделью, проверяемый реестр и удобная подготовка без ручных скриптов.

**Non-Goals:** перенос инструкции/скоринга из лаборатории, фиксация качества MiMo, универсальная система преобразований, реконструкция отсутствующих событий или отслеживание положения/готовности способностей по неполным журналам. Полный путь URL → загрузка → parse job → аналитик остаётся работой соседних модулей.

## Decisions

### 1. Чистый самостоятельный модуль и небольшой офлайн-вход

Планируемый каталог — `src/match-facts/`, публичная точка `index.ts`, типы, преобразование и проверка пакета; внутренние файлы разделять только по фактической сложности. Использовать существующую сборку, Ajv для границ сериализуемых форматов и стандартные Node.js SHA-256/JSON. Новые зависимости не нужны.

Предлагаемые публичные операции:

```ts
prepareMatchFacts(
  input: { matchId: number; side: 'radiant' | 'dire'; data: unknown },
  options: { dictionary: unknown; roleOverrides?: RoleOverride[] },
): FactsBundle;

verifyFactsBundle(bundle: unknown, input: MatchFactsInput, options: FactsOptions): FactsBundle;
validateFactReferences(ids: string[], bundle: FactsBundle): void;
```

Это предлагаемый контракт для будущего вызывающего кода, не существующий API. Клиент передаёт `snapshot.data`; лаборатория читает точные сохранённые байты, проверяет их digest и передаёт разобранный JSON. Подготовка не читает окружение, файлы, часы, сеть или состояние кеша и не изменяет вход. Проверка ссылок не доказывает правильность текста модели.

`match-facts` не импортирует runtime лаборатории. Её файловые helper остаются в тонком CLI-адаптере, а узкие структурные типы позволяют работать до появления клиента. Не выносить общий framework только ради повторного использования нескольких проверок. Альтернатива — развивать `buildContext` лаборатории как production API — отвергнута из-за зависимости от экспериментов, профилей модели и требования сохранить v1/v2.

### 2. Основа входа и различимые ошибки

`data` — JSON-совместимый объект. Проверить safe integer match ID и его совпадение, известную сторону, конечную положительную длительность, boolean исход, массив игроков с уникальными каноническими слотами 0–4/128–132 и положительными hero ID. Пять союзников обязательны; пропуски соперников допустимы с указанием ожидаемых слотов. Ники и account ID для этого не используются. Известный положительный hero ID без имени в справочнике сохраняется как неизвестный справочнику ID.

Рейтинговые lobby/game mode не отбираются здесь: модуль 3 отвечает за допустимость игры. Их исходные значения входят в факты, если корректны. `version` отсутствует/null/0 → basic, положительное целое → parsed; другой тип даёт предупреждение, не обещание готового разбора. `retrievedAt` не требуется и не выдумывается из start_time.

Типизированные ошибки: `invalid-input`, `unusable-match`, `invalid-dictionary`, `invalid-role-override`, `context-too-large`, `integrity-error`, `unknown-fact-reference`. Они содержат безопасный код и допустимые числовые детали, без исходного payload. Непригодная основа не выпускает usable пакет. Непригодное необязательное поле становится unavailable с диагностикой группы/слота; не теряются остальные известные поля.

### 3. Контекст и реестр разделены, значения остаются читаемыми

`FactsBundle` включает `facts`, `context`, `evidence`, `manifest`:

- `facts`: полный нормализованный набор объявленного профиля, `version: 1`, `format: 'facts-v1'`; metadata матча, каталог, игроки, хронология, карты, карточки и quality. Это не копия всех полей сырого JSON.
- `context`: короткий структурированный отчёт `version: 1`, `format: 'match-brief-v1'`, рассчитанный из facts тем же кодом. Только его точные minified bytes предназначены для первого запроса ИИ.
- `evidence`: полный локальный реестр исходных и производных наблюдений.
- `manifest`: версии/контрольные суммы обоих представлений и реестра, идентичность всего пакета.

Полные журналы, вложенные карты целей и подробные карточки не дублируются в context. Обычный запуск не вызывает LLM ни для отбора, ни для написания сводки; русский Markdown строится шаблонами из уже готового context. Числовые значения передаются без округления; display округляется только в Markdown.

Ячейка наблюдения:

```ts
type Fact<T> = { id: string; value: T };
type Missing = { unavailable: 'missing' | 'null' | 'invalid' };
type Observation<T> = Fact<T> | Missing;
```

Фрагмент, не полный валидный контекст: `"deaths": { "id": "e17", "value": 15 }`. Единица и смысл `deaths` определены один раз в каталоге. Нулевое наблюдение имеет ID и value 0. У missing/null/invalid нет фиктивного числового основания. Для коллекций: state `present|missing|null|invalid`, entries и проверяемый count существующего массива; present + entries [] отличается от неизвестности. Часть невалидных элементов даёт present с известными событиями и quality, где указаны исходное число/число недоступных элементов; это не считается полным журналом.

ID `e1`, `e2`, ... назначаются стабильным обходом полных фактов, затем объявленных производных; проекция в короткий отчёт не перенумеровывает их. Повтор одного наблюдения использует тот же ID и значение. Производные агрегаты отчёта тоже присутствуют в facts/evidence с формулой. ID действуют только внутри идентичности пакета. Ссылку из ответа модели можно принять лишь на ID, чьё значение включено в переданный context; существование ID только локально недостаточно. Статические подписи и справочные имена — metadata, а не свидетельства качества игры.

Локальный `evidence` содержит для каждого ID значение, playerSlot/null, metric/unit, исходные pointers либо входные ID производной формулы, тип источника `snapshot|override` и версию формулы. Все цепочки ацикличны и разрешаются до снимка/options; пути и подробные цепочки не попадают в context. Справочник подключается параметром: использовать закреплённый `evaluation/dictionaries/dotaconstants-v1.json`, записывать revision и digest содержания, не переносить его копию и не обновлять из сети. Ручная роль получает ID со ссылкой на сохранённые options, а не ложный pointer в OpenDota.

Профили facts-v1 и match-brief-v1 версионируются отдельно. Профиль фиксирует допустимые revision/content digest справочника; изменение файла требует явного обновления профиля. Валидация формы без проверки этого закрепления недостаточна для доверия к справочным строкам. Quality содержит parseState, missingOpponentSlots, доступность групп по слотам и issues с фиксированным code/scope и известными числовыми индексами. Coverage отчёта для каждой группы различает sourceState `present|missing|null|invalid` и представление `direct|aggregate|local-only`; известные sourceCount/reportedCount указываются отдельно. Это не позволяет спутать локально оставленную детализацию с отсутствием действия. Произвольные строки ошибок и длинные pointers остаются вне context.

Альтернативы: кортежи `[id,value]` меньше, но хуже читаются; простая перепаковка всех evidence всё ещё оставляет сотни KiB; текстовая сводка через вторую LLM добавила бы задержку и недетерминированность. Выбран короткий отчёт обычным кодом, именованные ячейки и отдельный полный локальный набор.

### 4. Полный локальный профиль facts-v1

Профиль полного локального набора — часть преобразования, без пользовательского конструктора полей/весов. За основу взять точные `summaryFields`, `mapFields`, `targetFields` текущего compact-v2, сохраняя их доступные разрешённые значения; расширение перечислено ниже. Эти группы не обязаны целиком передаваться ИИ. В production модуль переносится закреплённый manifest имён, без runtime импорта изменяемых allowlist лаборатории. Соответствие проверяется тестом покрытия.

| Группа | facts-v1 |
|---|---|
| Матч | match ID, сторона, исход, длительность, game/lobby mode, patch/start_time/parse version, оба счёта и состояния строений при наличии |
| Игроки | Все союзники и доступные соперники, playerSlot/hero ID, безопасное справочное имя, одинаковые группы метрик и явные отсутствия |
| Ресурсы/вклад | Все summaryFields v2: экономика, K/D/A, добивания, урон/контроль/лечение, поддержка, предметы/рюкзак/нейтральный слот, исходные оценки линии |
| Роли | position_est и явные overrides с источником; отсутствие и конфликт; без геройских нормативов |
| Экономика | Точные срезы 10/20/30 и delta 10–20/20–30 для всех доступных seriesFields v2, кроме массива times; gold_t, networth_t, xp_t и остальные ряды остаются разными метриками |
| Карты | Разрешённые числовые damage/damage_taken, killed/killed_by, uses, inflictors, healing, gold/xp reasons, ability_targets/damage_targets из v2; известные неполнота/невалидность не скрываются |
| События | Все доступные purchase/kills/deaths/buyback/runes/obs/sen/obs_left/sen_left/connection события по всем игрокам с разрешёнными полями, без длинных временных рядов и сырых координат |
| Драки | Все доступные карточки с обеими командами, scalar metrics и maps из context-v2; известные отсутствия показателей каждого участника |
| Объекты | Все исходные события с безопасными известными полями, фиксированными типами либо unknown и quality; без приписывания неизвестного исполнителя |

События упорядочиваются по time, равные времена — по исходному индексу; связь с исходным индексом хранится в реестре. Не сортировать эпизоды по плохой игре и не выбирать top-N. Для карт разрешены только ключи закреплённого справочника/числовые ID и явно перечисленные служебные ключи конкретного поля; неизвестные keys/строки исключаются с отметкой неполноты. JSON pointers экранируют `~` и `/`. Совпадение строкового ключа героя не используется для определения личности игрока, если оно неоднозначно.

Событие disconnect — только зафиксированное отключение; не вычислять AFK по `leaver_status`. Покупка, конечный слот предмета и item_uses — самостоятельные наблюдения. Карта ability_targets не гарантирует полный список применений: недостающий target не означает count 0. Ожидаемые геройские функции и правильность билдов в facts-v1 не кодируются.

### 4.1. Фиксированный короткий отчёт match-brief-v1

Алгоритм заранее выполняет арифметику, группировку и сопоставления. Контекст — структурированный JSON с именованными полями, из которого теми же шаблонами получается читаемый отчёт; модель не должна восстанавливать сводку из тысяч сырых событий. В модельном запросе не прикладываются facts/evidence целиком. Для самого отчёта не вызываются LLM, внешние рейтинги или сеть.

| Раздел отчёта | Обязательный состав |
|---|---|
| Матч | Сторона, длительность, исход, оба счёта, patch/mode/parseState при наличии и общие ограничения |
| Пятёрка союзников | Все пять слотов по одному шаблону: герой/роль/источник; K/D/A; GPM/XPM, net worth, last hits; hero/tower damage, hero healing, stuns; life_state_dead/dead-share; вычисленное участие в убийствах; установленные/снятые observer/sentry, stacks и buyback count |
| Предметы и способности союзников | Конечные слоты предметов/рюкзака/нейтрального слота; первая известная покупка каждого типа, оставшегося в этих слотах, и счётчик применения этого типа при однозначной словарной связи. Известные плоские ability_uses сохраняются, вложенные карты целей и подробности по дракам — local-only |
| Соперники | Все доступные слоты с героем/ролью/источником, K/D/A, GPM/XPM, net worth, hero/tower damage, stuns и life_state_dead; пропуски не заполняются |
| Экономика | Для обеих команд точные gold_t/networth_t/xp_t/lh_t на 10/20/30 при наличии. Для всех пяти союзников — заранее рассчитанные разницы earned gold/net worth/xp с соперником той же предполагаемой позиции на этих срезах, либо unavailable с причиной |
| Фазы союзников | Одинаковые интервалы 0–10, 10–20, 20–30, 30–конец: числа известных смертей/убийств, размещений observer/sentry и покупок; покрытие журналов и число нераспределённых событий. Отдельно известные причины смертей по вражеским героям для каждого интервала |
| Драки | Одна компактная карточка **каждой** исходной драки: времена/header deaths/participant sum/quality; для обеих команд deaths, buybacks, damage, healing, gold_delta каждого канонического слота. Для союзников — известное время пересечения death windows с этой дракой, с ограничением неполноты |
| Объекты и выкупы | Хронология всех доступных объектов с временем, безопасным типом/целью/подтверждённым actor; время и слот всех известных союзных buyback. Подробности и связи после драки остаются в facts; при передаче связи она называется только временной близостью |
| Подключения | Число известных disconnect/reconnect по союзнику и время последнего события каждого типа. Длительность AFK по этому не рассчитывается |
| Coverage | Доступность исходных групп и режим direct/aggregate/local-only. Подробные purchase/death/ward/connection журналы и вложенные карты не объявляются отсутствующими из-за сокращения |

Правила одинаковы для всех игроков соответствующей стороны и не зависят от того, кто предположительно худший, от победы или от знакомства. Сопоставление ролей возможно, только когда позиции обеих полных пятёрок известны и однозначны; иначе блок сравнения unavailable, а наблюдаемые ресурсы всё равно передаются. Знак разницы всегда «союзник минус соперник», имя/слот пары и источник роли сохранены. Никаких норм GPM, списков «правильных» предметов и штрафов за необычного героя.

Фазы определяются временем события в секундах: [0,600), [600,1200), [1200,1800), [1800,duration]; будущее относительно конца матча помечается недостигнутым, событие ровно на границе относится к начинающейся фазе. Если матч завершился ровно на границе, достигнутая граничная точка может содержать событие без положительной длины интервала; это число событий, не rate. Невалидное/неизвестное время не угадывается; соответствующее число исключённых элементов остаётся в coverage. Count по журналу отличается от общего upstream счётчика, отсутствие записей не подменяет его.

Первая покупка типа предмета не означает непрерывное владение конкретным экземпляром или его готовность. Неоднозначная связь item ID и purchase token делает тайминг unavailable. Счётчики применений не превращаются в рейтинг активности. Плоские ability_uses не доказывают своевременность/цель применения, а отсутствие подробной карты в отчёте не доказывает нулевой вклад способности.

Агрегаты содержат ID, источники и coverage. Они сохраняют положительные и отрицательные значения по всем заявленным периодам, а не только худший период. Ни один алгоритм не отбирает «трёх самых плохих смертей» и не делает готовый приговор. Если детализации brief недостаточно для вывода, downstream должен учитывать ограничения; автоматическое расширение отчёта, дополнительный вызов ИИ и выбор худшего не входят в модуль 4.

### 5. Формулы, единицы и временная точность

| Наблюдение / transform | Формула и условия |
|---|---|
| identity-v1 | Проверенное исходное значение по точному pointer; без подстановок |
| array-length-v1 | Длина реально существующего массива, включая пустой; количество не заменяет доступность/валидность его элементов |
| slice-Nm-v1 | Только один индекс `times[i] === N*60`, N*60 <= duration; значение из согласованного ряда по i. Дубликат нужного времени, неверная длина/значение → unavailable |
| delta-A-Bm-v1 | `series[B] - series[A]`, только при двух корректных срезах; источники включают времена и значения обоих концов |
| kill-participation-v1 | `(kills + assists) / teamScore`, только при известных неотрицательных целых и teamScore > 0; teamScore — отдельный upstream факт, не сумма убийств пятерых |
| dead-share-v1 | `life_state_dead / duration`, только при доступных конечных значениях и 0 <= deadSeconds <= duration; иное даёт ограничение и недоступную долю |
| fight-deaths-sum-v1 | Сумма десяти корректных participant.deaths; сравнение с header.deaths даёт quality, не заменяет исходный header |
| dead-window-v1 | `[max(0,time), min(duration,time+time_dead))` только при известном time_dead >= 0 и положительной длине; означает интервал по upstream time_dead, без реконструкции пропущенного respawn |
| interval-overlap-v1 | Пересечение известного dead-window с [fight.start,fight.end]; сохраняются границы и исходные времена, отсутствие связи не доказывает присутствия игрока в бою |
| following-objectives-v1 | `fight.end < objective.time <= fight.end+120`, без вычисления причинности; одно событие может подходить нескольким карточкам |
| same-position-difference-v1 | Корректный срез союзника минус срез однозначно сопоставленного соперника; источники включают оба значения, времена и назначения ролей |
| phase-count-v1 | Число известных валидных событий объявленного типа в фиксированной фазе; missing/null/invalid журнал не даёт count 0, частичность обозначена отдельно |
| phase-killer-count-v1 | Число известных смертей в фазе по безопасному ключу героя-убийцы; неизвестные/неоднозначные ключи не приписываются игроку и учитываются в coverage |
| first-final-item-purchase-v1 | Минимальное известное время покупки типа из финальных слотов при однозначной словарной связи; это тайминг типа, не история владения экземпляром |
| known-dead-overlap-v1 | Длина объединения известных пересечений dead-window с дракой без двойного счёта. Неполные окна дают только известное время с пометкой lower-bound. Present empty журнал даёт 0 известных секунд; отсутствующий журнал либо непустой журнал без пригодных окон даёт unavailable |
| connection-summary-v1 | Число известных событий disconnect/reconnect и последнее время каждого типа по исходному журналу, без вывода длительности отсутствия |

Доли не округляются; при нулевом знаменателе нет процента. Если kills+assists превышают teamScore, исходные значения сохраняются, доля unavailable и есть quality. Нет фиксированной суммы «штрафа» или сравнения с нормативом роли.

Обычные счётчики требуют неотрицательного целого, экономические/уронные значения — конечного неотрицательного числа, delta допускают знак, времена событий — конечного числа. У каждого поля в каталоге свой домен; единый фильтр nonnegative для всех полей не используется.

Единицы: gold/earned_gold для золота, отдельный net worth; gold/minute и xp/minute; xp; hp; seconds; count; ratio 0–1 для корректных долей. Контроль может суммироваться по целям и не трактуется временем личного присутствия. Исходный teamfight_participation и вычисленная доля участия — отдельные именованные поля.

`life_state_dead` не равен гарантированно сумме time_dead; суммирование логов не заменяет итоговый счётчик. Если для отдельной смерти time_dead отсутствует, это наблюдение сохраняется без выдуманного окончания. Даже при buyback нет попытки восстановить боевую позицию или реальную доступность способностей. События до 0 или после duration сохраняются, если тип/время допустимы, с ограничением при несогласованности; например, финальный объект может отличаться на секунду. Для срезов всё равно действует фактическая длительность.

### 6. Позиции, участники и ограничения драк

Нормализовать роли для обеих команд: валидные position_est 1–5 — `opendota-estimate`, явные `{playerSlot,position}` — `manual`, остальные — `unknown`. Не пересчитывать алгоритм OpenDota и не дополнять роль оставшимся номером. Ручные назначения требуют существующего слота, уникального слота и позиции внутри команды. Они вытесняют конфликтующие автоматические оценки; оставшиеся дубликаты оценок становятся unknown. Исходное предположение и исправление различаются в реестре.

Канонический индекс `teamfights.players` 0–9 соответствует слотам `[0,1,2,3,4,128,129,130,131,132]`, независимо от порядка `match.players`. Массив иной длины не сопоставляется предположением: header сохраняется, участники неизвестны и quality содержит код. Пустая запись участника не становится нулевым уроном/смертями. Слоты неизвестных основных соперников могут оставаться обозначенными в корректной карточке, без выдуманного hero ID.

В полном наборе для каждой карточки: start/end/last_death/deaths при наличии, для каждого участника deaths/buybacks/damage/healing/gold_delta/xp_delta/xp_start/xp_end и доступные ability_uses/ability_targets/item_uses/killed. В коротком отчёте сохраняется каждая карточка, но с фиксированными scalar полями из раздела 4.1, без вложенных карт. Если времена невалидны или end < start, наблюдения остаются отмеченными, производные временные связи недоступны. Заголовок и сумма смертей не смешиваются; при отсутствии хотя бы одного нужного числа сумма неизвестна. Не утверждать точный общий размен по противоречивой карточке.

Связи со смертями и объектами — только по временам. Нейтральная подпись «события в течение 120 секунд после end» входит в каталог/ограничения контекста. teamfight healing и hero_healing различаются; ноль урона не означает AFK, карточки не исчерпывают драки. Неизвестный actor не назначается по последнему удару, расположению в массиве или знакомому account ID.

### 7. Идентичность и проверка без сети

JSON-совместимые данные канонизируются рекурсивной сортировкой ключей объектов по кодовым единицам; массивы сохраняют порядок. `dataDigest` — SHA-256 канонического JSON data, **не checksum исходных HTTP bytes**. В лаборатории дополнительно проверяется имеющийся snapshot.digest точных байтов, он сохраняется в диагностике адаптера. Эти два digest имеют разные имена и не сравниваются между собой как одинаковые.

В manifest: envelope version, отдельные facts/brief format/transform/profile versions, dataDigest, side, dictionary revision/content digest, digest отсортированных overrides, factsDigest, contextDigest, evidenceDigest и bundleId. Bundle ID определяется этими входами и digest результатов, не временем подготовки. Изменение алгоритма brief меняет его профиль/версию и идентичность пакета. Evidence ID обходятся в фиксированном порядке метрик, канонических игроков, событий и производных. Повтор одного набора входов даёт те же facts/context/evidence/manifest; перестановка ключей объекта не меняет identity, перестановка массива может менять dataDigest/pointers, но не slot mapping.

`verifyFactsBundle` проверяет структуру и digests, затем воспроизводит нормализацию и алгоритм краткого отчёта по raw data/options, сравнивая facts/context/evidence/manifest. Это проверяет также роли, пропуски, агрегаты, coverage и структуру карточек. Неизвестная версия отвергается. `validateFactReferences` проверяет ID и наличие соответствующего значения в переданном context; ID только из facts/evidence отклоняется как unknown-fact-reference. Отчёт не содержит ссылок на неприложенные значения как будто они доступны модели. Ни одна проверка не оценивает справедливость текстового обвинения.

Альтернатива — доверять сохранённому digest без проверки источника — не позволяет обнаружить согласованно подменённые значения/ссылки. Общая схема JSON canonicalization со сторонней зависимостью не требуется для JSON-объектов этого приложения.

### 8. Размер, покрытие и измерения

Проектные значения **match-brief-v1**: целевой размер **32768 UTF-8 bytes (32 KiB)** и жёсткий предел **65536 bytes (64 KiB)** точного minified context. Цель и предел — разные показатели: результат 40 KiB допустим, но цель не достигнута и это видно в отчёте. Каждый из четырёх закреплённых снимков должен пройти жёсткий предел и обязательное покрытие. Это engineering acceptance, не текущие подтверждённые показатели модуля. В размер входят metadata, каталог, quality, все обязательные таблицы и компактные карточки; prompt/schema будущего аналитика измеряются отдельно модулем 5. Размер полного локального facts/evidence показывается отдельно и не считается размером входа ИИ.

Если brief превышает 64 KiB, `context-too-large` содержит размер и предел. Нет адаптивного fallback, который убирает поддержку у одного игрока, экономику у другого или часть драк. Полные карты/журналы заранее имеют объявленное локальное представление, это не аварийное усечение. Изменение состава brief требует новой версии профиля и проверки; вместо ошибки полный локальный набор модели автоматически не отправляется. Обычный вызов не строит compact-v2 ради сравнения — это только диагностика лаборатории.

Покрытие проверяется двумя независимыми уровнями:

1. **Полнота facts-v1:** сопоставить по source paths/transform все разрешённые значения compact-v2 и дополнительные факты объявленного полного профиля; unknown/untrusted исключаются только с quality.
2. **Покрытие match-brief-v1:** проверить все обязательные поля пятерых, соперников, достигнутых срезов, фаз и каждую компактную карточку; воспроизвести агрегаты из полных фактов; сверить coverage direct/aggregate/local-only. Количество полных фактов не требуется целиком помещать в brief, но отсутствие обязательной группы никогда не засчитывается как сокращение.

Список ожидаемых наблюдений/агрегатов формируется независимо от serializer и построителя отчёта, чтобы одинаковая ошибка исключения не проходила проверку. На четырёх снимках сравнивать выборочные сводные строки с исходниками, включая сильный вклад, слабый эпизод и контраргумент по каждому игроку, без назначения автоматического победителя проверки качества. Если нужное для прежнего вывода наблюдение осталось только локально, это фиксируется как ограничение brief, а не объявляется сохранённым смыслом. Реальные JSON не включаются в публичные фикстуры; CI использует синтетические edge cases, локальный отчёт хранит digests, coverage и размеры обоих представлений. Улучшение качества выбора требует отдельного пользовательского ревью/эксперимента.

Диагностика раздельно измеряет чтение/проверку bytes, нормализацию facts, построение brief, проверку пакета, сериализацию и запись. Для локального сравнения минимум пять повторов, медиана, максимум, размеры facts/brief/evidence, достижение цели 32 KiB и жёсткого предела 64 KiB; отношение к compact-v2 — справочная величина, прежняя цель 40% не применяется. Время ожидания OpenDota, ручной работы и генерации модели не приписывается преобразованию. Байты не называются tokenizer count; живые latency/quality MiMo остаются незамеренными.

### 9. Офлайн-команда и границы интеграции

Тонкое расширение существующего CLI:

```powershell
npm.cmd run build
npm.cmd run lab -- facts --match-id 9045784658 --side dire
# Необязательно: --root DIRECTORY --roles FILE
```

Это **будущие команды**, сейчас операция facts отсутствует. Выбрать запись corpus по match ID/side, проверить исходный bytes digest, прочитать закреплённый справочник и вызвать публичное преобразование/проверку. Никакого collect, requestParse, run или автоматического определения стороны. Если записи нет — понятная локальная ошибка. Файл ролей: `{version:1,matchId,entries:[{playerSlot,position}]}`, match ID должен совпадать с командой.

По существующему паттерну `newDirectory` сохранять `.local/evaluation/facts/<invocationId>/`: `facts.json` (полный нормализованный набор), `context.json` (точные minified bytes короткого отчёта), `evidence.json`, `manifest.json`, `summary.md`, `diagnostics.json`. Manifest записывается последним как признак завершённого пакета; partial каталог не принимается как готовый. Атомарные helper остаются в адаптере. Другой запуск создаёт новый каталог и не меняет прежний; одинаковые пакеты имеют одинаковый bundleId. Кеш анализа/TTL здесь не реализуется.

summary — читаемая шаблонная версия **короткого** context: таблица пятерых, соперники, срезы/сравнения, фазы, компактные карточки, объекты и coverage с ID. В неё не подмешиваются только локальные подробности, чтобы человек мог оценить фактический вход ИИ. Display округляется, ссылки ведут к неизменённым фактам. При необходимости человек открывает facts/evidence отдельно. Заголовки «худший» и roast не генерируются. diagnostics хранит даты, времена, размеры, исходный snapshot checksum/происхождение; он не входит в bundleId и не отправляется модели.

Лабораторные корпуса/эталоны и планы не переписываются; ручной эталон не обязателен и не входит в context. Старые команды, профили, full/compact-v1/v2 и analysis-v1/v2 остаются прежними. Для сетевого анализа match-brief-v1 понадобится отдельное изменение `match-analysis`/экспериментального пакета: основной запрос получает только короткий context и идентичность пакета; facts/evidence автоматически не прикладываются. Дополнительная LLM для написания сводки не нужна. В модуле 4 сетевой запуск аналитика не реализуется.

### 10. Проверки и передача дальше

Нужны unit tests для границ, пропусков, позиций, формул/агрегатов, времён, privacy, canonical mapping, расхождения смертей, двух уровней coverage и integrity; интеграционный тест офлайн-команды без сети с повторами/повреждением. Из fixtures можно переиспользовать `match()`, production от него не зависит. Проверить необычную пятёрку, смерть перед боем, disconnect у конца, положительное и отрицательное сравнение ресурсов, а также отклонение ID, существующего только в полном локальном наборе. Проверка равномерности brief не принимает исчезновение полезных фактов одного игрока ради объёма.

Отдельная проверка четырёх снимков выводит обе coverage, размеры facts/brief/evidence, сравнение с compact-v2 и timings, без LLM. Каждый brief должен пройти 64 KiB; результат относительно цели 32 KiB показывается отдельно. Запускать установленный typecheck/build/test и strict OpenSpec validation; нестабильные миллисекунды не становятся обязательным CI порогом. Linux paths используют node:path, фактический Linux runtime при отсутствии среды остаётся непроверенным.

Вместе с реализацией документировать API, оба профиля, формулы/поля, команды и результаты проверки. Короткий match-brief-v1 становится входом следующей спеки `match-analysis`; полный facts-v1 остаётся средством локальной проверки/углубления. Качество выбора/roast и независимые holdout остаются задачами лаборатории и не подтверждаются размером отчёта.

## Risks / Trade-offs

- [Агрегирование скрывает полезное действие или контраргумент] → равномерный профиль пятерых, все компактные драки, отдельная проверка brief и полного набора; честная фиксация локально оставленной информации и последующее содержательное ревью.
- [Source данные противоречат друг другу] → raw значения и производные различаются, локальная диагностика, отказ от точного общего размена при mismatch.
- [Разные версии/провайдеры меняют смысл метрик] → закреплённые версии/справочник, distinct gold/net worth/healing, unknown для неподдержанных данных; исходный код не объявляется гарантией production.
- [64 KiB недостаточно для очень длинной игры] → явный отказ и review версии brief; нет удаления игроков/драк или подмены короткого запроса полным пакетом.
- [Новый формат требует другого потребителя] → отдельные facts-v1/match-brief-v1 и их версии, замороженные старые планы, будущий consumer получает только brief и обновляется отдельной спекой.
- [Проверка воспроизведения повторяет ту же смысловую ошибку] → независимые примеры ожидаемых значений/покрытия и ручное ревью; структурная integrity не называется качеством анализа.
- [Основное время всё ещё занимает модель или ожидание parse] → раздельные замеры; ускорение end-to-end не обещается до фактического pipeline/аналитика.

## Migration Plan

1. По отдельному запросу реализовать самостоятельный модуль, полный facts-v1, алгоритмический match-brief-v1 и офлайн-вход, не заменяя лабораторные v1/v2. Существующей реализации facts-v1 пока нет, миграция её данных не требуется.
2. Проверить синтетические случаи и четыре снимка, сохранить результаты двух coverage/размеров и читаемый вход ИИ без изменения прежних планов/эталонов.
3. Подготовить отдельную спеку `match-analysis` под короткий match-brief-v1, затем продолжить эксперименты с явным бюджетом по запросу пользователя.
4. Откат будущего подключения — перестать передавать match-brief-v1 аналитику; исходные снимки и старые эксперименты остаются читаемыми. Преобразование не меняет БД или удалённое состояние.
