# Spec Delta

## Purpose

Предоставлять остальным модулям бота данные OpenDota и управляемое ожидание разбора реплея. Явно различать отсутствие данных, неподготовленный реплей и ошибки внешнего сервиса, чтобы дальнейший анализ не строился на выдуманных значениях.

## ADDED Requirements

### Requirement: Проверка идентификаторов и параметров

Клиент SHALL проверять идентификаторы матча, Steam32 аккаунта и задания, а также параметры страниц до сетевого запроса. Некорректный ввод SHALL возвращать отдельную ошибку аргумента без обращения к OpenDota.

#### Scenario: Корректные идентификаторы
- **WHEN** переданы допустимые положительные идентификаторы
- **THEN** клиент использует match ID для матча, Steam32 account ID для истории и возвращённый OpenDota job ID для задания

#### Scenario: Некорректный идентификатор или страница
- **WHEN** передано отрицательное, дробное, небезопасное число, Steam64 вместо Steam32, недопустимый job ID или параметры страницы вне допустимого диапазона
- **THEN** клиент возвращает ошибку аргумента и не отправляет HTTP-запрос

### Requirement: История матчей с явной пагинацией

Клиент SHALL получать страницу истории указанного игрока с явными размером и смещением. Он SHALL сохранять поля результата и не скрывать матчи по режиму, исходу, значимости или составу команды. Решение о пригодности матча принимает вызывающий модуль.

#### Scenario: Получение следующей страницы
- **WHEN** вызывающий модуль запрашивает страницу с ненулевым смещением
- **THEN** клиент передаёт размер и смещение OpenDota и возвращает только полученную страницу

#### Scenario: Пустая история
- **WHEN** OpenDota возвращает пустой массив
- **THEN** клиент возвращает успешный пустой результат без утверждения, что игрок не играл или его профиль закрыт

#### Scenario: Разные типы матчей
- **WHEN** ответ содержит победы, поражения или нерейтинговые игры
- **THEN** клиент сохраняет эти записи для последующей фильтрации вызывающим модулем

### Requirement: Получение и проверка данных матча

Клиент SHALL возвращать проверенные базовые поля матча, все полученные записи игроков, дополнительные поля OpenDota, время загрузки и состояние разбора. Несовпадение запрошенного match ID, некорректный JSON или нарушение базового контракта SHALL приводить к ошибке формата ответа.

#### Scenario: Матч успешно загружен
- **WHEN** OpenDota возвращает корректный матч с десятью игроками
- **THEN** клиент возвращает всех игроков обеих сторон вместе с исходными дополнительными полями

#### Scenario: Изменение расширенной схемы OpenDota
- **WHEN** ответ содержит новые поля или не содержит необязательных полей
- **THEN** клиент сохраняет новые поля и принимает отсутствие необязательных полей

#### Scenario: Некорректный ответ
- **WHEN** ответ не является ожидаемым объектом, содержит другой match ID, повторяющиеся слоты или некорректные базовые поля
- **THEN** клиент возвращает ошибку формата, не кеширует ответ и не выдаёт его за успешную загрузку

### Requirement: Отсутствующие значения и идентификация игроков

Клиент MUST сохранять различие между отсутствующим полем, `null`, пустым массивом и числовым нулём. Отсутствие публичного account ID SHALL сохранять запись игрока; идентификатором игрока внутри матча является `player_slot`.

#### Scenario: Анонимный союзник
- **WHEN** у игрока отсутствует account ID, он равен `null` или значению анонимного аккаунта
- **THEN** клиент сохраняет его героя, слот и доступную статистику без создания фиктивного Steam аккаунта

#### Scenario: Статистика не получена
- **WHEN** значение урона отсутствует, другое поле равно `null`, а число смертей равно нулю
- **THEN** клиент возвращает эти три разных состояния без подстановки нулей в отсутствующие поля

### Requirement: Признак разбора реплея

Клиент SHALL различать `basic` и `parsed` по наличию положительной версии разбора в ответе OpenDota. `parsed` SHALL означать наличие признака разбора, а не гарантию полноты всех расширенных полей; их отсутствие сохраняется в данных.

#### Scenario: Есть только базовая статистика
- **WHEN** положительная версия разбора отсутствует
- **THEN** клиент возвращает `basic`, даже если часть дополнительных полей присутствует

#### Scenario: Разобранный матч с неполными данными
- **WHEN** положительная версия разбора есть, но некоторые логи или временные ряды отсутствуют
- **THEN** клиент возвращает `parsed`, сохраняя пропуски для оценки полноты следующим модулем

### Requirement: Явный запрос разбора реплея

Клиент SHALL отправлять запрос разбора только при явном вызове соответствующей операции и возвращать job ID OpenDota. Обычное чтение матча или истории MUST NOT создавать задания разбора. Одновременные запросы разбора одного матча в одном экземпляре клиента SHALL использовать один POST.

#### Scenario: Реплей поставлен в очередь
- **WHEN** вызывающий модуль явно запрашивает разбор и OpenDota возвращает корректный job ID
- **THEN** клиент возвращает этот ID для последующего ожидания или сохранения

#### Scenario: Два параллельных инициатора
- **WHEN** два вызова одновременно запрашивают разбор одного матча
- **THEN** клиент выполняет один POST и возвращает обоим результат этого запроса

#### Scenario: Неопределённый результат POST
- **WHEN** запрос разбора завершается таймаутом, обрывом связи, ответом 5xx или некорректным успешным ответом
- **THEN** клиент сообщает об ошибке и возможности уже созданного задания, без автоматического повторного POST

### Requirement: Чтение состояния задания

Клиент SHALL различать существующую запись задания и ответ `null`, сохраняя доступные поля существующей записи. Исчезновение задания MUST NOT трактоваться как доказательство успешного разбора или как основание автоматически создать новое задание.

#### Scenario: Задание присутствует
- **WHEN** OpenDota возвращает корректный объект задания
- **THEN** клиент возвращает состояние `present` и доступные поля без выдуманного конечного статуса

#### Scenario: Задание отсутствует
- **WHEN** OpenDota возвращает `null`
- **THEN** клиент возвращает состояние `missing`, не объявляя матч разобранным

### Requirement: Ограниченное ожидание разобранного матча

Клиент SHALL поддерживать ожидание по match ID и известному job ID с общим сроком и отменой. Успех SHALL подтверждаться свежим ответом матча с признаком `parsed`. Ожидание MUST NOT создавать новые задания; истечение срока SHALL возвращать отдельный результат с последним успешно загруженным матчем и job ID.

#### Scenario: Разбор завершился
- **WHEN** при ожидании свежий ответ матча получает положительную версию разбора
- **THEN** ожидание завершается успешно с обновлёнными данными матча

#### Scenario: Задание исчезло раньше обновления матча
- **WHEN** задание возвращает `missing`, а свежий матч остаётся `basic`
- **THEN** клиент продолжает проверки в пределах срока без повторного POST

#### Scenario: Срок ожидания истёк
- **WHEN** срок истёк до получения `parsed`
- **THEN** клиент возвращает `timed-out`, последний успешный снимок или `null`, job ID и последнюю временную ошибку, если она была

#### Scenario: Временная ошибка во время ожидания
- **WHEN** чтение получает временную ошибку или ограничение частоты
- **THEN** клиент планирует следующую проверку в пределах общего срока, учитывая допустимое время повторения

### Requirement: Различимые ошибки и безопасные повторы

Клиент SHALL различать отсутствие ресурса, отказ авторизации, отклонённый запрос, ограничение частоты, сетевой сбой, таймаут, неверный ответ и отмену. Автоматические повторы SHALL применяться только к временным сбоям GET и оставаться ограниченными; постоянные ошибки и POST не повторяются автоматически.

#### Scenario: Временный сбой чтения
- **WHEN** GET получает сетевой сбой, таймаут или 5xx
- **THEN** клиент выполняет ограниченные повторы с задержкой, после чего возвращает данные или типизированную ошибку

#### Scenario: Постоянная ошибка
- **WHEN** OpenDota отвечает 400, 401, 403 или 404
- **THEN** клиент возвращает соответствующую ошибку без автоматического повтора и без подмены пустым успешным ответом

### Requirement: Соблюдение ограничений API

Клиент SHALL учитывать общий бюджет запросов своего экземпляра и повышенную стоимость запроса разбора. При 429 клиент SHALL учитывать корректный `Retry-After`, а при его отсутствии назначать ограниченную паузу. До разрешённого времени новые обращения SHALL возвращать время возможного повтора без сетевого запроса.

#### Scenario: Ограничение со стороны OpenDota
- **WHEN** API возвращает 429 с допустимым `Retry-After`
- **THEN** клиент возвращает ошибку ограничения с временем повторения и не обращается к API до этого времени

#### Scenario: Локальный бюджет исчерпан
- **WHEN** очередное обращение превысит общий минутный бюджет с учётом стоимости POST разбора
- **THEN** клиент возвращает локальную ошибку ограничения и ближайшее разрешённое время без отправки HTTP-запроса

### Requirement: Кеш и одинаковые запросы

Клиент SHALL иметь ограниченный кеш успешных чтений с временем жизни и возможность свежего чтения матча. Одинаковые параллельные GET без пользовательского сигнала отмены SHALL объединяться. Ошибки и некорректные ответы MUST NOT кешироваться, а проверки готовности реплея MUST NOT использовать кеш.

#### Scenario: Повторное чтение свежих данных
- **WHEN** повторный GET соответствует ещё действующей записи кеша
- **THEN** клиент возвращает её без сетевого запроса, сохраняя исходное время загрузки

#### Scenario: Проверка готовности после запроса разбора
- **WHEN** выполняется ожидание разбора или явно запрошено свежее чтение матча
- **THEN** клиент читает OpenDota без использования кеша и обновляет кеш успешным ответом

#### Scenario: Параллельные чтения
- **WHEN** одинаковые некешированные GET без пользовательского сигнала выполняются одновременно
- **THEN** они используют один HTTP-запрос, а последующая ошибка не сохраняется в кеше

### Requirement: Отмена операций

Клиент SHALL поддерживать пользовательскую отмену чтения и ожидания. После отмены он SHALL завершать данный вызов с отдельной ошибкой отмены, прекращать его задержки и новые запросы. Отмена одного вызова MUST NOT отменять независимую работу других потребителей.

#### Scenario: Отмена ожидания
- **WHEN** сигнал отменён во время интервала между проверками
- **THEN** ожидание завершается без следующего запроса и освобождает таймеры

#### Scenario: Заранее отменённый вызов
- **WHEN** операция запускается с уже отменённым сигналом
- **THEN** клиент возвращает ошибку отмены до чтения кеша или отправки запроса

### Requirement: Необязательный ключ API

Клиент SHALL работать без ключа OpenDota и поддерживать ключ из конфигурации окружения. Ключ MUST NOT попадать в возвращаемые данные, ошибки, URL диагностики, логи или тестовые примеры.

#### Scenario: Запуск без ключа
- **WHEN** ключ API не задан
- **THEN** клиент использует публичный API с тем же контрактом результатов и ошибок

#### Scenario: Ошибка запроса с ключом
- **WHEN** запрос с настроенным ключом завершается ошибкой
- **THEN** диагностические данные не содержат ключ, заголовок авторизации или необработанное тело ошибки API
