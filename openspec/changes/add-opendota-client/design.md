# Design

## Context

Проект пока содержит только OpenSpec и локальную интеграцию Codex. Прикладного кода, зависимостей и существующих соглашений модулей нет. Мотивация и границы изменения описаны в [proposal.md](proposal.md), контракт поведения — в [spec.md](specs/opendota-client/spec.md).

На 17 октября 2026 проверены:

- [Публичная OpenAPI-схема](https://api.opendota.com/api): история с `limit`/`offset`, данные матча, запрос и чтение задания разбора, необязательный ключ и авторизация Bearer.
- [Обработчики API](https://github.com/odota/core/blob/master/svc/api/spec.ts): POST возвращает `{ "job": { "jobId": ... } }`; GET задания возвращает объект с `jobId` либо `null`. Запрос разбора не является проверкой его готовности.
- [Определения данных](https://github.com/odota/core/blob/master/global.d.ts): расширенные поля и account ID могут отсутствовать; `lane_role` и оценка позиции — разные поля.
- [Настройки OpenDota](https://github.com/odota/core/blob/master/config.ts): исходники содержат отдельные ограничения для запросов с ключом и без него. Это настройки upstream, а не гарантия тарифа или квоты публичного сервиса.
- Два безопасных живых GET: пример матча `271145478` вернул HTTP 200, десять игроков и `version: 22`; `/request/1` вернул HTTP 200 с `null`. Это проверка формата, не калибровка оценки на ваших матчах.

### Проверка предоставленных матчей

| Матч | Наша сторона и герои | Наблюдение API |
|---|---|---|
| [9044556864](https://www.opendota.com/matches/9044556864) | Radiant, победа за 25:13; Phantom Lancer и Dragon Knight | При первом GET уже `version: 22`; доступны временные ряды, логи, 9 командных драк и 20 событий объектов. Повторный разбор не запрашивался. |
| [9046778399](https://www.opendota.com/matches/9046778399) | Radiant, поражение за 49:24; Juggernaut, Lich и Dawnbreaker | Первый GET без версии, логов и временных рядов. Один POST разбора вернул HTTP 200 и `job.jobId: 588786891`. Последующий GET задания вернул `null`, а GET матча — `version: 22`, 14 командных драк, 29 событий объектов и 50 точек ряда золота. |

Получен реальный переход `basic → parsed`. Исчезновение записи задания наблюдалось уже после разбора; успех подтверждён данными матча. Случай `missing` при ещё базовом матче остаётся изолированным тестовым сценарием, а не наблюдавшимся фактом. Прямые HTTP-запросы проверяют upstream, но не являются тестами ещё не реализованного TypeScript клиента.

Эти матчи используются как источники данных для будущих фикстур; сохранённых полных JSON-снимков в проекте пока нет. После разбора второй матч уже нельзя использовать как гарантированно базовый ответ живого API: состояние до разбора необходимо воспроизводить изолированной фикстурой. Ошибки недоступного реплея, 429 и длительная очередь вживую пока не проверены.

Уточнение пользователя для следующих модулей: настраивается простой список Steam32 account ID компании без привязки к людям или Discord. Для авторазбора достаточно двух аккаунтов из списка на одной стороне. Phantom Lancer (`98341323`) и Juggernaut (`113756505`) включаются как отдельные аккаунты; владение и тот, кто сейчас на них играет, для отбора матчей не нужны. Аккаунты остальных указанных героев: Dragon Knight — `122376567`, Lich — `440101453`, Dawnbreaker — `98558045`. Клиент обрабатывает каждый account ID независимо.

## Goals / Non-Goals

**Goals:** дать вызывающему коду небольшой типизированный API, сохранить данные для будущего анализа и исключить бесконечное ожидание или скрытое создание повторных parse jobs.

**Non-Goals:** клиент не определяет нашу команду, роли и худшего игрока, не хранит задачи между перезапусками и не запускает фоновые опросы самостоятельно. Постоянную обработку и решение о повторном запуске обеспечивает будущий модуль обнаружения.

## Decisions

### 1. Небольшой самостоятельный модуль

Планируемый каталог — `src/opendota/`: публичный клиент, типы и ошибки, небольшие внутренние функции HTTP и проверки ответов. Одна точка экспорта для остальных модулей. Разделять внутренние функции на файлы только по мере необходимости; отдельные repository/service слои здесь не нужны.

Использовать встроенные `fetch`, `AbortController` и `node:test`. TypeScript компилируется перед запуском тестов; реализация должна поддерживать установленный Node.js 22.14 и Linux. Внешний SDK и полная генерация типов из OpenAPI не выбраны: нужны четыре endpoint, а схема заданий недостаточно точна.

### 2. Публичный контракт

Клиент создаётся один раз на процесс. В production базовый адрес фиксирован: `https://api.opendota.com/api`. Необязательный `OPENDOTA_API_KEY` читается при сборке конфигурации и передаётся клиенту; транспорт отправляет `Authorization: Bearer ...`, без ключа в query string. Для тестов допускается подмена транспорта и часов без изменения production окружения.

| Операция | Вход | Выход / endpoint |
|---|---|---|
| `getPlayerMatches` | `accountId`, `limit = 20`, `offset = 0`, `signal?` | Страница `PlayerMatch[]`; GET `/players/{accountId}/matches?limit=...&offset=...&significant=0` |
| `getMatch` | `matchId`, `fresh = false`, `signal?` | `MatchSnapshot`; GET `/matches/{matchId}` |
| `requestParse` | `matchId`, `signal?` | `{ matchId, jobId }`; POST `/request/{matchId}` |
| `getParseJob` | `jobId`, `signal?` | `{ state: 'present', data }` или `{ state: 'missing' }`; GET `/request/{jobId}` |
| `waitForParsedMatch` | `matchId`, `jobId`, `timeoutMs = 900000`, `signal?` | `parsed` или `timed-out`; новых POST не выполняет |

Значения по умолчанию и диапазоны — наши проектные решения:

- `matchId`: положительный `Number.isSafeInteger`.
- `accountId`: целое Steam32 от 1 до 4294967294; 0 и 4294967295 не принимаются как аккаунты для запроса истории.
- `jobId`: строка положительного десятичного целого в безопасном диапазоне. Числовой ID из ответа приводится к строке; произвольный путь или строка URL не принимаются.
- `limit`: целое 1–100; `offset`: неотрицательное безопасное целое. Клиент загружает одну страницу и сохраняет порядок ответа; автоматического обхода истории нет.
- `timeoutMs`: положительное конечное безопасное целое в миллисекундах.

`significant=0` исключает скрытый фильтр значимости OpenDota. Режимы, включая `lobby_type`, возвращаются как получены. Политику «только рейтинговые» реализует следующий модуль.

`MatchSnapshot` содержит `data`, `parseState: 'basic' | 'parsed'` и `retrievedAt` — Unix timestamp в миллисекундах фактической загрузки. Исходные времена матча остаются в единицах OpenDota.

Результат ожидания:

```ts
type ParsedMatchResult =
  | { state: 'parsed'; matchId: number; jobId: string; snapshot: MatchSnapshot }
  | {
      state: 'timed-out';
      matchId: number;
      jobId: string;
      snapshot: MatchSnapshot | null;
      lastError: OpenDotaErrorSummary | null;
    };
```

### 3. Проверять основу ответа, сохранять расширенные данные

Типы описывают используемые поля; дополнительные ключи сохраняются как `unknown`. Не поддерживать вручную копию всей схемы OpenDota и не удалять незнакомые поля при проверке.

Минимум матча: совпадающий `match_id`, неотрицательные целые `start_time` и `duration`, целые `game_mode` и `lobby_type`, `radiant_win` типа boolean либо null и массив `players`. Для каждой записи обязательны уникальный целый `player_slot` в диапазоне 0–255 и положительный целый `hero_id`. Не требовать ровно десять игроков: неполный массив сохраняется, а его пригодность проверяет модуль подготовки фактов.

Минимум строки истории: корректный `match_id`, `player_slot`, `start_time`, `duration`, `hero_id`, `game_mode`, `lobby_type` и boolean/null `radiant_win`. Числовые поля, используемые клиентом, должны иметь ожидаемый тип и конечное значение; неизвестные поля не проверяются как известная статистика. Некорректная строка делает страницу ошибочной, без молчаливого пропуска матчей.

Account ID, ник, расширенные метрики, логи, временные ряды, оценки позиции и версия разбора необязательны. Исходные `null`, 0, пустые массивы и отсутствующие ключи сохраняются. Анонимные account ID не используются как ключи игроков. Клиент не вычисляет роли, рейтинг вклада, процентили и производные показатели.

Положительный целый `version` даёт `parsed`; отсутствие, null или 0 дают `basic`. Остальные значения версии — ошибка формата. `parsed` не обещает наличие всех событий: более старые реплеи могут не содержать новых полей.

### 4. Разбор и ожидание

`requestParse` выполняет один явный POST, инвалидирует кеш матча и проверяет `job.jobId`. Параллельные вызовы одного match ID используют один выполняющийся POST; после завершения запись об этом запросе удаляется. Последующий отдельный вызов считается новым явным запросом, поэтому постоянную дедупликацию обеспечивает вызывающий модуль.

`getParseJob` не кешируется. Для объекта проверить `jobId` на соответствие запрошенному, а `data.match_id`, если это поле присутствует, использовать для проверки соответствия при ожидании. В остальном запись сохраняется без предположений о конечном статусе. `null` означает только отсутствие записи.

`waitForParsedMatch` сначала выполняет свежее чтение матча. Если он остаётся `basic`, читает известный job и повторяет цикл через 15 секунд. Вызовы проверяются общим ограничителем API. `missing` не является успехом или поводом повторить POST. Временные ошибки и `rate_limited` сохраняются и переносят следующую проверку; для ограничения учитывается `retryAt`.

Общий срок включает HTTP-запросы, повторы и задержки. Внутренние таймауты ограничиваются оставшимся временем. На сроке вернуть `timed-out` с последним успешным снимком и последней временной ошибкой либо null. Отмена, неверный формат, неверный job/match ID, 400, 401, 403 и 404 завершают операцию ошибкой сразу.

После перезапуска процесса вызывающий модуль сможет передать сохранённый job ID снова. Сам клиент не создаёт SQLite таблицы и не гарантирует дедупликацию между процессами.

### 5. Ошибки, повторы и бюджет

`OpenDotaError` содержит безопасное сообщение, `code`, имя операции, HTTP status при наличии, `retryAt` для ограничения и `requestMayHaveSucceeded` для неопределённого исхода POST. Не включать необработанные headers, body, URL с параметрами авторизации или исходный сетевой объект ошибки в диагностику.

Коды: `invalid_argument`, `not_found`, `unauthorized`, `forbidden`, `bad_request`, `rate_limited`, `network_error`, `timeout`, `upstream_error`, `invalid_response`, `aborted`.

- Один HTTP attempt имеет таймаут 10 секунд. GET при network error, timeout и 5xx повторяется максимум два раза с задержками 1 и 2 секунды плюс случайная добавка 0–250 мс.
- 400/401/403/404, другой неуспешный 4xx и неверный успешный ответ не повторяются. Неизвестный 4xx классифицируется как `bad_request` с исходным status.
- POST не повторяется автоматически. Таймаут, обрыв, 5xx и некорректный 2xx имеют `requestMayHaveSucceeded: true`; клиент не утверждает, что задания точно нет.
- Общий бюджет одного клиента: 60 единиц в скользящем окне 60 секунд; GET стоит 1, POST разбора — 10. Каждая реально отправленная попытка учитывается, в том числе повтор. Кеш и объединённые подписчики единицы не расходуют.
- При исчерпании бюджета вернуть `rate_limited` и ближайшее освобождение нужного числа единиц. Не держать скрытую очередь запросов.
- При 429 установить общий cooldown: `Retry-After` в секундах или HTTP-date; при отсутствии/некорректном значении — 60 секунд. До `retryAt` обращаться к сети нельзя. Если действуют несколько ограничений, выбирается наиболее позднее разрешённое время.
- Ключ API не увеличивает локальный бюджет автоматически и не гарантирует отсутствие суточной или иной квоты. Расширение бюджета — отдельное изменение после измерений.

### 6. Кеширование и отмена

Один ограниченный кеш в памяти: максимум 100 ответов с вытеснением самой старой добавленной записи. TTL истории — 30 секунд; базового матча — 15 секунд; разобранного — 15 минут. Только успешные проверенные чтения. GET задания не кешируется. Ключ истории включает account ID, limit и offset.

`fresh` и ожидание обходят кеш матча, но успешный ответ обновляет его. Возврат из кеша сохраняет `retrievedAt`; ошибка свежего чтения не подменяется старым кешем. Результат возвращается копией, чтобы потребитель не повредил кеш другого вызова.

Параллельные одинаковые GET объединяются только без пользовательского `signal`; вызовы с сигналом выполняются независимо. Для объединённого POST отмена завершает ожидание конкретного подписчика, а общий HTTP attempt ограничивается собственным таймаутом. Если все подписчики отменились до отправки POST, он не отправляется; отправленный POST мог уже создать задание. Отмена одного подписчика не отменяет остальных.

Все операции проверяют заранее отменённый сигнал до чтения кеша и запроса. Обычные отдельные запросы используют объединение пользовательского сигнала и внутреннего таймаута; таймеры и обработчики снимаются после завершения.

## Risks / Trade-offs

- [OpenDota появляется с задержкой или не содержит часть матчей] → пустой результат не считается доказательством отсутствия игр; клиент поддерживает пагинацию, а повторный поиск планируется следующим модулем.
- [Реплей недоступен или очередь дольше 15 минут] → ограниченный результат ожидания и сохранённый job ID; дальнейший режим анализа решает вызывающий модуль.
- [Исходники upstream отличаются от production] → реальные GET, POST и переход basic → parsed проверены напрямую; будущий клиент проверяется отдельно изолированными тестами и smoke-прогоном после реализации.
- [Опрос друзей расходует квоту] → общий минутный бюджет клиента, кеш и явный `retryAt`; период опроса и необходимость платного ключа определяются в модуле обнаружения.
- [Локальное объединение запросов не работает между процессами] → первая версия бота работает одним процессом; постоянная дедупликация остаётся в будущем хранилище.

## Migration Plan

Существующего кода и данных нет, миграции не требуются. При реализации добавить минимальную TypeScript сборку, модуль и изолированные тесты. Подключать Discord, OpenRouter, постоянную БД или деплой в рамках этого изменения не требуется.

Проверка перед готовностью: типизация, тесты сценариев и реальные GET на предоставленных match ID после реализации клиента. Повторный POST для уже разобранных примеров не нужен; сценарий исходного `basic → parsed` воспроизводится изолированно. Дополнительный POST smoke выполняется отдельно на новом выбранном матче, без автоматической постановки реальных заданий в обычных тестах. Все задачи остаются открытыми до реализации; изменение не архивируется сейчас.
