# Лаборатория оценки

Локальный инструмент для сравнения полного и сокращённого контекста MiMo на фиксированных матчах. Это исследовательский модуль: инструкция `v1` экспериментальная, её качество не подтверждается сборкой или тестами.

Нужны Node.js 22.14+ и npm. Общие команды из корня проекта:

```powershell
npm.cmd ci
npm.cmd run typecheck
npm.cmd test
npm.cmd run lab -- --help
```

`npm test` сначала собирает TypeScript. При изменении исходников перед отдельным запуском CLI выполните `npm.cmd run build`. В Linux те же команды используют `npm` вместо `npm.cmd`. Файловая система должна поддерживать атомарные rename и hard link в пределах одного каталога. Песочница Codex на Windows может запрещать эти операции с `EPERM`; тесты нужно запускать с локальными разрешениями, не заменяя атомарную запись небезопасным fallback.

## Рабочий порядок

### 1. Снимки

```powershell
npm.cmd run lab -- collect --match-id 9044556864 --side radiant
npm.cmd run lab -- collect --match-id 9046778399 --side radiant
npm.cmd run lab -- collect --match-id 9047349496 --side dire
```

Без `--from-file` выполняется ровно один публичный GET OpenDota, без ключа, кеша, повторов и POST разбора. Необязательный `--split holdout` назначает матч проверочным; по умолчанию `development`. До появления клиента OpenDota используется минимальный исследовательский транспорт в `corpus.ts`; позже его заменяет публичный `getMatch(matchId, { fresh: true })` без изменения формата артефактов.

Импорт без сети:

```powershell
npm.cmd run lab -- collect --match-id 101 --side radiant --from-file .local/match.json
```

`retrievedAt` у импорта без исходной даты будет `null`. Известную дату можно передать через `--retrieved-at ISO_DATE`. `importedAt` всегда отдельное время. Для искусственно изменённых данных нужны `--parent-digest SHA256` и при необходимости `--original-match-id ID`: источник будет `derived-fixture`, ограничение попадёт в контекст. Не объявляйте такой файл прежним состоянием API.

Сырые UTF-8 байты сохраняются в `.local/evaluation/snapshots/<matchId>/<sha256>.json`. Обновлённый матч создаёт новый снимок; старый остаётся. Текущий `corpus.json` обновляется атомарно, предыдущие ревизии хранятся в `corpora/`. Все стороны и производные одного исходного match ID должны принадлежать одному разделу.

Коллектор сохраняет и непригодные ответы, если match ID совпал. `prepare` отдельно проверяет рейтинговый режим, исход, длительность, героев, уникальность слотов и наличие пяти союзников. Анонимность аккаунта не исключает игрока. Начальный исследовательский профиль: lobby 5/6/7 и game mode 1/2/3/16/22; это не политика будущего автоматического поиска.

### 2. Исходная оценка

Скопируйте `evaluation/templates/labels.json` в `.local/evaluation/labels.json` и заполните записи. Пример на вымышленном матче:

```json
{
  "matchId": 101,
  "side": "radiant",
  "snapshotDigest": "SHA256_ИЗ_CORPUS",
  "status": "selection",
  "acceptableSelections": [[1], [1, 3]],
  "modelOutputSeen": false,
  "reasons": [
    {
      "playerSlot": 1,
      "subjective": false,
      "paths": ["/players/1/deaths"],
      "comment": "Проверяемое наблюдение; само число смертей ещё не доказывает плохую игру."
    },
    {
      "playerSlot": null,
      "subjective": true,
      "paths": [],
      "comment": "Моё впечатление от сыгранного матча."
    }
  ]
}
```

`[[1], [1, 3]]` разрешает либо слот 1, либо пару 1+3, а не произвольный выбор из этих игроков. Для `insufficient-evidence` и `unlabeled` массив альтернатив пуст. `unlabeled` отличается от сознательного отказа выбирать. Любой заполненной оценке нужны основания; личное впечатление помечается `subjective`.

Слоты Radiant: 0–4, Dire: 128–132. JSON pointers используют реальные индексы массива снимка, которые могут не совпадать со слотами. Проверяйте `/players/<index>/player_slot`.

Оболочка labels имеет `version: 1`, уникальную `revision`, `previousRevision: null` для первой версии, `createdAt` в ISO и `entries`. `prepare` архивирует точную ревизию. После изменений назначьте новую `revision`, укажите прежнюю в `previousRevision`, обновите дату. Старую ревизию нельзя перезаписать. Если уже видели анализ любой модели (включая Codex), ставьте `modelOutputSeen: true`; это не независимый эталон. Последующая ревизия не может скрыть этот факт.

### 3. План без сети

Скопируйте `evaluation/templates/experiment.json` в `.local/evaluation/experiment.json`, проверьте пути и список матчей:

```powershell
npm.cmd run lab -- prepare --experiment .local/evaluation/experiment.json
```

Пути `corpus`, `labels`, `prompt` разрешаются относительно рабочего каталога процесса. Путь `dictionary` в профиле — относительно папки инструкции. `--root` по умолчанию `.local/evaluation`; используйте его последовательно для всех четырёх операций.

Первый план: три development матча × full/compact × одно повторение = шесть запросов. Для изучения стабильности задайте `repeats: 3` и отдельный лимит отправок/бюджет. Внутри каждого матча варианты чередуются; на следующем повторении порядок меняется. Один ответ не измеряет стабильность.

План получает уникальную папку `plans/<planId>`. Он содержит точные копии корпуса, эталонов, снимков, инструкции, примеров, схемы, профиля, справочника, контекстов и готовых тел запросов. `plan.json` перечисляет SHA-256 всех этих файлов. Эталон и субъективные комментарии не включаются в запрос целевого матча. Изменение текста при прежнем названии версии меняет digest пакета/запроса.

`prepare` не читает ключ, не обращается к сети и не обрезает контекст. Превышение `maxRequestBytes` даёт `context-too-large`; для сокращения нужно отдельное представление/профиль. Изменённый или повреждённый артефакт блокирует `run`/`report`.

`examples.json` по умолчанию пуст. Каждый пример требует match ID, digest снимка, точного безопасного контекста, структурно проверенного ответа и пользовательской разметки источника. Разрешены только другие development матчи. Целевой матч, holdout или произвольно собранный контекст в пример не допускаются. Не копируйте вручную проверочные ответы/эталоны в текст инструкции: автоматическая проверка не распознаёт все такие утечки.

Для holdout задайте `holdoutUntouched: true` только после ручной проверки отсутствия подгонки. Если матч использовали для настройки, отметьте в корпусе `usedForTuning: true`, переведите все его стороны/производные в development с новой ревизией корпуса и выберите свежий holdout.

### 4. Явный запуск MiMo

Ключ `OPENROUTER_API_KEY` настройте локально в окружении процесса; не присылайте значение в чат и не добавляйте в файлы проекта. CLI не загружает `.env` автоматически. Импорт, `prepare` и `report` работают без ключа.

После выбора бюджета и просмотра плана:

```powershell
npm.cmd run lab -- run --plan .local/evaluation/plans/PLAN_ID --budget-usd 1 --max-requests 6
```

Число `1` — пример явного бюджета, не рекомендация и не обещание стоимости. До POST инструмент получает свежие публичные метаданные модели и endpoint, проверяет поддержку `temperature`, `max_tokens`, `response_format`, `structured_outputs`, пределы контекста и тарифы. Метаданные и время сохраняются в запуске. Неподдержанный формат, неизвестный тариф и недоступные метаданные останавливают запуск без подмены модели или свободного JSON режима.

Профиль v1: `xiaomi/mimo-v2.6-pro`, `stream: false`, `temperature: 0.2`, `max_tokens: 8192`, строгий `json_schema`, `require_parameters: true`. Список маршрутов в профиле: DeepInfra, GMICloud, Xiaomi; фиксируется предпочтение, фактический провайдер записывается при наличии в ответе. Reasoning оставлен upstream default. Изменения параметров требуют нового плана. `contextFields` фиксирует полный allowlist и исключения; он сверяется с реализацией преобразований, чтобы расхождение не осталось незаметным.

Оценка входных токенов `utf8-bytes-div-2-v1`: `ceil(UTF-8 bytes точного тела / 2)`. Это консервативная эвристика для текстового JSON, не токенизатор и не доказанная верхняя граница. Оценка следующей отправки: вход × максимальный известный входной тариф допустимых endpoint + `max_tokens` × максимальный выходной тариф + плата за запрос при наличии. Известные cache-тарифы также учитываются консервативно. Превышение оценочного контекста останавливает запуск, провайдерская ошибка о размере сохраняется отдельно.

Перед каждым POST проверяются бюджет и число отправок. Фактическая стоимость — только `usage.cost` или явно импортированная сверка по generation ID. Известные расходы сохраняются и для ошибочных/невалидных ответов. Предварительная оценка не гарантирует внешний потолок списания.

Перед отправкой записывается `attempt-<index>.json` со статусом `started`; результат атомарно завершает эту запись. Таймаут по умолчанию 180000 мс, можно задать `--timeout-ms`. Ctrl+C отменяет активный запрос и всю оставшуюся серию. Таймаут, обрыв или завершение процесса могут сопровождаться внешним списанием. Статусы: valid, invalid-output, api-error, transport-error, timed-out, aborted; оставшийся started в отчёте считается interrupted.

Автоповторов POST нет: 429, 5xx, неправильный JSON, усечение и API error в HTTP 200 завершают серию. `Retry-After` (секунды или HTTP date, при некорректном значении 60 секунд) сохраняется и проверяется перед следующим запуском. Каждый явный `run` создаёт новый run ID и заново выполняет план с первого запроса: это не возобновление.

Если стоимость попытки неизвестна, новые запросы останавливаются с `unknown-cost`. Для нового запуска сначала сверьте расход либо явно задайте `--reserve-unknown-usd NUMBER` на каждую неизвестную попытку в этом root. Резерв суммируется, включается в новый бюджет, но не становится фактической стоимостью. Альтернатива `--reconciliation FILE`:

```json
{
  "version": 1,
  "entries": [
    { "runId": "RUN_ID", "index": 0, "generationId": "gen-ID", "source": "openrouter-generation", "costUsd": 0.01 }
  ]
}
```

Данные должны быть получены из сведений OpenRouter о соответствующей генерации; JSON сам не доказывает достоверность введённой суммы. Сверка сохраняется в новой серии и не переписывает исходную попытку. История исходных неизвестных затрат остаётся видимой в отчётах.

`run` сохраняет только необходимые поля ответа: content, ID, модель/провайдера, finish reason, usage и безопасную категорию ошибки. Headers, reasoning и provider metadata не сохраняются; точное значение настроенного ключа удаляется, если оказалось в возвращённом тексте. Исходные сообщения ошибок API не публикуются.

### 5. Отчёт и ревью

```powershell
npm.cmd run lab -- report --plan .local/evaluation/plans/PLAN_ID
```

Без сети создаются `reports/<reportId>/report.json`, `report.md`, копия отзывов и `reviews-template.json`. В JSON есть тексты ответов, причины ошибок, исходные ограничения данных и отдельные показатели по вариантам/разделам. При необходимости ограничьте входы `--run-id ID,ID`.

Скопируйте сформированный reviews-template в отдельный локальный файл. Проверьте каждое основание (`reasonIndex` начинается с нуля), заполните `supported`/`unsupported`/`uncertain`, согласие, ошибки роли/причинности, пригодность roast и комментарий, затем измените статус записи с `unreviewed` на `reviewed`. Существующая ссылка на число не означает, что текстовый вывод из него верен. Русский язык, смысл объяснения/сравнения и стиль roast проверяются вручную.

```powershell
npm.cmd run lab -- report --plan .local/evaluation/plans/PLAN_ID --reviews .local/evaluation/my-reviews.json
```

Ревью имеет уникальную ревизию, дату, предыдущую ревизию, digest ответа и ревизию эталона. Изменение уже сохранённого отзыва требует новой ревизии. Если после прогона понадобился новый эталон, создайте новый план; нельзя молча заменить эталон старого плана. Отзывы на старый план сохраняют его разметку.

Отчёт показывает:

- валидные / все отправленные попытки и ошибки по статусам, включая interrupted;
- точное совпадение набора слотов с допустимой альтернативой среди валидных и среди всех отправок с эталоном; частичное пересечение не засчитывается;
- независимые эталоны отдельно от разметки после просмотра, неразмеченные и непросмотренные отдельно;
- проверенные утверждения, ошибки роли/причинности, пригодность roast среди реально просмотренных;
- парное full/compact сравнение по одному матчу, стороне, снимку, пакету, параметрам и повторению; неизвестный/разный провайдер исключает вывод об изолированном влиянии контекста;
- стабильность при минимум двух валидных ответах на одинаковые входы, с числом всех попыток рядом;
- медиану/min/max времени отдельно для успешных и ошибочных, токены с покрытием, известный subtotal и неизвестные расходы;
- число уникальных матчей и число попыток; повторения одного матча не увеличивают корпус.

Стадии: `tool-ready` — инструмент/артефакты доступны, эксперименты ещё не подтверждены; `hypotheses` — получены ответы и ручное ревью первых пар трёх development матчей; `candidate` — есть явная пользовательская рекомендация, минимум 10 реальных уникальных матчей и 3 независимых holdout, замороженный пакет, все проверочные ответы выбранного варианта просмотрены, нет нерешённых содержательных обвинений. Необходимое разнообразие, повторы и другие ограничения пользователь фиксирует отдельно: одно количество матчей качества не доказывает.

Поле `recommendation` в reviews по умолчанию `null`. Для запроса переноса укажите `variant`, `conclusion: candidate` (либо `not-confirmed`), непустые списки `matchFacts`, `matchAnalysis` и `limitations`. Если условия не выполнены, отчёт не выдаёт положительную рекомендацию. Артефакты соседних модулей автоматически не изменяются.

## Преобразования и форматы

Все оболочки имеют `version: 1`. Формы определены в `src/evaluation-lab/types.ts`; входы проверяются при соответствующей операции. Неизвестная версия отклоняется.

| Артефакт | Основные поля |
|---|---|
| corpus | revision, entries: matchId, side, split, snapshot, digest, retrievedAt/importedAt, source, originalMatchId, parentDigest, usedForTuning |
| snapshot | точные байты OpenDota JSON; оболочка и checksum находятся в corpus |
| labels | revision, previousRevision, createdAt, entries: snapshotDigest, status, acceptableSelections, modelOutputSeen, reasons |
| profile | id, model, параметры, предел размера, маршрут, reasoning default, разрешённые режимы, dictionary |
| plan | уникальный planId, packageDigest, ревизии корпуса/эталонов, holdoutUntouched, tokenEstimation, requests и digests всех artifacts |
| attempt | runId/planId/index, requestDigest, даты/elapsedMs, статус, ID/model/provider/finishReason/content/responseDigest, usage, error/retryAt |
| reviews | revision, previousRevision, createdAt, entries с привязкой к ответу/эталону и поэлементным claims, recommendation |

`full-v1` и `compact-v1` содержат всех доступных игроков, сторону, исход, длительность, parseState, справочник использованных героев/предметов, соответствие индекса слоту, limitations и evidence. В evidence: ID, слот или null, value, unit, исходные JSON pointers и transform.

Точный allowlist находится в `context.ts`: `summaryFields`, `seriesFields`, `logFields`, `mapFields`, `eventKeys`. В full входят итоговая экономика/KDA/урон/поддержка/предметы, доступные временные ряды, покупки/убийства/варды/выкупы/подключения, числовые карты использования способностей/предметов, общие объекты и командные драки. Строки разрешены только из проверенного справочника и фиксированных перечислений событий/объектов. Неизвестные поля остаются в сыром снимке, не попадают в модельный контекст.

В compact остаются итоговые поля, точные срезы 10/20/30 минут (только если время достигнуто и найдено в `times`), изменения экономики между 10–20 и 20–30, события покупок/убийств/выкупов, количества прочих доступных логов, общие объекты и число командных драк. Отсутствующие ряды не интерполируются и не заменяются нулями.

| Transform | Формула и происхождение |
|---|---|
| identity-v1 | исходное значение без арифметики; точный pointer |
| slice-Nm-v1 | значение `series[index]`, где `times[index] === N * 60`, при duration >= N * 60; pointers к времени и значению |
| delta-A-Bm-v1 | значение на B минус значение на A; четыре pointers к временам/значениям, оба среза должны существовать |
| array-length-v1 | length только реально существующего массива; pointer к массиву, единица count |

Золото и net worth — gold, опыт — xp, GPM/XPM — gold/minute и xp/minute, урон/лечение — hp, время — seconds. Прочие значения передаются как count-or-upstream-value без выдуманного пересчёта. `lane`/`lane_role` явно помечены upstream-role-hypothesis. Слоты проверяются по массиву снимка. Null, ноль и пустой массив остаются различимыми; отсутствию поля соответствуют ограничения. `parsed` не обещает полноту логов.

Справочник взят из OpenDota dotaconstants; URL и commit сохранены в `evaluation/dictionaries/dotaconstants-v1.json`. Неизвестный ID остаётся числом с ограничением, обновления из `prepare` запрещены. Синтетические данные для изолированных тестов создаёт `test/helpers.ts`, не используются как реальные эксперименты.

Источники протокола: [OpenRouter endpoints](https://openrouter.ai/docs/api/api-reference/endpoints/list-endpoints), [Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs), [Usage Accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting). Поддержка и тарифы проверяются заново в каждом `run`.

`.local/`, `.env*` (кроме пустого `.env.example`), node_modules и dist исключены из Git. Не переносите сырые снимки и личные оценки в публичные фикстуры/отчёты. Ни одна команда не использует Discord или SQLite приложения.

## Эксперимент v2

Пакет `evaluation/prompts/v2` добавляет `full-v2`/`compact-v2`, `analysis-v2`, предполагаемые позиции и карточки всех доступных драк обеих команд. В профиле явно заданы `contextVersion: 2`, `analysisVersion: 2`; отсутствие этих полей означает v1. Смешанные версии отклоняются. Параметры модели остались прежними, включая 8192 выходных токена. Старый пакет v1 сохранён.

Для нового плана укажите `prompt: "evaluation/prompts/v2"` в отдельном файле эксперимента и выполните обычный `prepare`. V2 не добавляет сетевых обращений. Сохранённый план содержит точные запросы, роли, ограничения, схемы и digests. Внутри одного отчёта сравнивается пара одной версии; сравнение v1/v2 выполняется по отдельным планам на одинаковых снимках с учётом отличий пакета и разметки.

`roles` содержит `position` 1–5 или null, источник `opendota-estimate`/`manual`/`unknown` и evidence ID исходного `position_est`, если он есть. Роли не назначаются по имени героя; противоречивые оценки остаются неизвестными. Для явной поправки добавьте в эксперимент числовое назначение, например:

```json
"roleOverrides": [{ "matchId": 101, "playerSlot": 0, "position": 5 }]
```

Назначение должно относиться к целевому матчу и существующему слоту. Повторные ручные слоты/позиции команды отклоняются. Ручное назначение имеет приоритет; конфликтующая оценка другого игрока становится неизвестной с ограничением. Отсутствующая роль не дополняется автоматически.

`fights` содержит индекс исходного эпизода, ссылки на start/end/deaths, участников с metrics и evidenceIds, ссылки на последующие объекты и ограничения. Числовые показатели сохраняют нули, пропуски — null. Индексы `teamfights.players` 0–9 переводятся в слоты 0–4/128–132 независимо от порядка `match.players`; массив неизвестного размера не размечается догадкой. Карты использования способностей/предметов и целей допускают только числовые значения с ключами проверенного справочника. Компактный вариант теперь сохраняет эти данные, но не длинные временные ряды.

`followingObjectives` включает события строго после end и не позднее end + 120 секунд; это временная близость, не доказательство причинности. [Обработчик OpenDota](https://github.com/odota/parser/blob/ac6e79c6d7d227f0ee68a98164d2cb4f6a47c45d/processors/processTeamfights.mjs) выделяет бои с минимум тремя смертями и может не включить незавершённый последний бой. Отсутствие карточки не доказывает отсутствие участия. `healing` карточки не приравнивается к итоговому `hero_healing` или спасению союзника.

Ответ содержит пять `playerAssessments`: позицию, ресурсы, вклад, проблемы, контраргумент и ограничения. Фактические поля требуют evidence ID, отсутствие наблюдений обозначается null/пустым списком с объяснением. Для одного выбранного игрока обязателен другой союзник `closestAlternative`, для пары/отказа это null. `confidence` low/medium/high — качественная уверенность в относительном выборе, не вероятность. «Слабейший среди пятерых» отделён от «сыграл плохо» и «виноват в исходе».

В reviews-template v2 `claims.section` адресует `resources`, `contributions`, `concerns`, `counterargument` и `alternative`; отсутствие section по-прежнему означает reasons выбранного игрока. `reasonIndex` — индекс внутри соответствующего поля, для одиночного факта 0. Статус reviewed требует проверки **всех** этих фактов, включая при отказе от выбора. Структура не проверяет смысл автоматически: согласие с кандидатом, роль/причинность и пригодность roast остаются отдельной ручной обратной связью.

Первые три известных матча используются для разработки; просмотр их разборов Codex учитывается в новой ревизии labels через modelOutputSeen. Общее согласие не заполняет за пользователя acceptableSelections. Более подробный контекст увеличивает размер запросов; превосходство v2 над v1, реальные токены, задержки и стоимость ещё не проверены.
